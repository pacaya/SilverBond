### R3-2 (#10). WS reconnect backoff reset on `onopen` → reconnect storm (FINALIZED)
**Severity:** HIGH (bounded) — confirmed verbatim on current HEAD (`flickering-fluttering-iverson` never touched `client.ts`). Reachable in normal use (viewing a pane of a completed/failed run, or a stale `selectedPane` per R3-6). On loopback it won't DoS the box but is a persistent ~2 req/s busy-loop per stale viewer (WS upgrade + `get_run` DB hit + warn-log spam) until the user navigates away.
**Files:** ui/src/lib/api/client.ts:212-215 (`ws.onopen` resets `reconnectDelay` to base before any frame), ui/src/lib/api/client.ts:178 + 131 (`reconnectDelay` init 500ms / `PANE_RECONNECT_BASE_MS`), ui/src/lib/api/client.ts:193 (double-capped-at-5000ms in `scheduleReconnect`), ui/src/lib/api/client.ts:249-254 (`onclose` schedules reconnect); backend src/api.rs:530 (`ws.on_upgrade` accepts unconditionally), src/api.rs:553 + 557 (pane resolved after upgrade; `send_socket_error_and_close` on failure), src/api.rs:677 + 712-714 (`resolve_run_pane_context` bail paths), src/api.rs:571 (warn-log spam).
**Description:** The backend completes the WS upgrade unconditionally (src/api.rs:530) and only then resolves the pane (src/api.rs:553); when it can't (`resolve_run_pane_context` bails at src/api.rs:712-714 for finished/no-pane runs) it error-frames and closes (src/api.rs:557). Because the upgrade already succeeded, the client's `ws.onopen` (ui/src/lib/api/client.ts:212) fires and resets `reconnectDelay` back to 500ms (:213) on every cycle; `onclose` (:249-254) then schedules a reconnect at that just-reset 500ms. The result is a steady 500ms reconnect loop that never escalates toward the 5000ms cap — exponential backoff is defeated for any pane that accepts-then-immediately-closes. A stale `selectedPane` pointing at a completed run's pane streams this loop indefinitely, burning CPU/DB and spamming `tracing::warn!` (src/api.rs:571). No tests cover reconnect backoff.
**Fix:** Frontend-only, two mechanisms together. (1) Remove the `reconnectDelay` reset from `ws.onopen` (ui/src/lib/api/client.ts:212-215) and instead reset it in `onmessage` upon the first `snapshot`/`data` frame of a connection (per-connection "first frame seen" flag), so an accept-then-error connection never resets backoff and the existing exponential growth (:193) takes effect. (2) Track each connection's open→close duration; after N consecutive closes within ~1s of opening, stop reconnecting and surface a terminal "pane unavailable" status to the user instead of looping. Add tests: an accept-then-immediately-close server causes backoff to grow (not stay at 500ms) and the client gives up with a terminal status after the threshold; a healthy stream that delivers a frame resets backoff normally.

### R3-5 (#12). Nested subflow catalog resolution inconsistent/broken (FINALIZED)
**Severity:** HIGH — confirmed on current HEAD (not mooted by `flickering-fluttering-iverson`). Fully reachable via UI; the catalog model is split-brained (recursive TS type vs flat backend) and no tests cover drill/compound/nested. A saved compound can't be re-opened and breaks the run.
**Files:** ui/src/lib/stores/workflowStore.svelte.ts:259 (`drillIntoSubflow` — root-only `this.workflow.subflows?.[name]`), ui/src/lib/stores/workflowStore.svelte.ts:221-227 (`resolveActive` — walks nested `doc.subflows?.[name]`), ui/src/lib/stores/workflowStore.svelte.ts:411 + 460-461 (`saveSelectionAsCompound` — writes to active doc via `wf = resolveActive(...)`); backend src/model.rs:676 (flat `BTreeMap` catalog; recursive type unused), src/runtime.rs:1489 + 2131 (subflow calls resolved against `root_workflow.subflows` only), src/model.rs:1290 + 1347 (validation iterates/resolves root catalog only).
**Description:** The subflow catalog is split-brained: the TS type permits nesting, but every consumer except `resolveActive` assumes a flat root. When the editor is drilled into subflow A and the user runs save-as-compound, the new subflow B is written into `A.subflows[B]` (ui/src/lib/stores/workflowStore.svelte.ts:461, because `wf = resolveActive(...)`). The immediate canvas looks correct since `resolveActive` (workflowStore.svelte.ts:221-227) is the only nested-aware reader, but `drillIntoSubflow` (workflowStore.svelte.ts:259) only checks `this.workflow.subflows`, so double-clicking B's new compound node fails to drill in. Worse, the runtime (src/runtime.rs:1489, 2131) and validator (src/model.rs:1347) resolve every subflow call against the **root** catalog only, so at execution time B is missing and the run errors. The backend model is a flat `BTreeMap` (src/model.rs:676) — the recursive TS type is unused by any backend path.
**Fix:** Frontend-only — converge all four layers on the flat root catalog the backend already enforces. (1) `saveSelectionAsCompound` (ui/src/lib/stores/workflowStore.svelte.ts:411, 460-461) writes the new compound to `this.workflow.subflows` (root) instead of the drilled active doc. (2) Flatten `resolveActive` (workflowStore.svelte.ts:221-227) to resolve every breadcrumb name from `this.workflow.subflows` rather than walking nested maps. (3) `drillIntoSubflow` (workflowStore.svelte.ts:259) already keys off root — leave it, now consistent with the other two. Move the name-collision check to root scope (names become globally unique). Add a regression test: drill into a compound, marquee-select, save-as-compound, then assert the new subflow is at root and is both re-drillable and resolvable by a (mocked) run.

### F12. Command-prefix editor corrupts the argv round-trip (FINALIZED)
**Severity:** MEDIUM — real corruption of operator-authored config, but triggers only when an argv token contains whitespace (most prefixes like `sudo -u sandbox --` have none); corruption is inspector-only and the mismatched hint is cosmetic.
**Files:** ui/src/features/editor/InspectorPanel.svelte:1526-1534 (editor input + `.join(" ")` render at :1529), ui/src/features/editor/InspectorPanel.svelte:73 (`updateRunAsCommand` write-back `.trim().split(/\s+/).filter(Boolean)`), ui/src/features/editor/InspectorPanel.svelte:83-88 (attach-hint `$derived` hard-coding `sudo -u <user>`); backend shape src/model.rs:201 (`command: Option<Vec<String>>`), verbatim spawn src/tmux_exec.rs:41-42, :71, test src/tmux_exec.rs:1816 (`build_invocation_command_prefix_is_verbatim`); correct backend hint src/api.rs:132-140.
**Description:** The Run-As command-prefix editor (InspectorPanel.svelte:1526-1534) renders the argv via `.join(" ")` (:1529) and parses it back via `.trim().split(/\s+/).filter(Boolean)` (:73, `updateRunAsCommand`). The backend treats `command` as a verbatim argv — `Option<Vec<String>>` (src/model.rs:201) passed straight to `Command::args` (src/tmux_exec.rs:41-42,71) — so any token containing whitespace is silently split into multiple tokens on round-trip (e.g. `["sudo","-u","Agent User"]` → `["sudo","-u","Agent","User"]`) and empty tokens are dropped, causing the backend to spawn the wrong prefix. Fix the attach-hint `$derived` (:83-88) to prefer `runAs.command.join(" ")` when set, mirroring src/api.rs:132. Add a vitest round-trip test asserting an argv element containing a space (e.g. `Agent User`) survives render→edit→write-back intact, and that the hint reflects a custom `command`.

### R3-3 (#21). `activeWorkflow` getter mutates `$state` during `$derived` (FINALIZED)
**Severity:** MEDIUM — confirmed on current HEAD (line refs drifted; Part A's backend rewrite didn't touch this frontend path). Hard runtime crash, but only when drilling into a subflow with no persisted `ui.canvas` (e.g. backend-loaded workflows whose subflows were never opened/saved) — real, reproducible, narrow trigger.

**Description:** `resolveActive` (workflowStore.svelte.ts:221-235) walks `this.workflow` (a `$state` object) along `drillStack` and, when the resolved subflow doc lacks `ui.canvas`, assigns `doc.ui = {...}` at :229 — a mutation of reactive `$state`. Audit the ~10 existing `resolveActive` call sites and point each at the pure or mutable variant as appropriate. Add a vitest asserting that drilling into a subflow with no `ui.canvas` and reading `activeWorkflow` does not mutate store state (no `state_unsafe_mutation`), while a subsequent `addNode`/`setNodePosition` does persist the canvas.

### R3-7 (#22). Debounced validation doesn't track nested workflow edits (FINALIZED)
**Severity:** MEDIUM — confirmed on current HEAD (line refs drifted; Part A's backend rewrite didn't touch this path). Validation is advisory (backend re-validates on save/run), so it's a stale UI hint not data corruption — but it's wrong after nearly every edit, which is more than cosmetic.
**Files:** ui/src/app/AppShell.svelte:73-83 (validation `$effect` — top-level read at :74, deep read inside the `setTimeout` callback at :78), errors/warnings pill ui/src/app/AppShell.svelte:332-336; in-place mutators ui/src/lib/stores/workflowStore.svelte.ts:277-283 (`updateWorkflow`), :344 (`wf.nodes.push`), :391 (`setNodePosition`), plus InspectorPanel callbacks; deep-clone helper ui/src/lib/workflow.ts:489-491 (`cloneWorkflow` → `JSON.stringify`).
**Description:** The debounced validation `$effect` (AppShell.svelte:73-83) reads only `store.workflow` as an opaque top-level reference at :74; its deep read happens later inside the `setTimeout` callback (`cloneWorkflow` → `JSON.stringify`) at :78, outside the effect's reactive tracking scope, so no nested field is ever registered as a dependency. Svelte 5 `$state` is deeply reactive, but only fields read *synchronously* during the effect are tracked. Because all editing flows through in-place nested mutation (workflowStore.svelte.ts:277-393, InspectorPanel callbacks) and never reassigns the top-level reference, the effect only re-runs on full-document swaps (`setWorkflow`/`createWorkflow`/`undo`/`redo`). User-visible impact: after the first validation, editing a node's prompt/timeout, adding/removing nodes or edges, moving nodes, or editing inside a drilled-in subflow does not re-trigger validation, so the errors/warnings pill (:332-336) goes stale until reload or undo/redo. No vitest covers validation re-run on nested edits.
**Fix:** In the validation effect (AppShell.svelte:74), perform a synchronous deep read inside the reactive scope — `const snap = $state.snapshot(store.workflow)` — and validate `snap` in the debounced callback instead of capturing the bare `store.workflow` reference. `$state.snapshot` walks the entire tree, so every nested field becomes a tracked dependency and the effect re-fires on any in-place edit; the snapshot is already detached/serializable, so it can be passed straight into the async validate mutation (replacing the later `cloneWorkflow`). Add a vitest asserting that an in-place nested edit (e.g. changing a node prompt via a store mutator) re-triggers the debounced validation.

Confirmed on current HEAD (Part A's backend rewrite didn't touch this frontend path), but transient and self-correcting: the new connection always leads with a snapshot that resets and repaints, so worst case is a momentary flicker of wrong bytes, not persistent corruption.

Add a vitest asserting that a `data` frame delivered on a socket after its `close()` (or after a replacing connection is opened) is not forwarded to `onData`/the terminal.

### R3-10 (#24). Gap detection appends data before snapshot repaint (FINALIZED)
**Severity:** LOW — lowered from MEDIUM (reviewer flagged it cosmetic). Confirmed on current HEAD, but transient: the snapshot does a full clear+repaint, so stale frames vanish within one round-trip — a brief flicker, never persistent corruption.
**Files:** ui/src/lib/api/client.ts:231-238 (`"data"` case — gap detect + `requestResync()` at :234, unconditional `onData` at :237), ui/src/lib/api/client.ts:227-230 (`"snapshot"` case → `onSnapshot`); full repaint in ui/src/features/runtime/PaneTerminal.svelte (snapshot handler).
**Description:** In the `"data"` case (client.ts:231-238), a detected sequence gap (`seq > lastSeq + 1`) calls `requestResync()` at :234 but does not `break`/`return`, so control falls through to :237 and `onData(...)` appends the out-of-order gap frame onto the buffer it just declared stale. No `resyncPending` state exists, so every incremental `data` frame arriving between the resync request and the snapshot's arrival is also written on top of the stale buffer. The window is one network round-trip; the snapshot handler (:227-230 → `onSnapshot`) triggers a full clear+repaint in PaneTerminal, so the inconsistency is overwritten and the effect is a brief visual flicker, not data corruption. No `client.paneStream.test.ts` case asserts gap-frame suppression.
**Fix:** Add a `resyncPending` flag in `streamPane`. On gap detection (client.ts:234), set `resyncPending = true`, call `requestResync()`, update `lastSeq`, and `return` before `onData` so the gap frame and all subsequent `data` frames are skipped while a snapshot is in flight. In the `"snapshot"` case (client.ts:227-230), clear `resyncPending = false` after `onSnapshot` so incremental frames resume. Heartbeats are unaffected. Add a vitest asserting that after a gap, `onData` is not called until a snapshot arrives, then resumes.
