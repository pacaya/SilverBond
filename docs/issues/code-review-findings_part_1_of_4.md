## HIGH (4)

### R1-1 (#1). ParallelBatch `collectorVar` written to global scope (FINALIZED)
**Severity:** HIGH — correctness bug + subflow isolation breach; fully reachable (`collectorVar` is a first-class UI field), though latent today (no shipped template or test triggers batch-collector-inside-subflow yet).
**Files:** src/runtime.rs:3486 (global write `checkpoint.var_map.insert(collector_var, …)`), src/runtime.rs:1519-1528 (`var_map_for_cursor` — returns scoped clone with no global fall-through), src/runtime.rs:2211 (subflow populates `cursor.var_map`), src/runtime.rs:3052 (subflow-exit restore from `parent_var_map`), src/runtime.rs:1421-1422 (top-level fallback to global), src/runtime.rs:3377 + 3515-3518 (`parent_index` / `call_stack` in scope at batch site), src/runtime.rs:3380 (stale `parent_cursor` snapshot — do not mutate).
**Description:** A ParallelBatch with `collectorVar` writes its aggregated result to the global `checkpoint.var_map` at src/runtime.rs:3486, but `var_map_for_cursor` (src/runtime.rs:1519-1528) returns `cursor.var_map.clone()` whenever non-empty and never merges global underneath. A subflow populates `cursor.var_map` from declared vars/inputs (src/runtime.rs:2211), so a downstream `var:collectorVar` lookup inside that subflow misses entirely — the batch result is invisible. Simultaneously the global write persists past subflow exit (`cursor.var_map` is restored from `frame.parent_var_map` at src/runtime.rs:3052, but `checkpoint.var_map` retains the leaked key), exposing the value to root-scope nodes and sibling cursors — an isolation breach. Top-level batches work only by accident, via the global fallback at src/runtime.rs:1421-1422.
**Fix:** At src/runtime.rs:3486, insert `collectorVar` into the live `checkpoint.active_cursors[parent_index].var_map` (the cursor's scoped map), and additionally write the global `checkpoint.var_map` only when `call_stack.is_empty()`. Both `parent_index` and `call_stack` are already in scope at the batch-completion site (src/runtime.rs:3377, 3515-3518), and this mirrors the existing `call_stack.is_empty()` guard at src/runtime.rs:3515. Mutate the live cursor in `checkpoint.active_cursors`, not the stale `parent_cursor` snapshot at src/runtime.rs:3380. Add a regression test: a ParallelBatch with `collectorVar` inside a subflow that declares a variable, asserting (a) a downstream node in the subflow reads the collected value, and (b) the value does not appear in root/global scope after subflow exit.

### R1-7 (#4). ParallelBatch task `Err` leaves run stuck in Running forever (FINALIZED)
**Severity:** HIGH — user-visible perpetual-`Running` checkpoint with no terminal event; not self-healing. Fires on infrastructure faults, not routine node failures. *(Line numbers drifted; mechanism intact on HEAD — `let _ = execute_workflow` predates the refactor.)*
**Files:** src/runtime.rs:3436 (batch join `Ok(Err(error)) => return Err(error)`), src/runtime.rs:1962 (`process_immediate_cursors().await?`), src/runtime.rs:1698 (`execute_workflow` loop `?`), src/runtime.rs:1854 + 4536 (`finalize_run`, only terminal-state writer), src/runtime.rs:774/796/902 (`let _ = execute_workflow(...)` spawn sites).
**Description:** When a ParallelBatch item's `run_cursor_task` returns `Err` — an infrastructure fault such as pane spawn failure, missing driver, or runner panic, **not** an ordinary `Ok(NodeResult{success:false})` — the batch handler propagates it out through `process_immediate_cursors` and out of `execute_workflow`. Because the future is spawned `let _ = …`, the `Err` is silently dropped and `finalize_run` never runs, so the DB checkpoint stays `Running`, no `done`/`failed` event fires, and the UI shows a perpetual spinner. This is a general single-choke-point gap for any `Err` exit from `execute_workflow`; batches just make it reachable. Recoverable only via `abort_run`/`restart_from`.
**Fix:** Apply both layers. (1) At src/runtime.rs:3436, convert a per-item task `Err` into an `Ok` batch-item result with `success: false` and the error text as stderr, so the batch completes via the normal `!success` terminal path and produces a coherent per-item summary with partial results preserved. (2) Replace each `let _ = execute_workflow(...)` (774/796/902, via a shared helper) with a wrapper that, on any `Err`, persists a `Failed` checkpoint and emits a terminal `workflow_error`+`done` event — a backstop guaranteeing no future early-`Err` path leaves a run stuck. Add a test forcing a per-item infra `Err` and asserting the run reaches a terminal `Failed` state with a `done` event.

### R1-8 (#8, incl R3-12). Subflow catalog bodies not fully validated (FINALIZED)
**Severity:** HIGH — reachable (saved subflows are hydrated into the catalog and a parent embedding a malformed body passes validation); failure mode is **silent** (skipped dangling edges, mis-merged collectors → stuck/wrong run) rather than a loud error. Raised independently in both the engine and frontend review batches.
**Files:** src/model.rs:1289-1313 (`validate_subflow_catalog` — only entry-node existence at 1292-1305 + nested call-config at 1307-1311), src/model.rs:786-1071 (`validate_workflow` per-node rule loop — NOT applied to bodies), src/model.rs:1088-1110 (edge loop — NOT applied to bodies), src/model.rs:1496-1513 (`validate_subflow_call_cycles` — flat-map cycle guard, already present), src/runtime.rs:2114-2211 (`handle_subflow_node` — no runtime re-validation), src/runtime.rs:1612 (dangling edges silently skipped, `else { continue; }`), src/api.rs:348 + 457 (`hydrate_saved_subflows` — load path making malformed bodies reachable).
**Description:** `validate_subflow_catalog` (src/model.rs:1289-1313) validates only each catalog subflow's `entry_node_id` existence (1292-1305) and the call-config of nested call/subflow nodes (1307-1311). It never runs subflow bodies through the per-node rule loop (src/model.rs:786-1071) or the edge loop (src/model.rs:1088-1110), so duplicate node ids, Decide outcome/branch-edge matching, ParallelBatch config, collector single-exit/inbound/duplicate-merge-key rules, Split fan-out rules, and dangling edge source/target are all unchecked inside saved subflows. A user can save a malformed subflow standalone (hydrated via src/api.rs:348/457), then save a parent that passes `validate_workflow` while embedding the broken body. At runtime nothing re-validates: `handle_subflow_node` (src/runtime.rs:2114-2211) repoints the cursor onto the subflow entry and walks edges, silently skipping dangling edges (src/runtime.rs:1612) and mis-merging collectors — yielding a stuck or silently-wrong run instead of a clean authoring-time error.
**Fix:** Extract the per-node + edge rule body out of `validate_workflow` into a shared `validate_graph_body(&workflow, prefix, issues)` helper, and invoke it for the root graph and once per entry in the flat `subflows` `BTreeMap`. Prefix issue messages and `node_id`s with the subflow name so issue ids don't collide across root/subflow scope. No visited-set is required — the catalog is flat and call-cycle safety is already handled by `validate_subflow_call_cycles` (src/model.rs:1496-1513). Guard the few root-only rules (entry node, run_as) so they don't misfire on bodies. Add a test: save a parent embedding a subflow body with a dangling edge / mismatched Decide outcome / two-exit collector, and assert `validate_workflow` reports the scoped issue.

### R3-11 (#14). ParallelBatch item bindings use unsupported `node:…output.path` syntax (FINALIZED)
**Severity:** HIGH — confirmed against current HEAD (the `flickering-fluttering-iverson` refactor did not fix it). Shipped and reachable: the flagship template is bundled and load-validated, but `validate_batch_node_config` only checks non-emptiness, so all three batches pass validation and abort at runtime with zero items spawned.
**Files:** src/runtime.rs:3739-3770 (`read_batch_items` — literal-key only: bare node id w/ array `parsed_output` at 3745, var-map name at 3752, node id w/ array `output` at 3755; error at 3756), src/runtime.rs:2701-2748 (`resolve_input_binding_source` — the richer `var:`/`node:<id>.output`/`node:<id>.parsedOutput.<path>` resolver used by Decide/subflow/call, NOT shared by the batch path), src/model.rs:1700-1726 (`validate_batch_node_config` — only checks `itemsBinding` non-empty), src/storage.rs:57 (template bundled via `include_dir!`), templates/multi-agent-plan-implementation.json:32, 59, 94 (the three `node:…output.<path>` bindings).
**Description:** `read_batch_items` (src/runtime.rs:3739-3770) treats `itemsBinding` as a literal key — a bare node id or var name that must resolve to a JSON array — with no `node:`/`var:` prefix handling and no nested-path (`.output.<path>`/`.parsedOutput.<path>`) support. The engine already has a richer resolver, `resolve_input_binding_source` (src/runtime.rs:2701-2748), used by Decide/subflow/call inputs, but the batch path never calls it. The shipped flagship template `templates/multi-agent-plan-implementation.json` binds all three ParallelBatch nodes with `node:…output.<path>` syntax (lines 32, 59, 94), none of which is a literal node id or var name, so each lookup misses and returns `Err("parallel_batch itemsBinding \"…\" is not set")` (src/runtime.rs:3756) — a clean abort before any item spawns. `validate_batch_node_config` (src/model.rs:1700-1726) only checks non-emptiness, so the failure surfaces at runtime rather than authoring time; existing tests exercise only the bare-id/var forms (src/runtime.rs:5675, 7028), which is why it regressed silently.
**Fix:** Factor the `node:`/`var:`/`parsedOutput.<path>` parsing out of `resolve_input_binding_source` (src/runtime.rs:2701) into a shared helper returning a `serde_json::Value`, call it from `read_batch_items` (src/runtime.rs:3739), and require the resolved value be a JSON array (error otherwise). This unifies the batch item-source grammar with Decide/subflow/call so authors get one consistent binding syntax. Note the current resolver returns `String`, so a `Value`-returning variant is needed. Add tests covering `node:<id>.output.<path>`, `node:<id>.parsedOutput.<path>`, and `var:` bindings that resolve to arrays, and a load-and-run test of the flagship template's three batches.

### R1-2 (#15). Decide outcome matching: order-dependent substring fallback misroutes (FINALIZED)
**Severity:** MEDIUM — silent wrong-branch routing; prefix-overlap is author-constructible (not reachable in shipped templates), but reasoning-bleed misroute is reachable for any template.
**Files:** src/runtime.rs:2776-2790 (`select_decide_outcome`), src/runtime.rs:2783 (trimmed exact-match attempt), src/runtime.rs:2787-2788 (`contains` substring fallback), src/model.rs:347 (author-ordered `outcomes: Vec<String>`), src/runtime.rs:2640-2642 (selected outcome routes the next edge), src/model.rs:1636-1666 (outcome validation — no overlap guard).
**Description:** `select_decide_outcome` (src/runtime.rs:2776-2790) maps a decide agent's response to one of the node's enumerated outcomes. It first tries a trimmed exact match (src/runtime.rs:2783) — good — but on miss falls back to `outcomes.iter().find(|o| response.contains(o.as_str()))` (src/runtime.rs:2787-2788), returning the *first* outcome whose label appears anywhere in the raw response. Because `outcomes` is an author-ordered `Vec<String>` (src/model.rs:347), the scan is order-dependent: with overlapping labels (`approve` listed before `approve_with_changes`) or when the agent's reasoning prose merely mentions a sibling outcome name, the wrong label wins. The selected outcome routes the next edge (src/runtime.rs:2640-2642), so the run silently takes the wrong branch with no error raised. Validation (src/model.rs:1636-1666) rejects empty/duplicate labels but not substring-overlap. (Related to the finalized Part 2 F9, which addresses the upstream response-extraction corruption.)
**Fix:** Keep the exact-match-first attempt (src/runtime.rs:2783). Replace the `contains` fallback scan (src/runtime.rs:2787-2788) with a word-boundary match (regex with every label properly escaped). Among all matching outcomes, rank by earliest byte offset of the match, then by longest label, to pick the most specific/earliest candidate. If two labels tie ambiguously, return `None` so the run takes the existing no-match failure path rather than silently guessing. Add tests covering: overlapping labels (`approve` vs `approve_with_changes`) resolving to the correct one; reasoning-bleed (response prose mentions a sibling token) not misrouting; and an ambiguous multi-match returning no outcome.

> the echoed prompt contains exact occurrences of every label. Coordinate with the Part 2 owner.

### R1-4 (#17). Subflow with zero declared variables leaks global scope (FINALIZED)
**Severity:** MEDIUM (soft) — confirmed on current HEAD. Reachable but uncommon (the only shipped subflow declares 1 var, so never hits the empty path); silent corruption when a zero-var subflow reads a same-named root variable (accidental capture). **Files:** src/runtime.rs:1519-1528 (`var_map_for_cursor`), src/runtime.rs:1523 (guard `if cursor.var_map.is_empty()` — falls back to global, ignores `call_stack`), src/runtime.rs:1421 (existing precedent that DOES gate on `var_map.is_empty() && cursor.call_stack.is_empty()`), src/runtime.rs:2174-2187 (`subflow_vars` built from declared vars + inputs), src/runtime.rs:2211 (`cursor.var_map = subflow_vars`, empty for zero-var subflow), src/runtime.rs:1774 (dispatch read site), src/runtime.rs:3052 (parent_var_map restore on return).
**Description:** `var_map_for_cursor`'s guard at src/runtime.rs:1523 is `if cursor.var_map.is_empty() { checkpoint.var_map.clone() }` — it falls back to the global root scope whenever the cursor's map is empty, with no check of `cursor.call_stack`. ### R1-5 (#2). Collector barriers not scoped to subflow call instance (FINALIZED)
**Severity:** MEDIUM — lowered from HIGH. Mechanism confirmed and the dangerous construct ships in a template, but it isn't concurrently invoked as shipped; trigger (Split→same-subflow call, or recursion) is author-constructible. Silent corruption when hit. *(Line refs accurate post-refactor.)*
**Files:** src/runtime.rs:385 (run-global `collector_barriers` map), src/runtime.rs:3973 (entry key `{node.id}:{execution_epoch}` in `handle_collector_entry`), src/runtime.rs:4240 (terminal key in `handle_terminal_cursor_status`), src/runtime.rs:4025-4046 (release/parse-back), src/runtime.rs:156 (`CallFrameState`, no frame id), src/runtime.rs:819 (`execution_epoch` is restart counter, not call-instance id).
**Description:** Collector barriers live in one run-global map keyed `{node_id}:{execution_epoch}`. Inside a subflow the active graph is the subflow's own, so `node.id`/`collector_id` are workflow-local, and `execution_epoch` is a run-global restart counter shared by all concurrent cursors — so the key has no per-call-instance component. If the same collector-containing subflow runs in two concurrent cursors (a root-level Split fanning into multiple `call` nodes targeting it, or recursion), both compute the identical barrier key and share one `CollectorBarrierState`. Because arrivals are de-duped by `merge_key`, the second call's arrival is silently dropped under the first call's key, and the barrier releases early or with the wrong call's inputs — no error surfaces. The shipped `dual-review` subflow has such an internal barrier but is invoked by a single `call`, so it is latent.
**Fix:** Add a stable `frame_id` to `CallFrameState` (minted at call time, src/runtime.rs:2189) and build the barrier key as `{frame_id_or_root}:{node_id}:{epoch}` at both src/runtime.rs:3973 and :4240 (and the `collector_id` parse-back at :4046), sourcing it from `cursor.call_stack.last()` with a sentinel for the root (empty stack) case. Split children receive a clone of `call_stack` (src/runtime.rs:3894-3902), so the `frame_id` is correctly shared by sibling Split branches of one call yet distinct across separate concurrent calls — exactly the required scoping. Add a test with a Split fanning into two `call` nodes targeting one collector-containing subflow, asserting each barrier releases on its own call's arrivals.

### R1-6 (#3). Terminal ParallelBatch/collector/call exit drops parent call result (FINALIZED)
**Severity:** MEDIUM — lowered from HIGH. Real correctness gap but latent: no shipped template triggers it (the only subflow template, `dual-review`, has a `run_agent` exit). Reachable only via a user-authored subflow ending in batch/collector/call. *(Line numbers drifted; mechanism intact on HEAD.)*
**Files:** src/runtime.rs:3002 (`complete_subflow_if_at_exit`), src/runtime.rs:2900 + 3301 (correct call sites — task & approval nodes), src/runtime.rs:3599 (batch terminal cursor-removal, missing the call), src/runtime.rs:4123-4127 (collector-release, same gap), src/runtime.rs:2114 (`handle_subflow_node`, call-as-exit unhandled), src/runtime.rs:2240 (`resolve_subflow_exit_node`, no node-type restriction).
**Description:** When a ParallelBatch, collector, or call node is a subflow's exit and has no outgoing success edge, the runtime removes the cursor without popping the call frame, so the parent caller's `call` node never receives its result, `checkpoint.last_output` is never updated from the subflow, and the parent execution stalls with the subflow's output value lost. The contrast proves it: a regular task node at the same exit position hits src/runtime.rs:2900, pops the frame, and the parent receives output. `resolve_subflow_exit_node` accepts any terminal node, so a user-authored reusable subflow ending in a batch/collector/nested-call silently breaks the parent run.
**Fix:** Centralize at a single cursor-removal choke-point: replace the scattered terminal `checkpoint.active_cursors.remove(index)` calls with one helper `finish_cursor(checkpoint, index, node, result)` that first runs `complete_subflow_if_at_exit`, then removes the cursor only if the frame didn't consume it — so every terminal node type (batch, collector, call, and any future kind) routes through subflow-exit handling. Take care threading the correct `node`/`NodeResult` into the collector representative-cursor case. Add tests for a subflow whose exit is a batch and one whose exit is a collector, asserting the parent call receives the subflow output.

For each `Option<f64>` timing field on `WaitConfig` and `RunAgentConfig`, push an error if the value is not finite or is `< 0.0`. Extend `validates_wait_until_requires_marker` (src/model.rs:2533) with cases asserting an invalid regex and a negative/NaN timing value are rejected. (Optionally add `min="0"` to the UI inputs for defense in depth.)

Add a unit test asserting that `command: Some(vec![""])`, a `command` with a whitespace-only token, and `user: Some("")` are each rejected by validation.
