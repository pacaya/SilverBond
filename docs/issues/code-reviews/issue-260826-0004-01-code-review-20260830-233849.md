### M1. Pinning test cannot distinguish "defaulted to first edge" from "first edge's condition matched" (FIXED)
> **Fix:** Added a positive-control case to `unmatched_branch_conditions_route_to_first_branch_edge` — parsed `{"status": "match_second"}` now asserts routing to `edge_second`. Verified by mutation rather than by reading: the Claude reviewer patched `evaluate_condition` (`src/model.rs:3182`) to `return (true, None)` and the test failed at `src/runtime.rs:14532`; patched to `return (false, None)`, it failed at the same assertion. The test now goes red under both the always-match and never-match mutants, so the unmatched assertion is load-bearing. `src/model.rs` was restored and confirmed clean.

**Severity:** MEDIUM · **File:** `src/runtime.rs:14521` · **Source:** Claude (Codex cross-verify: AGREE)

The new regression test's unmatched case feeds parsed `{"status":"unmatched"}` against two edges whose conditions are `status == match_first` / `status == match_second`, and asserts the result is `edge_first`. But `edge_first` is *also* what the condition scan (`src/runtime.rs:6530-6539`) returns if `evaluate_condition` were broken and reported a match for everything. The test therefore stays green under a total failure of condition evaluation, and it is the only test this change adds to pin the routing it must not alter. Nothing in the test asserts that a *matching* non-first edge is actually selected, so the `edge_first` result is not load-bearing.

Codex confirmed independently: "`src/runtime.rs:6530-6539` would select `edge_first` if every condition incorrectly reported a match, still satisfying `src/runtime.rs:14521-14524`; a positive `edge_second` case is needed to distinguish fallback from broken matching."

This matters more than its severity suggests: acceptance criterion 4 exists precisely to pin behavior the change must not alter, and a characterization test that cannot go red under the failure it characterizes does not discharge that criterion.

**Fix:** Add a positive-control case to the same test: parsed `{"status": "match_second"}` must route to `edge_second`. That makes the unmatched case's `edge_first` result load-bearing.

### L2. Second half of the test passes a cursor id that belongs to a different checkpoint (FIXED)
> **Fix:** The test now re-reads `checkpoint.active_cursors[0].cursor_id` at `src/runtime.rs:14542`, immediately after rebuilding the checkpoint for the no-parsed-output case, so the id passed at `:14549-14556` belongs to the checkpoint passed alongside it. M1's positive-control case, inserted before it, still uses the first checkpoint together with the first checkpoint's cursor id, so the shadowing order is consistent throughout.

**Severity:** LOW · **File:** `src/runtime.rs:14549` · **Source:** Claude (Codex cross-verify: AGREE)

`cursor_id` is captured once from the first checkpoint (`src/runtime.rs:14490`), but `checkpoint` is rebuilt at `src/runtime.rs:14526-14527` for the no-parsed-output case. `build_initial_checkpoint` mints a fresh id via `new_cursor_id()` = `format!("cursor_{}", Uuid::now_v7())` (`src/runtime.rs:1913-1915`), so the id handed to the second `select_next_decision` call names no cursor in the checkpoint it is called with.

Harmless today — `select_next_decision` only stamps `cursor_id` into emitted event payloads (7 sites, all `.with("cursorId", …)`) — but it emits a `branch_decision` attributed to a nonexistent cursor, and the test would silently mis-exercise the function if it ever resolves the cursor.

**Fix:** Re-read `checkpoint.active_cursors[0].cursor_id` after rebuilding the checkpoint, or reuse the first checkpoint for both cases.
