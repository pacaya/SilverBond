### M4. The writer factory erases the compile-time kind→config-field guarantee the baseline writers had (FIXED)

> **Fix:** Round 4 closed it, after rounds 2 and 3 each closed one direction and missed another. Final shape: `defineConfigTarget<K, F, D extends KindConfigValue<K, F>>(kinds, configKey, defaults: Exact<D, KindConfigValue<K, F>>)` — the constraint supplies required-property and property-type checking, `Exact` supplies the excess-key check, and the two are complementary rather than substitutes. Ten `@ts-expect-error` fixture cases now pin all three axes (wrong field key, invalid kind, wrong defaults in the subset, superset and wrong-type directions), and each was confirmed to suppress a real diagnostic. Both reviewers VERIFIED_FIXED; Codex called the checked surface closed with no follow-up required.

**Severity:** MEDIUM · **File:** `ui/src/features/editor/mergeConfig.ts:92` · **Source:** Both (Claude
finding; Codex's `STILL_BROKEN` verdict on M3 is the same defect) · **Cluster:** M3 + M4, one defect

`makeConfigWriter<T extends object>(nodeId: string, kindTypes: readonly string[], configKey: string, defaults: T)`
relates none of `kindTypes`, `configKey` and `T` to each other or to the `NodeKind` union, and the body casts
the union away (`const kind = n.kind as Record<string, unknown>`, `:102-103`). At baseline the per-kind switch
was checked by TypeScript: narrowing on `n.kind.type === "capture"` pinned the field name to the kind and
inferred the config type, so a wrong key or mismatched default failed to compile. Now
`makeConfigWriter(node.id, ["capture"], "capureConfig", DEFAULT_KILL_CONFIG)` type-checks cleanly and would
silently write a phantom property onto the persisted node.

No current call site is wrong — all eight triples were verified against the baseline switch — so there is no
live defect. This is a type-safety regression relative to baseline, and the compiler was the only guard on the
five panels (`decide`, `parallel_batch`, `send`, `wait`, `subflow`) that have no direct test coverage.

**The mechanism to remove** (not the symptom): the kind→config-field→defaults association now exists in *two*
unchecked places — once in the accessor functions (`captureConfig()` knows capture → `captureConfig` →
`DEFAULT_CAPTURE_CONFIG`) and again as three loose string/value arguments at each panel's call site, with
nothing tying the second to the first or to the union. A round that only adds tests leaves that mechanism
standing.

**Fix:** Redesign so the association is stated once and derived from `NodeKind`, e.g.
`makeConfigWriter<K extends NodeKind["type"], F extends keyof Extract<NodeKind, {type: K}>>(nodeId, kinds: readonly K[], configKey: F, defaults: NonNullable<Extract<NodeKind, {type: K}>[F]>)`,
keeping a single unchecked cast inside the factory body. Required properties and the fixture corpus that
asserts them are in the round-2 brief.

**Round 2 outcome — redesign sound, one arm of P2 still open.** Round 2 replaced the loose triple with a
`defineConfigTarget` construct: each kind's discriminator(s), config field and defaults are bound once in an
exported target that accessors *and* panel writers consume, so no call site passes an unchecked string any
more. Both reviewers independently confirmed P1, P3, P4 and P5, and confirmed the compile-axis fixture is
genuinely in the typecheck graph (`tsconfig.json` includes `ui/src/**/*.ts`) with every `@ts-expect-error`
suppressing a real diagnostic. The mechanism this escalation targeted — the association restated as unchecked
strings — is gone.

P2 is met on its kind-name and config-field-key arms but **not** on its defaults arm. Both reviewers, probing
independently, compiled `defineConfigTarget(["kill"], "killConfig", DEFAULT_SPAWN_CONFIG)` and
`defineConfigTarget(["spawn"], "spawnConfig", DEFAULT_KILL_CONFIG)` with no error at all: `defaults` is checked
by ordinary *assignability*, and `SpawnConfig`/`KillConfig` are both all-optional weak types that overlap on
`sessionName`, so neither excess-property checking nor weak-type detection fires. Codex returned
`STILL_BROKEN` on that basis; Claude returned `VERIFIED_FIXED` while explicitly stating the verdict flips if
P2 is treated as an absolute bar. **Adjudicated: P2 was stated as absolute, so the cluster stays open into
round 3**, which closes this arm and extends the fixture to pin it. Round 3 is not a fresh patch of the same
symptom — the redesign stands; one constraint is being tightened from assignable to exact, with the two probe
lines added to the corpus so the hole cannot silently reopen.

Claude also verified a safety property beyond the brief: mixing unrelated kinds in one target
(`["capture","kill"]`) is rejected, because the shared config-field type collapses to `never`.

**Round 3 outcome — closed the named hole, opened a wider one on the same axis.** Round 3 replaced round 2's
`defaults: NoInfer<KindConfigValue<K, F>>` with `defaults: Exact<D, KindConfigValue<K, F>>` where
`type Exact<D, U> = Exclude<keyof D, keyof U> extends never ? D : never` and `D` was declared **bare**. That
closed the two mutually-assignable probe lines — both reviewers confirmed the new `@ts-expect-error` cases are
live and every prior case still red for its intended reason — but `Exclude<keyof D, keyof U>` forbids *extra*
keys while never requiring the *required* ones, and an unconstrained `D` is checked only against itself. So
the assignability check round 2 did have was removed: any subset-shaped object now compiles.

Both reviewers demonstrated this by compiling wrong triples on the current tree — Claude six
(`captureConfig` ← `{}`, `batchConfig` ← `{}`, `waitConfig` ← `{ target: "x" }` missing required `mode`,
`decideConfig` ← `{ outcomes: [] }` missing required `prompt`, `subflowConfig` ← `{ inputs: [] }`, and
`captureConfig` ← `{ all: "yes", ansi: false }`, a **wrong property type**), Codex four (`sendConfig` ← `{}`,
`sendConfig` ← `{ text: "" }`, `captureConfig` ← `{ all: false }`, `batchConfig` ← `{ maxConcurrent: 4 }`).
The hole is strictly larger than the one it replaced: round 2 admitted two weak-type pairs, round 3 admits
every subset including `{}`.

Both reviewers also answered the two questions raised about round 3's collateral. The cast added at
`mergeConfig.ts:61` (`defaults as KindConfigValue<K, F>`) is **not** union-erasing — it collapses the `Exact`
brand — so P2's one-cast budget is intact, `makeConfigWriter`'s remains the only union-erasing cast. But that
cast is load-bearing for this defect: it launders an incomplete `defaults` into `ConfigTarget.defaults`, from
where every accessor fallback and every `mergeConfig` seed carries it. Constraining the type parameter makes
it safe again. The stale suite measurement was also cleared — both reviewers re-ran the gates post-final-state
and got 124/124 vitest across 11 files, `InspectorPanel.test.ts` unmodified at 17/17, typecheck 0/0.

**Round 4 (final) remedy, validated rather than proposed:** constrain the type parameter —
`D extends KindConfigValue<K, F>` — keeping `Exact` for the extra-key direction, so both directions are
checked. Claude applied exactly this to a copy, ran `just typecheck`, and confirmed all four subset probes
error for the right reasons while all eight real targets and every existing fixture case stayed green, then
restored the file byte-identically (checksum verified). Codex independently named the equivalent two-sided
form. The fixture must gain the subset probes under `@ts-expect-error` — particularly the wrong-property-type
case, the only one that exercises property-type checking.

### L7. Accessors hand-index `kindTypes` while the writer iterates it, so the two can silently disagree (FIXED)

> **Fix:** Round 3 — extracted `matchesTarget(kind, target)` at `mergeConfig.ts:64-69`, a type predicate guarding with `target.kindTypes.some(...)`. All eight accessors and `makeConfigWriter` now use it, so the arity coupling is gone and a target listing a third kind would be honoured identically by reader and writer. Fallback semantics verified unchanged: `?? TARGET.defaults` retained on `spawn`/`send`/`wait`/`capture`/`kill`, absent on `decide`/`parallel_batch`/`subflow`, H9 intact. Both reviewers VERIFIED_FIXED.

**Severity:** LOW · **File:** `ui/src/features/editor/mergeConfig.ts:117` · **Source:** Claude (Codex did not
cover it)

`ConfigTarget.kindTypes` is typed `readonly K[]`, not a tuple, so nothing pins its arity. The single-kind
accessors test only `kindTypes[0]`, and `subflowConfig` tests `kindTypes[0] || kindTypes[1]`, whereas
`makeConfigWriter` guards with `target.kindTypes.some(...)` over the whole array. Add a third kind to any
target — the natural way a future `call`-like alias would be introduced, which is exactly what this construct
exists to make safe — and the writer accepts it while the accessor returns defaults: the panel would render
default values over a node that writes are landing on, so an edit appears to revert while silently persisting.

All targets are consistent today (single-kind targets index `[0]`; the subflow target has two kinds and
indexes both), so there is no live defect. It is also a small reintroduction of the "stated twice" shape P1
exists to remove — the accessor restates the target's arity.

**Fix:** Have the accessors reuse the writer's predicate — extract a shared
`matchesTarget(kind, target)` using `target.kindTypes.some(...)` and call it from both — or type `kindTypes`
as a tuple so the arity is pinned at the definition site.

### L8. Union-annotated defaults escape the exactness check (deferred)

**Severity:** LOW · **File:** `ui/src/features/editor/mergeConfig.ts:40` · **Source:** Claude

`Exact<D, U>` keys off `Exclude<keyof D, keyof U>`, and `keyof` over a union yields only the keys common to
all members. So a value *annotated* as `SpawnConfig | KillConfig` collapses to `keyof` = `"sessionName"`, the
excess-key gate passes, and the `D extends KindConfigValue<K, F>` constraint also passes because `KillConfig`
is assignable to `SpawnConfig`. Verified: `declare const unionDefaults: SpawnConfig | KillConfig;
defineConfigTarget(["spawn"], "spawnConfig", unionDefaults);` compiles with zero diagnostics. The same shape
where one member lacks the target's required properties is correctly rejected.

**Deferred, on the reviewer's own recommendation** (~10 confidence it is worth any work). It requires someone
to annotate a defaults constant as a union; no target does — all eight pass a constant declared with exactly
one config type — and `{spawn, kill}` is the only mutually-assignable pair in the schema, since they are the
only two all-optional configs. It is an inherent property of `keyof` over unions rather than a defect in the
fix, and the runtime consequence is the same nil-impact class as the closed findings, both defaults being
`{}`. Recorded so it is not rediscovered as new; a one-line comment on `Exact` noting that union-typed
defaults are outside its guarantee would be the cheapest response if anyone wants one.
