### H1. `cursor_cancelled` is falsely claimed to fire on every terminal cursor removal (FIXED)

> **Fix:** Split removal from emission: `handle_terminal_cursor_status` emits `cursor_cancelled` on the failure/timeout path only, and the three silent removal paths are named; event-table row at `:110` rescoped to match. Line 11 no longer contradicts line 47.

**Severity:** HIGH · **File:** `docs/execution-model.md:11`, `docs/execution-model.md:110` · **Source:** Both (CLAUDE-1, CODEX-2)

The lifecycle prose states that "`handle_terminal_cursor_status` or `finish_cursor` removes it from `active_cursors` and emits `cursor_cancelled` (the event fires for every terminal removal, not only failure-policy cancellation)". This is false in both halves.

The only production construction of `cursor_cancelled` is `src/runtime.rs:6318`, inside `handle_terminal_cursor_status`, and that function is only ever called with `CursorTerminalStatus::Failure` or `Timeout` (call sites `src/runtime.rs:4581`, `:4832`, `:5066`, `:5410` — never `Success`). `finish_cursor` (`src/runtime.rs:4900-4915`, called on the success paths at `:4657`, `:5040`, `:5444`, `:6213`) removes the cursor and emits nothing at all. `handle_skipped_task` removes silently (`src/runtime.rs:3372`), as does the non-representative-waiter deletion (`src/runtime.rs:6093-6098`) — which the document's own line 47 correctly calls "discarded silently", so line 11 contradicts line 47.

The claim was lifted verbatim from drift-audit D51 (`docs/sources/workflow-schema-drift-260825.md:521`), which is itself wrong — exactly the case the brief warned about when it required audit claims to be verified against source.

**Fix:** Rewrite line 11 so removal and emission are separate facts: `handle_terminal_cursor_status` removes the cursor and emits `cursor_cancelled` on the failure/timeout path only; `finish_cursor`, the skipped-node path and the non-representative-waiter deletion all remove the cursor with no event. ### M1. Pane ownership bookkeeping is misstated in both directions (FIXED)

> **Fix:** Rewrote both directions: `spawn` alone establishes owned-target membership via `register_owned_target`, control kinds only check it; pane kill's target-and-key clears distinguished from session kill's key-only clear, and owned-target membership recorded as having no removal path before Run-registry teardown.

**Severity:** MEDIUM · **File:** `docs/execution-model.md:65`, `docs/execution-model.md:67` · **Source:** Both (CLAUDE-2, CLAUDE-8, CODEX-5)

Two mutually reinforcing errors about the same security boundary, merged here as one defect.

Line 65's parenthetical — "(`resolve_pane_target`, `register_owned_tmux_target` on spawn and control nodes)" — implies control kinds register ownership. `ActivePaneRegistration::register_owned_target` is called at exactly two sites, both spawn paths (`src/tmux_exec.rs:448` in the task-node pane spawn, `:786` in `execute_spawn`). `send`, `wait` and `capture` never register ownership; they only read it through `owns_pane`/`owns_session` and then write the resolved target to the Active Pane Registry (`src/tmux_exec.rs:814`, `:848`, `:890`). Line 69 states the correct rule, so line 65 contradicts the document's own next paragraph.

Line 67 claims "`kill` clears both registry and ownership entries." It does not. `execute_kill`'s pane branch calls `clear_target` and `clear_key` (`src/tmux_exec.rs:955-958`) and its session branch calls `clear_key` alone (`src/tmux_exec.rs:935-945`); both helpers mutate `active_panes`, not `owned_tmux_targets` (`src/runtime.rs:1204-1218`). There is **no** removal path from `owned_tmux_targets` anywhere in `src/` — only the insert at `src/runtime.rs:1173` and the two membership reads at `:1186` and `:1198`. `CONTEXT.md:61`'s "`kill` clears both" means the two *registry* clears (it cites `tmux_exec.rs:957`), not registry plus ownership; the document misread it.

Together these misdescribe the lifetime of the ownership boundary — the one mechanism the document elsewhere correctly identifies as what refuses a pane node after a resume.

**Fix:** State that `spawn` alone establishes ownership and that control kinds only check that membership before updating the Active Pane Registry. State that pane kill clears the registry entry by node key and by resolved target, session kill clears its node key only, and owned-target membership has no removal path at all — it persists until the Run's registry entry is torn down.

### M2. The post-resume pane-context trace is stated but never completed (FIXED)

> **Fix:** Completed the trace with both outcomes: session continuation fails outright against an empty rebuilt registry, while the HTTP path recovers persisted checkpoint candidates after a registry miss, with `match_pane_candidate`'s current-node-else-last rule and `PaneUnavailable` only on total failure.

**Severity:** MEDIUM · **File:** `docs/execution-model.md:61` · **Source:** Codex (CODEX-1)

The brief made this an explicit acceptance criterion: cover session reuse and the HTTP pane-context endpoints "separately, since they degrade differently". The document says they "degrade differently" and then stops without stating either outcome, so the criterion is named but not discharged.

The two outcomes are materially different. `resolve_reused_pane` hard-fails when the rebuilt registry is empty (`src/tmux_exec.rs:1494-1512`, via `ActivePaneRegistration::resolve` at `:661-675`, which consults only `resolve_active_pane`). `resolve_run_pane_context` does not: after a registry miss it falls back to trusted candidates reconstructed from persisted checkpoint Node Results and Execution Log entries (`src/api.rs:1392-1416`, `src/runtime.rs:618-657`), and `match_pane_candidate` (`src/api.rs:2323-2349`) resolves `active`/`current` to the current-node candidate else the last candidate — **not** the "exactly one registered pane" rule the document states at `:61`, which is the registry rule and does not govern this fallback. `PaneUnavailable` is returned only when that fallback also misses.

**Fix:** State both outcomes separately — session continuation fails outright because its source is absent from the rebuilt registry; the HTTP pane-context path misses the registry but can still recover a persisted checkpoint candidate, and returns `PaneUnavailable` only if that recovery also fails. Give the fallback's own `active`/`current` selection rule rather than reusing the registry's.

### M3. The `anyhow` backstop is conflated with the panic path, mis-stating both (FIXED)

> **Fix:** Separated the two mechanisms: a returned `execute_workflow` error is failed and finalized by `fail_workflow_after_error`; a panic reaches only `spawn_supervised_run`, which clears the in-memory registry and can leave the persisted Run `running`.

**Severity:** MEDIUM · **File:** `docs/execution-model.md:77` · **Source:** Both (CLAUDE-5, CODEX-3)

The run-killers sentence names "the `anyhow` backstop when the supervised run task panics", which fuses two separate mechanisms with different blast radii and different persistence outcomes.

`fail_workflow_after_error` (`src/runtime.rs:3062-3113`) is invoked from `execute_workflow_to_terminal` (`src/runtime.rs:3034-3060`) only when `execute_workflow` *returns* `Err(anyhow::Error)`. It never runs on a panic. A panic (or cancellation) reaches the `JoinError` arm in `spawn_supervised_run` (`src/runtime.rs:3090-3131`), which only logs and clears the in-memory registry entry; its own warn string reads "run task exited before finalize_run; clearing registry entry (DB status may remain Running)". The panic path is therefore explicitly **not** a run-killer: it produces no terminal status and can leave the persisted Run at `running`.

Listing the panic among the run-killers hides a real operator-visible failure mode — a Run that is gone from memory but still reads `running` in the database.

**Fix:** Split into two statements. The `anyhow` backstop fails and finalizes the Run when `execute_workflow` returns an error. A panic in the supervised task is caught only by `spawn_supervised_run`, which clears the registry entry and leaves the persisted status `running`.

### M4. The three-way failure classification is wrong (FIXED)

> **Fix:** Replaced success/failure/timeout with aborted/timeout/failure, documenting that the aborted branch clears every cursor and ends the Run before any `CursorTerminalStatus` is chosen.

**Severity:** MEDIUM · **File:** `docs/execution-model.md:75` · **Source:** Claude (CLAUDE-4)

The document writes: "Failure is classified into three terminal outcomes for collectors: success, failure, and timeout (`CursorTerminalStatus`)." The actual three-way classification of a failed task result (`src/runtime.rs:4555-4589`) is **aborted / timeout / failure**. An abort — the registry abort flag, or `error_type == "aborted"` — short-circuits to `RuntimeStatus::Aborted` and clears every cursor before any `CursorTerminalStatus` is chosen; only after that branch is the remaining choice `Timeout` (exit code −2 or `error_type == "timeout"`) versus `Failure`.

The document's version lists `success`, which is not a failure classification at all, and drops `aborted`, which is the branch with by far the largest blast radius. Drift-audit D46 states it correctly, so this is a transcription error rather than a research gap.

**Fix:** Rewrite as: a failed task result is classified three ways at `src/runtime.rs:4555` — aborted (short-circuits the whole Run to `aborted` and clears every cursor), timeout, or failure; only the latter two become a `CursorTerminalStatus` on a barrier arrival.

## Round-2 escalation — same-site cluster, redesigned rather than patched

**Cluster: L7 + L8.** Both surfaced on the round-1 re-verify, and both land on the region the round-1 fix had just edited — L8 on `:67`, a line M1 rewrote, and L7 ten lines from L5's edit at `:11`. That is the same-site trigger: the patch and the finding are the same text disagreeing with itself. They are recorded here as one defect, not two.

**Shared root cause — the mechanism.** The document states the same mechanism in two sections and lets the copies drift. Two instances:

- the dispatch predicate is stated at `:11` and restated in shorthand at `:21`;
- pane-registry resolution and the HTTP pane-context path are described in §Checkpoint/resume (`:61`) *and* re-derived in §Pane kinds (`:67`).

This is not a fresh observation. Both reviewers' Step-A smell scan already flagged the second instance independently — "Divergent Change: the resume section closes with a pane-registry/ownership paragraph that re-derives most of §Pane kinds, so a change to pane mechanics forces edits in two sections". Round 1 then demonstrated the cost: correcting one copy of each fact left the other stale, generating L7 and L8 as a direct by-product of the fixes.

**Why redesign rather than a third one-clause patch.** Editing `:21` and `:67` in place would close L7 and L8 while leaving the duplication that produced them, so the next correction to either mechanism regenerates the same class of finding. The round-2 brief therefore requires the mechanism removed: **every mechanism gets exactly one owning site, and any other section that needs it cross-references rather than restates.** A fix that closes L7 and L8 by editing the two clauses while leaving both facts stated twice is rejected on judging even though the named findings are gone.

**Checkable properties the redesign must satisfy** (stated so that "is the mechanism gone?" is answerable by reading, not by taking the fixer's word):

1. The dispatch predicate — `Runnable` and not cancel-requested — is stated in exactly one place. Every other mention refers to it ("the dispatch filter above", "dispatchable") without restating a filter of its own.
2. The Active Pane Registry's resolution rule — registered keys, the `active`/`current` alias, node-id prefix matching by highest sequence — is stated in exactly one place.
3. The HTTP pane-context path's behavior, including its own distinct `active`/`current` rule, is stated in exactly one place.
4. The post-resume consequence for pane nodes (the ownership gate refusing a `send`/`capture`) stays where the acceptance criterion put it, in the resume section, and names the mechanism rather than re-deriving it.
5. No claim in this file's `## Verified Clean` section is weakened or deleted, and none of the fourteen round-1 fixes is reverted.
6. The document is still prose about mechanism — the deduplication must not turn either section into a list of pointers.

Round 2 counts against the cap of 4. Rounds used after it: 2.
