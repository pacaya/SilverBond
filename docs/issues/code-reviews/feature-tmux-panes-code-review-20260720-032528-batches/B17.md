#### Issue L7: Password entered through an unmasked `window.prompt`
**Severity:** LOW
**File(s):** `ui/src/app/AppShell.svelte:193`, `:194`, `:469`; `ui/src/features/editor/InspectorPanel.svelte:195`; `ui/src/lib/components/ConfirmDialog.svelte` (pattern to copy); `ui/src/lib/api/client.ts:80-101`; `ui/src/features/editor/InspectorPanel.test.ts:117-151`; `src/api.rs:636`, `:714`, `:759-796`; `src/app.rs:69-86`, `:100-104`, `:105-116`, `:128-170`
**Description:** Severity rationale: LOW — real cleartext exposure, but the secret is an app-local unlock token rather than a system credential, it is correctly transported and never persisted client-side, and the backend gate is throttled and fails closed.

The privileged-run unlock secret is collected with `window.prompt("Unlock password")` at `ui/src/app/AppShell.svelte:193` and `ui/src/features/editor/InspectorPanel.svelte:195`, rendering it in cleartext on screen and in some browsers' prompt autofill history. Everything downstream is already correct: the value is a function-local `const` passed to `api.createRun` / `api.testNode` (`ui/src/lib/api/client.ts:80-101`), serialized into a **POST JSON body** rather than a URL query string, read at `src/api.rs:636`, `:714`, never written to `localStorage`/`sessionStorage` (neither appears anywhere in `ui/src`), never held in `$state` or a store, never logged, and re-prompted on every privileged action. Secondary defect not in the original write-up: `prompt()` is suppressible by the browser's "prevent this page from creating additional dialogs" control, after which it returns `null` and every subsequent unlock silently becomes "Run cancelled" (`AppShell.svelte:194`) with no recovery path.

*Scoping — what the credential actually is:* an operator-chosen, **app-local** token compared against `SILVERBOND_UNLOCK_PASSWORD_HASH` (a `sha256:<64-hex>` value read only from the server process env, `src/app.rs:69-86`, `:105-116`) via constant-time compare behind global exponential throttling (`:128-170`). It is never a sudo or system credential and is never forwarded to sudo — the threat-model comment at `src/app.rs:100-104` records that contained launches use `sudo -u <user> -H --` without `-E`. No system-credential severity multiplier applies. Unlocking permits a `run_as`/process-spawning workflow to proceed under the operator's own uid instead of being 403'd (`src/api.rs:759-796`).

*Not to be conflated:* the third `prompt(` in `ui/src` is `GraphEditor.svelte:232`, the compound-node name prompt belonging to M1 — not a password, and out of scope here.

*Prior history:* `docs/issues/feature-tmux-panes-code-review-20260716-003531.md:165` cites `AppShell.svelte:193` only as evidence the secret is operator-chosen (low entropy), and its M6 explicitly **rejected** entropy enforcement as unenforceable. Masking was never raised.
**Recommended Fix:** Replace both `window.prompt` calls with a reusable masked dialog modeled on the repo's one established dialog pattern.
- Add `ui/src/lib/components/PasswordDialog.svelte` mirroring `ConfirmDialog.svelte`: a native `<dialog>` driven by `showModal()` from an `open` prop inside a `$effect`, `onsubmit`/`oncancel` callback props, `::backdrop` styling, and Escape handling.
- Expose `<input type="password" autocomplete="current-password">` and resolve a promise on submit or cancel, so both call sites can `await` it in place of `window.prompt`. A small deferred-resolver helper is needed to bridge the declarative modal into the existing imperative flow.
- Update `ui/src/app/AppShell.svelte:193` and `ui/src/features/editor/InspectorPanel.svelte:195` to use it; a shared component is warranted because both sites need identical UX.
- Rewrite `ui/src/features/editor/InspectorPanel.test.ts:117-151`, which currently does `vi.spyOn(window, "prompt")` and asserts `toHaveBeenCalledWith("Unlock password")`. No Playwright change is required — e2e never drives this prompt (`ui/e2e/run-agent-pane-stream.spec.ts:28`, `:37` POST `unlockSecret` directly and no spec registers a `page.on("dialog")` handler).
- Add vitest coverage for the new component, including that the input is `type="password"` and that cancel resolves without submitting.
- Note this also removes the dialog-suppression dead end: unlock currently becomes permanently impossible in a tab where the user has blocked additional dialogs, and today that path has zero e2e coverage.
