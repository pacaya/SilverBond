#### Issue M18: `runAs.socket` is unvalidated and the agent-user case is excluded from the privileged-run gate
**Severity:** MEDIUM
**File(s):** `src/tmux_exec.rs:89-92` (socket passthrough), `:1200` (`list_silverbond_tmux_sessions` prefix filter), `:1209-1222` (`cleanup_panes`), `:2482-2506` (`stable_session_name`/`normalized_session_name`), `:2508-2521` (`sanitize_tmux_name`), `:2979-2988` (socket tests); `src/model.rs:220-224` (`RunAsConfig`), `:874`, `:1875-1919` (`validate_run_as_config`); `src/api.rs:767-784` (unlock), `:831-846` (`resolved_run_as_is_privileged`); `src/runtime.rs:6449-6460` (reaper reconstruction), `:6505-6519`; `ui/src/features/editor/InspectorPanel.svelte:69-91`, `InspectorPanel.test.ts:281-302`; `docs/workflow-schema.md:67-97`
**Description:** Severity rationale: MEDIUM (lower edge) — author-controlled, ungated, and defeats a deliberate isolation boundary, but kills stay `silverbond-`-name-scoped, so it degrades isolation and leaks sessions rather than destroying arbitrary user panes.

`build_tmux_invocation_without_resolving` does `run_as.socket.clone().unwrap_or_else(|| format!("silverbond-{run_id}"))` (`src/tmux_exec.rs:89-92`), passing the author's string verbatim to `tmux -L <socket>`; neither `validate_run_as_config` (`src/model.rs:1875-1919`) nor `resolved_run_as_is_privileged` (`src/api.rs:831-846`) inspects `socket`, and `runAs.user == SILVERBOND_AGENT_USER` requires no unlock (`src/api.rs:767-784`). `socket` is not operator-only — it is a documented schema field (`docs/workflow-schema.md:67-97`) editable in the UI inspector (`ui/src/features/editor/InspectorPanel.svelte:69-91`), so any saved workflow can opt out of per-run socket isolation with zero friction. Consequences: SilverBond panes land on a live interactive tmux server and are cleaned up there; `kill-session -t` uses tmux prefix/fnmatch target matching, so deterministic continuation names from `stable_session_name` (`:2482-2506`, e.g. `silverbond-Reviewer-A`) collide across runs and users sharing a socket; and the per-run-socket isolation boundary is silently defeated.

*Corrections to the original write-up:* tmux-tools emits `-L`, not `-S`, so the socket is a label under the per-uid socket dir and tmux itself rejects `/` — there is no path escape. "Killing the user's own panes" does **not** follow: every kill is `silverbond-`-name-scoped (`src/tmux_exec.rs:1200`, `:2491-2506`), the boot reaper additionally requires a DB-registered terminal session (`src/runtime.rs:6505-6519`), `cleanup_panes` only kills targets from SilverBond's own registry, and tmux never reuses pane ids within a server, so a stale `kill-pane` is a no-op.

*Governing precedent:* `20260620` M12 (FIXED) chose per-run sockets **as** the isolation boundary and M10 (FIXED) requires kills to stay invocation-scoped; both are re-ratified at `docs/issues/feature-tmux-panes-code-review-20260716-003531.md:191`, `:266`. No prior finding rules on socket validation or on what the privileged gate is meant to cover.
**Recommended Fix:** Remove `runAs.socket` from the schema so the socket is always `silverbond-<run_id>` — eliminating the defect class rather than constraining it, and aligning the code with the M12 ruling that the socket is the per-run isolation boundary and therefore not the author's to choose.
- Delete the `socket` field from `RunAsConfig` (`src/model.rs:220-224`) and drop the override branch at `src/tmux_exec.rs:89-92`, leaving the `silverbond-{run_id}` construction unconditional.
- Remove the socket control from the UI inspector (`ui/src/features/editor/InspectorPanel.svelte:69-91`) and its assertions at `InspectorPanel.test.ts:281-302`.
- Remove the field from `docs/workflow-schema.md:67-97`.
- Migrate saved workflows carrying `runAs.socket`: accept and discard the field on deserialize (e.g. `#[serde(default)]` on a deprecated alias, or drop it in `normalize`) so existing documents load rather than erroring, and confirm the reaper's reconstruction path (`src/runtime.rs:6449-6460`) still derives the same socket name for in-flight runs.
- Update the socket tests at `src/tmux_exec.rs:2979-2988`, and add a regression asserting a workflow document containing `runAs.socket` loads successfully and still runs on `silverbond-<run_id>`.
- Accept the tradeoff: this removes the operator escape hatch for attaching to a pre-provisioned tmux server. If that need resurfaces, it should return as an explicitly privileged, gate-tripping field rather than an ungated one.

#### Issue L5: Prompt/argv exposure — re-scoped to dead env plumbing and world-readable database
**Severity:** LOW
**File(s):** `src/tmux_exec.rs:2106-2109` (dead `-e` loop), `:2073`, `:2299-2301` (`send_text`), `:3140` (`--` regression test); `src/driver.rs:517` (`CommandArgs.env`), `:698-700`, `:857-859`, `:985-987` (all four `env: Vec::new()` sites), `:665-667` (`--append-system-prompt`); `src/storage.rs:99` (`SqliteConnectionManager::file`), `:133` (`state_json`), `:134` (`workflow_json`), `:143` (`event_json`); `src/model.rs:801` (`Node.prompt`)
**Description:** Severity rationale: LOW — the finding as filed is dismissible (dead env code plus a millisecond argv window), but the investigation surfaced a real permanent leak in the same data: the SQLite database holding every prompt is created with default permissions.

Both cited mechanisms are real — `send_text` passes prompt text as an argv element (`src/tmux_exec.rs:2299-2301`) and `spawn_pane` appends `-e KEY=VALUE` pairs to the `tmux new-session` argv (`:2106-2109`) — but neither is meaningfully exploitable. `CommandArgs.env` is constructed at exactly four sites (`src/driver.rs:698-700`, `:857-859`, `:985-987`, `src/tmux_exec.rs:2073`) and **every one hardcodes `env: Vec::new()`**, so the `-e` loop is provably dead code iterating an always-empty vector. The prompt window is single-digit milliseconds (the tmux client is short-lived), while the agent's own argv — including `--append-system-prompt <text>` at `src/driver.rs:665-667` — is `ps`-visible for the agent's entire multi-minute lifetime and is untouched by the proposed fix. The genuine leak is elsewhere and permanent: `Node.prompt` (`src/model.rs:801`) is stored verbatim in `workflow_json` (`src/storage.rs:134`) alongside interpolated `state_json` (`:133`) and `event_json` (`:143`), and the database is opened via `SqliteConnectionManager::file` (`:99`) with **no `set_permissions` call anywhere in `src/`** — default umask, typically world-readable 0644. The same local adversary can therefore `cat` the prompts off disk indefinitely.

*Correction to the original write-up:* "`CommandArgs.env` is explicitly designed to carry environment values" is true of the type but false of the system — nothing populates it on any path, so the env half is not "no secrets yet" but no values at all.

*Fix viability note:* the reviewer's `load-buffer -` / `paste-buffer` route is not currently available. The pinned `tmux-tools` rev has no stdin plumbing (`core/src/tmux.rs:191-196` pipes only stdout/stderr and inherits stdin), so it would require an upstream change as H6 does. `paste-buffer` is also not equivalent to `send-keys -l`: it needs `-p`/`-d` handling, interacts with the target TUI's bracketed-paste mode (agents treat pasted and typed input differently), and buffer names collide across concurrent panes unless `-b`-namespaced. The `--` guard at `:2300` is deliberate and regression-tested at `:3140`.

*Prior history:* never previously raised — argv/`ps`/secrets-in-process-arguments appears nowhere in `docs/issues/`. `send_text` was reviewed twice (`code-review-20260608_part_*`) on Enter semantics only. Roughly ten prior severity rationales lean on "single-user loopback desktop" as a bounding factor.
**Recommended Fix:** Remove the dead mechanism, close the real leak, and record the argv window as accepted risk.
- Delete the `-e` loop at `src/tmux_exec.rs:2106-2109` and the `env` field at `src/driver.rs:517` together with its four `Vec::new()` initializers. It exists only to someday leak; removing it now is zero-risk.
- Set the SQLite file mode to `0o600` after creation at `src/storage.rs:99`, so prompts, interpolated state, and event payloads are not world-readable. Handle the non-Unix path with `#[cfg(unix)]` rather than failing the build.
- Verify the mode applies to the WAL and shared-memory sidecars (`-wal`, `-shm`) as well, not just the main database file — they carry the same content.
- Do **not** pursue the `load-buffer`/`paste-buffer` rewrite: it buys milliseconds against an adversary who can read the same prompts off disk permanently, requires a coordinated upstream change, and risks bracketed-paste regressions on the highest-traffic input path.
- Record explicitly that millisecond argv exposure of prompts is accepted risk for a loopback single-user desktop application, so a future review does not re-litigate it.
- Add a regression asserting the created database file is not group- or world-readable.
