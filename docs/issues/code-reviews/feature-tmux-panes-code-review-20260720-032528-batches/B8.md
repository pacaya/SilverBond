#### Issue M7: `run_decide_node` discards the agent's failure/timeout/abort status
**Severity:** MEDIUM
**File(s):** `src/runtime.rs:3843`, `:3860-3877`, `:4081-4112` (`select_decide_outcome`), `:4189-4195`, `:4221`, `:4237-4245`, `:4251` (`apply_join_result`), `:5886`; `src/tmux_exec.rs:1101-1116` (interactive timeout), `:1104` (`-1` sentinel), `:1138-1144`, `:2452-2469` (`aborted_result`), `:763`, `:1055`, `:2437` (`-2` sentinel sites)
**Description:** Severity rationale: MEDIUM (upper band) — a timed-out Decide can silently route down a real branch on a truncated answer, the same silent-wrong-answer class as the already-fixed R1-2/F9 pair; metadata reset additionally destroys telemetry on every decide, including successful ones.

`run_decide_node` discards the entire agent `NodeResult` except `output` (`src/runtime.rs:3843`) and reconstructs a fresh one at `:3860-3877` with `..Default::default()`. The interactive-poll timeout path builds `failed_result("Timeout waiting for agent response", -1, …)` and then sets `result.output = response.output` — the **partial capture** — plus `error_type = "timeout"` (`src/tmux_exec.rs:1101-1116`). That partial capture flows straight into `select_decide_outcome`, whose word-boundary regex matching (`:4081-4112`) can succeed on it, yielding `success = true` and `exit_code = 0` (`:3861-3864`). The user therefore sees one of two wrong outcomes: the run routes down a real branch as if the agent had answered — no error, no timeout event — or outcome selection fails and the node reports the misleading `"LLM response did not match any decide outcome: …"` classified as `Failure`, so `on_timeout` collector/split semantics (`:5886`) receive the wrong status. `aborted_result` (`src/tmux_exec.rs:2452-2469`) likewise carries a partial capture, so a matching abort capture can advance the run one node past the abort before the loop's next `is_aborted` check.

*Two defects the original write-up missed:* (1) the `..Default::default()` reconstruction resets `metadata` on **every** decide, including successful ones, losing `agent_session_id` and all cost/token telemetry that `node_done` events (`:4189-4195`) and `NodeExecutionLog.metadata` (`:4221`) depend on; (2) the interactive timeout sentinel is **`-1`** (`src/tmux_exec.rs:1104`), not `-2` — `-2` appears only at `:763`, `:1055`, `:2437` — so even a perfect pass-through of the agent result would still map to `Failure` rather than `Timeout`. Any fix must normalize the sentinel or key off `metadata.error_type`.

*Scope corrections:* the abort half is **already covered** — `apply_join_result:4237-4245` consults `ctx.registry.is_aborted(run_id)` before `metadata.error_type`, which is why `decide_abort_returns_promptly_and_kills_pane` (`:9922`) passes for reasons independent of this finding. And the reviewer's early-return concern is unfounded in the other direction: there is no path where the oneshot reports `success: false` while legitimately carrying a complete answer, since normal completion always returns `success: true, exit_code: 0` (`src/tmux_exec.rs:1138-1144`) and the pane kill happens after capture.

*Coupling:* **M7 and M8 must be fixed as a single change.** Today `run_tmux_oneshot` passes `timeout_secs: None`, so the timeout path is largely dormant for Decide; M8 makes it reachable, and fixing M8 alone strictly increases this finding's blast radius.

*Prior history:* no prior finding covers status/metadata discard. Adjacent fixes: `code-review-20260608_part_1_of_4.md:66` R1-2 (FIXED, decide substring misrouting → word-boundary + tie→`None`), `..._part_2_of_4.md:75` F9 (FIXED, prompt echo → `PromptCaptureMarkers`, consistent with this review's adjudication note), `feature-tmux-panes-code-review-20260620-092605.md:218` M17 (FIXED, decide abort latency → the `select!`/abort-token plumbing at `:3819-3841`), `...20260716-003531.md:277` L4. Open sibling in this review: L9.
**Recommended Fix:** Carry the agent's `NodeResult` forward and overlay only the outcome, rather than rebuilding it.
- Keep `result` as the base instead of constructing a fresh `NodeResult` at `src/runtime.rs:3860-3877`. On `!result.success`, return it with `resolved_prompt` and `parsed_output` filled in so the UI still shows the captured text.
- On success, mutate `output`/`stderr`/`success`/`exit_code` from `select_decide_outcome` while preserving `metadata`, `raw_output`, and the cost/token fields — this ends the telemetry loss on the success path.
- Normalize the timeout sentinel: either change `src/tmux_exec.rs:1104` from `-1` to `-2`, or make `apply_join_result` (`:4251`) test `metadata.error_type == "timeout"` rather than the numeric sentinel. Without this, `CursorTerminalStatus::Timeout` remains unreachable for Decide no matter how the result is propagated. If changing the sentinel, audit the three other `-2` sites (`src/tmux_exec.rs:763`, `:1055`, `:2437`) for consistency.
- Land this together with **M8** in one change.
- Add regressions for: a decide timeout whose partial capture *does* match an outcome (must not route down that branch), a decide timeout that reaches `CursorTerminalStatus::Timeout`, and a successful decide that retains `agent_session_id` and cost metadata.

#### Issue M8: Decide nodes ignore their configured timeout entirely
**Severity:** MEDIUM
**File(s):** `src/runtime.rs:3810` (decide call site), `:1748` (preview call site), `:6971`, `:7004` (orchestrator call sites), `:2110-2128` (`timeout_for_node`, Decide arm at `:2120`), contrast `:3658`/`:3706` (`run_agent_node` pattern); `src/tmux_exec.rs:1167-1174` (signature), `:1180`, `:948-951` (300 s default); `ui/src/features/editor/InspectorPanel.svelte:972`, `:978-987`
**Description:** Severity rationale: MEDIUM — loss of the configured deadline with silent fallback to a much longer generic cap, compounded by a UI that renders the setting as if it worked.

`run_decide_node` never computes `timeout_for_node(&node)` before calling `run_tmux_oneshot` at `src/runtime.rs:3810`, and `run_tmux_oneshot` has no timeout parameter to receive one — its signature (`src/tmux_exec.rs:1167-1174`) omits it entirely and it forwards a literal `None` as `run_agent_interactive`'s 4th argument at `:1180`. `node.timeout` is therefore parsed and validated for `NodeKind::Decide` (`timeout_for_node`'s catch-all arm, `src/runtime.rs:2120`) but never consumed, so every Decide node silently falls back to the generic 300 s cap in `run_agent_interactive` (`src/tmux_exec.rs:948-951`) regardless of what the author configured.

*User-visible broken promise not noted in the original write-up:* `InspectorPanel.svelte:978-987` renders the generic "Timeout" input bound to `selectedNode.timeout` inside the "Guards & retry" section (`:972`), and that section is **not** gated by node kind — so an author can add it to a Decide node, set a timeout, and observe no effect whatsoever.

*Scope corrections:* the original fix text ("compute `timeout_for_node` in `run_decide_node` and pass it into `run_tmux_oneshot`") is under-specified, since there is no parameter to pass it into. The preview call site (`src/runtime.rs:1748`) has a real `node` in scope and ignores its timeout for the same reason — the same defect, unreported. The two orchestrator call sites (`:6971` `run_orchestrator_refinement`, `:7004` `run_orchestrator_branch`) are meta-calls that rewrite a prompt or choose a branch rather than executing the node's own agent run, and both already pass `config: None`, so `None` is correct for them. The cross-reference to M3 does not hold — M3 was dismissed as factually unfounded; this is an independent missing-parameter defect. No prior review deliberately omitted decide's timeout, and no test asserts decide timeout behaviour.

*Coupling:* **land as one change with M7.** M8 makes the timeout path reachable for Decide; without M7 the newly-firing timeout is laundered into a wrong branch or a bogus outcome-selection failure.
**Recommended Fix:** Thread an explicit timeout through the oneshot seam and honour it wherever a node's own agent run is being executed.
- Add `timeout_secs: Option<u64>` to `run_tmux_oneshot`'s signature (`src/tmux_exec.rs:1167`) and forward it at `:1180` in place of the literal `None`.
- Pass `timeout_for_node(&node)` from the decide site (`src/runtime.rs:3810`) and from the preview site (`:1748`).
- Pass explicit `None` from the two orchestrator sites (`:6971`, `:7004`).
- Add **no** new default: rely on `run_agent_interactive`'s existing 300 s fallback (`src/tmux_exec.rs:951`), exactly mirroring `run_agent_node`'s `Option<u64>` pass-through at `src/runtime.rs:3658`/`:3706`. Introducing a decide-specific default would create a second fallback location diverging from every other node type.
- Implementation note: at the decide site the timeout must be captured by value alongside the cloned `agent_config`, since `node` is moved into the `spawn_blocking` closure — compute it before the closure.
- Add the missing regression: a Decide node with a short configured `timeout` must time out at that deadline rather than at 300 s.

#### Issue L9: Non-string decide outcome fails with an imprecise diagnostic
**Severity:** LOW
**File(s):** `src/runtime.rs:4056-4113` (`select_decide_outcome`), `:4061-4069` (structured branch), `:4063` (`as_str()?`), `:4064-4067` (exact match + `return`), `:4071-4079` (trimmed exact), `:4081-4112` (regex scan), `:4026-4041` (`decide_output_schema`), `:4007-4010` (prompt instruction), `:4043-4054` (`parse_decide_structured_response`), `:6741-6761` (`parse_structured_output`), `:3847-3858` (`run_decide_node` failure mapping), `:3860-3877` (block M7 rewrites), `:4237-4266` (`apply_join_result`), `:12166-12177` (pinning test)
**Description:** Severity rationale: LOW — *lowered*: the "abandoned fallbacks" premise is refuted, no behavior differs from the already-correct non-matching-string path, and what remains is a diagnostics polish item. ID retained as `L9` for stability.

When a structured `outcome` field is a non-string, `as_str()?` at `src/runtime.rs:4063` returns `None` from the whole function. This is **behaviorally identical** to the string path: a string `outcome` that matches no label also returns `None` at `:4064-4067` without reaching stages 2–3. The consequence is a clean, correctly classified failure — `run_decide_node` (`:3847-3858`) maps `None` to `success=false`, `exit_code=1`, `stderr = "LLM response did not match any decide outcome: {labels}"`, and `apply_join_result` (`:4237-4266`) routes it to `CursorTerminalStatus::Failure`. The only real defect is diagnostic: the operator cannot tell that the agent emitted the wrong *type* rather than an unrecognized label.

*Correction to the original write-up — the central premise is false.* The fallbacks would recover nothing legitimate for a non-string, and skipping them is deliberate, tested behavior. `decide_routing_invalid_json_artifact_outcome_does_not_fall_back_to_prose` (`src/runtime.rs:12166-12177`) requires `{"outcome":"maybe","reason":"approve"}` to return `None` precisely so the prose scan cannot harvest a label from the `reason` field. Since stage 3 regexes over the raw JSON text, falling through would make `{"outcome": 1, "reason": "I would approve"}` route to `approve` — reintroducing the silent-misroute class fixed by R1-2 (`docs/issues/code-review-20260608_part_1_of_4.md:66`) and F9 (`...part_2_of_4.md:75`). **The reviewer's "fall through instead of returning" variant is a regression and must not be taken.**

*Reachability:* `outcome_value` comes from LLM text via `parse_decide_structured_response` (`:4043-4054`) → `parse_structured_output` (`:6741-6761`), a bare `serde_json::from_str` with no schema enforcement; `decide_output_schema` (`:4026-4041`) and the prompt instruction (`:4007-4010`) are prompt-only advice. So `{"outcome": true}` is possible but rare, and coercion rarely helps — `true` → `"true"` matches no realistic label (`yes`/`no`/`approve`). The one genuine case is a scalar `{"outcome": 1}` against a label literally named `"1"`.

*Prior decisions:* no prior review covers outcome type coercion; R1-2, F9, and the `:12166` test all push toward strictness.
**Recommended Fix:** Keep the strict contract, make the failure legible, and fold the change into M7 rather than landing it separately.
- Have the structured branch report *why* it failed instead of collapsing to a bare `None` — change the return type from `Option<String>` to a small result-ish enum distinguishing "no structured outcome", "outcome was not a string", and "outcome matched no label".
- Use that at `src/runtime.rs:3853` so the stderr reads e.g. `"decide agent emitted a non-string outcome (got number); expected one of: …"` rather than the current generic message.
- Fold in scalar coercion at `:4063`: map `String`/`Number`/`Bool` to their text form before exact-matching, so a legitimately numeric label still resolves. Keep arrays and objects non-matching.
- Preserve the no-prose-fallback contract exactly — the structured branch must still `return` rather than fall through, and `:12166-12177` must continue to pass unchanged.
- **Sequence with M7:** M7 rebuilds `run_decide_node`'s result construction at `:3860-3877` and already names L9 as its open sibling. The improved stderr lands in the same `:3847-3858` block, so implement both together to avoid two edits to one path.
- Update the ~20 test call sites the return-type change touches, and add cases for a numeric outcome matching a `"1"` label, a boolean outcome (fails with the type-specific message), and an object outcome (fails, no prose fallback).
