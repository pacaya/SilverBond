#### Issue H2: Session registration lifecycle ignores its own success/failure signals
**Severity:** HIGH
**File(s):** `src/tmux_exec.rs:1205-1207` (`kill_tmux_session`), `:1209-1222` (`cleanup_panes`), `:517` (dropped register result); `src/storage.rs:464-473` (`register_tmux_session`), `:479-506` (`remove_tmux_sessions`), `:525` (`list_reapable_tmux_sessions`); `src/runtime.rs:6352-6371`, `:6374-6381`, `:6479`, `:6507-6510`, `:6517-6538`
**Description:** Severity rationale: an unkilled session plus its agent process leaks permanently and silently, unrecoverable by any later reaper pass; the same path carries `run_as` panes running as another user.

`kill_tmux_session` is `tmux::run(&["kill-session", "-t", name]).is_ok()`, and in the pinned `tmux-tools-core` rev `69173d1` `run_with` returns `Ok(TmuxOutput { … exit_code })` with no status check — only `run_checked` routes through `check()`. A kill *rejected* by tmux therefore reports success. The reaper treats that `Ok(true)` as confirmation and calls `remove_tmux_sessions` (`src/runtime.rs:6517-6537`), deleting the only record that makes the session reapable; because the reaper attempts kills only on sessions it just confirmed live (`:6479`, `:6507-6510`), a nonzero exit there is almost certainly a genuine failure, so the delete is wrong in exactly the reachable case. `cleanup_panes` discards every result with `let _ =` while its caller computes `killed_sessions` from the target list *before* the kills run (`:6352-6355`), and `register_tmux_session`'s `false` return (runs row absent) is dropped at both `src/runtime.rs:6374-6381` and `src/tmux_exec.rs:517`. Net: a live tmux session survives permanently, invisible to boot reaping and to the run-observability surface, with zero diagnostics.

*Correction to the original write-up:* the `Ok(false)` warn arm at `src/runtime.rs:6538` is **not** dead code — `run` still returns `Err` on spawn failure and on the 5 s command timeout. It is unreachable only for tmux-level rejection.
**Recommended Fix:** Determine kill success by observing tmux state rather than trusting the kill's own result.
- After issuing the kill, probe `has-session -t <name>`; treat a nonzero exit as "session gone". Ignore the kill command's exit status entirely.
- Delete the DB registration only when the session is confirmed absent. Otherwise retain the registration and `warn!` with `run_id` and `session_name` so a later reaper pass can reconcile it.
- Change `cleanup_panes` to return per-target absent/present verdicts instead of `let _ =`, and compute `killed_sessions` (`src/runtime.rs:6352-6355`) from those verdicts rather than from the target list.
- Propagate `register_tmux_session`'s `bool` at `src/runtime.rs:6374-6381` and `src/tmux_exec.rs:517`, and `warn!` on `false` — a false there means the pane is unreapable from birth.
- Add reaper and terminal-cleanup regressions using tmux fakes that exit **nonzero**; the existing fakes at `src/tmux_exec.rs:3761` and `src/runtime.rs:8534` are `exit 0` scripts and cannot catch this.

#### Issue M4: Stale session registrations accumulate and can target a newer run
**Severity:** MEDIUM
**File(s):** `src/tmux_exec.rs:450-463` (`PaneGuard::drop`), `:550-556` (`clear_key`/`block_on`), `:678-681` (spawn node), `:2083-2087`, `:2482-2506` (`stable_session_name`); `src/runtime.rs:1155-1159`, `:1592` (`dismiss_run`), `:6344-6355`, `:6371`, `:6383-6389`, `:6418`, `:6507-6510`, `:6517`, `:6523-6537`, `:6554-6569` (`kill_active_run_panes`); `src/storage.rs:547-561` (`list_reapable_tmux_sessions_for_run_id`)
**Description:** Severity rationale: MEDIUM (upper band) — under per-run sockets every orphaned row adds a `spawn_blocking` + `tmux list-sessions` subprocess to **every boot**, so growth is O(runs) process spawns at startup rather than a cosmetic row count; the cross-run kill destroys a live user session.

`run_tmux_sessions` rows are deleted on only two paths — reaper-after-confirmed-kill (`src/runtime.rs:6523-6537`) and terminal cleanup of still-registered active panes (`:6371`). Guard teardown and the abort path `kill_active_run_panes` (`:6554-6569`) both kill without deregistering: `PaneGuard::drop` (`src/tmux_exec.rs:450-463`) calls only `active_pane.clear_key()`, which removes the entry from `active_panes` (`src/runtime.rs:1155-1159`) — and since terminal cleanup derives its `killed_sessions` *from* `active_panes` (`:6344-6355` → `:6371`), the guard has already erased the only record that would have triggered `remove_tmux_sessions`. The reaper cannot compensate, because `:6507-6510` iterates *live* sessions and `continue`s on any name not present, so a row whose session is gone is never visited. There is no TTL, no `created_at`, no prune, and no `LIMIT` on the reapable query. Separately, `list_reapable_tmux_sessions_for_run_id` (`src/storage.rs:547-561`) filters only on `runs.status IN ('completed','failed','aborted','restarted')` with no exclusion of names registered to nonterminal runs, and `:6418` skips rows by `run_id` only — so `dismiss_run` (`:1592`) on an old terminal run can reach `:6517` and kill a live run's identically-named session.

*Corrections to the original write-up:* UUID suffixing does **not** refute the cross-run half, but the colliding names do not come from the path cited. `spawn_pane` (`src/tmux_exec.rs:2083-2087`) uniquifies only when no explicit name is given; `PaneGuard` builds its `SpawnConfig` with `session_name: None` (`:1002-1009`, `:1244-1251`), so `run_agent` sessions are always UUID-suffixed and can never collide. The colliding names originate from the **`spawn` node** (`:678-681`), whose explicit `SpawnConfig.session_name` goes through `stable_session_name` → `normalized_session_name(name, None)` (`:2482-2506`) with no UUID. The cross-run kill therefore requires an explicit `spawn`-node `sessionName` reused across runs, a shared invocation, and a reaper pass during the live window — narrower than stated, and impossible for `run_agent`. Also, the "`Drop` cannot reach async DB code" concern does not hold: `ActivePaneRegistration` carries a `tokio::runtime::Handle` and `clear_key` already does `handle.block_on` (`:550-556`).

*Relationship to H2:* **complementary — implement together, H2 first.** H2's finalized fix supplies the `has-session` absent/present probe that this reconciliation consumes. H2 makes accumulation marginally worse (rows are now retained on an unconfirmed kill), which is correct in isolation and tolerable only because this reconcile pass sweeps them on the next reap.

*Prior history:* not a regression. `20260705-074320` M3 created the table with a "DELETE at cleanup" contract, and S2 introduced `PaneGuard` with `Drop` explicitly scoped to "kill + `clear_key`" — DB deregistration was never in its contract. `20260716-003531` M7 recorded that registration is removed only after a successful kill and that the table has no TTL, but did not file it. No prior finding covers the cross-run name collision.
**Recommended Fix:** Make the reaper authoritative by reconciling the database against observed tmux state — the same discipline H2 establishes for kills.
- In the per-invocation reaper loop, after `list_silverbond_tmux_sessions` succeeds, delete every terminal registration in that invocation group whose session name is **absent** from `live_sessions`, replacing the bare `continue` at `src/runtime.rs:6507-6510`. Gate the deletion on a successful listing so a transient tmux failure cannot wipe live registrations.
- Add a `NOT EXISTS` anti-join to `src/storage.rs:547-561` excluding any session name registered to a nonterminal run, so a stale terminal row can never target a live run's session.
- Do **not** add a DB write to `PaneGuard::drop`: `Drop` does not run on SIGKILL or `abort()` (recorded `20260610`), so it can never be the guarantee, and adding it creates a second source of truth for no additional correctness.
- Tests: zero residual rows after an ephemeral agent run followed by a reap; a terminal stale row sharing a name with a live nonterminal run is not killed; a failing `list-sessions` deletes nothing. Note nine tmux/socket tests are EPERM-inconclusive under sandbox, so prefer the fake-tmux harness.
- Side benefit to verify: the pass should also clean rows orphaned by the abort path and by SIGKILL, and heal databases already carrying accumulated rows.
