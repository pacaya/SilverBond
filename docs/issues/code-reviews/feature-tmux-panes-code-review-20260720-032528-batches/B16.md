#### Issue M13: Unhandled promise rejections — abort/approve/respond fail silently
**Severity:** MEDIUM
**File(s):** `ui/src/app/AppShell.svelte:446` (`abortRun`), `:449` (`approveRun`), `:452` (`respondToInteraction`), `:461` (`dismissRun` — `.then` with no `.catch`), `:72-75` (`validateMutation`, no `onError`), `:220-223` (`runLifecycle` try/catch — the convention), `:360-361` (error pill render), `:57`, `:68` (mutation `onError` handlers); `ui/src/lib/api/client.ts:22-35` (`ApiError`), `:38-52`, `:51` (throw); `ui/src/lib/stores/workflowStore.svelte.ts:1051-1058` (`setError`, 5000 ms auto-clear); backend reachable failures `src/api.rs:2416`, `:2411`, `src/runtime.rs:1061`, `:1583-1586`
**Description:** Severity rationale: MEDIUM (upper edge) — `respondToInteraction` has a genuinely reachable 409 whose failure mode is a permanently blocked run with zero feedback; held below HIGH because `abortRun` is effectively infallible server-side, the fix yields only a 5-second transient pill, and the pattern is pre-existing on `development` rather than a branch regression.

Four API calls in `AppShell.svelte` are invoked as bare statements — `:446`, `:449`, `:452`, and `:461`, the last chaining `.then` with no `.catch` so both the call and the chained `invalidateQueries` float. All four sit inside arrow callbacks passed as props to `RunPanel`/`HistoryPanel`, so no parent can await them either. `apiFetch` throws `ApiError` on any non-2xx (`ui/src/lib/api/client.ts:51`) and nothing catches it: there is no `unhandledrejection` listener and no `<svelte:boundary>` anywhere under `ui/`. The non-2xx paths are real — `respond_interaction` returns `StaleInteractionSession` → **409** (`src/api.rs:2416`, `src/runtime.rs:1061`) on a double-submitted or stale interaction card, and `approve_run` → `resolve_approval` 404s when no approval is pending (`src/api.rs:2411`). The user clicks Approve or answers a prompt, nothing changes, and the run stays blocked, while every comparable action in the same file reports through the header pill at `:360-361` via `store.setError`.

*Correction to the original write-up:* "every other call path in the file routes errors through `store.setError`" is overstated. The direct-call paths do (`runLifecycle:220-223` covering `startRun`/`resumeRun`/`restartFromNode`; mutation `onError` at `:57`, `:68`), but `validateMutation` (`:72-75`) has no `onError` and the three `createQuery` calls at `:38-40` surface nothing — TanStack swallows those, making them silent-but-not-unhandled. Real ratio: 4 unguarded floating promises vs 5 guarded, plus 4 TanStack-managed calls that never reach the user.

*Prior history:* no prior review flagged these four sites, so no dismissal is being reversed. `docs/issues/feature-tmux-panes-code-review-20260610.md:140-142` rewrote what is now `:452` to pass `sessionId` without adding error handling (out of scope then), and `...20260716-003531.md:351-352`'s per-card `sessionId` work is precisely what makes the 409 reachable. The repo-wide convention across multiple FIXED findings (e.g. `...20260620-092605.md:337-342`, L8) is to surface failures loudly rather than drop them silently; this is the frontend instance of that rule. No `.test.ts` under `ui/src` references `abortRun`, `approveRun`, `respondToInteraction`, `dismissRun`, `setError`, or `errorMessage`.
**Recommended Fix:** Introduce one shared error-wrapping helper in `AppShell.svelte` and route every floating call through it with a per-action label.
- Define a local helper: `const guard = (label: string, p: Promise<unknown>) => void p.catch((e) => store.setError(\`${label} failed: ${e instanceof Error ? e.message : "Unknown error"}\`));` — reusing the `instanceof Error` narrowing already present at `:223` so the message shape stays identical to the rest of the file.
- Wrap all four sites with their own action names (`"Abort"`, `"Approve"`, `"Respond"`, `"Dismiss"`); at `:461` attach the guard around the whole `.then` chain so the chained `invalidateQueries` rejection is covered too.
- Close the adjacent silent gap in the same change: give `validateMutation` (`:72-75`) an `onError` that routes to `store.setError`, matching `:57` and `:68`.
- Do **not** add a global `unhandledrejection` listener as the fix: it leaves each call site unhandled and degrades the user-visible result to a generic unlabelled pill with no action name. It is acceptable only as a separate dev-time diagnostic.
- Add the missing regressions — no test currently touches any of these actions. Assert that a rejected `respondToInteraction` (409) sets `errorMessage` naming the action, and the same for `approveRun` (404).

#### Issue L13: Resync blanks the terminal with no repaint when the socket isn't open
**Severity:** LOW
**File(s):** `ui/src/features/runtime/PaneTerminal.svelte:167-174` (`resync`), `:168` (unconditional reset), `:169-170` (`unavailable` arm), `:75` (label), `:101` (`scrollback: 5000`), `:152` (`onSnapshot` reset), `:201` (button `disabled`), `:299` (CSS); `ui/src/lib/api/client.ts:306-310` (`requestResync`), `:233` (`PaneStreamStatus`), `:342` (`PANE_RECONNECT_MAX_MS`), `:347` (`connecting` emit), `:385-386` (`stalled` emit), `:488-489` (close → `scheduleReconnect`); `ui/src/lib/stores/workflowStore.svelte.ts:64`, `:722-726`; `src/api.rs:2062` (snapshot opts); test `ui/src/lib/api/client.paneStream.test.ts:612`
**Description:** Severity rationale: LOW — bounded at ~5 s with no permanently-blank path, but the premature reset discards xterm's 5000-line scrollback, and the dead `stalled` branch is a regression against S18's accepted fix intent.

`resync()` calls `term?.reset()` unconditionally at `PaneTerminal.svelte:168` before knowing whether the request can be sent, while `requestResync` silently returns when `socket.readyState !== OPEN` (`client.ts:306-310`); the button is enabled whenever a run exists (`:201`), so `connecting` and `closed` are both clickable. The pane then goes blank for up to 5 s (`client.ts:342`), and the eventual repaint restores only the visible screen — `src/api.rs:2062` passes `CaptureAnsiOpts::default()` with `start: None` — so the premature reset discards the 5000-line scrollback (`:101`) rather than merely flickering. Separately, `"stalled"` is emitted once at `client.ts:385` and overwritten synchronously by `connect()`'s `"connecting"` at `:347`; since `setPaneStatus` is a bare `$state` write rendered on a microtask (`workflowStore.svelte.ts:722-726`), the DOM never shows it and the label (`:75`), CSS rule (`:299`), and `stalled` branch of `resync()` (`:169`) are all unreachable.

*Correction to the original write-up:* there is no permanently-blank path — `client.ts:488-489` unconditionally schedules a reconnect on every non-`giveUp` close, and the sole terminal state (`unavailable`, `:300-304`) is already routed to `handle.reconnect()` at `PaneTerminal.svelte:169-170`. The blanking is bounded, but it is *history-losing*, not cosmetic.

*Prior history:* `"stalled"` was deliberately introduced by S18 (`docs/issues/feature-tmux-panes-code-review-20260705-074320.md:463-466`, FIXED), whose fix text required that "the UI stops showing Live over a dead terminal." That half was never achieved, so this is a regression against an accepted fix intent rather than gratuitous dead code — which argues for repairing the status, not deleting it.
**Recommended Fix:** Make the clear snapshot-driven so no state check is needed, and make `stalled` observable so S18's intent is honored.
- Delete `term?.reset()` from `resync()` (`PaneTerminal.svelte:168`) entirely. `onSnapshot` (`:152`) already resets before writing, so the clear happens exactly when replacement bytes exist — this removes the blank window on *all* paths, including the `open` path where a send-gated reset would still clear early.
- Route `resync()` by status: `open` → `requestResync`, every other status → `handle.reconnect()`. Keep the existing `unavailable` handling, which already does this.
- Stop calling `reconnect()` synchronously after `onStatus?.("stalled")` (`client.ts:385-386`) — defer it (e.g. `setTimeout(reconnect, 0)` or a short grace window) so the status actually renders and the `stalled` branch at `PaneTerminal.svelte:169` becomes live. Do **not** delete the status; that would discard S18's diagnostic and invalidate `client.paneStream.test.ts:612`.
- Add regressions: pressing Resync while `connecting` must not clear the terminal and must trigger a reconnect; a `stalled` emission must remain observable to a status subscriber across the deferred reconnect.
- Note as an independent pre-existing issue, not part of this fix: `src/api.rs:2062` snapshots the visible pane only, so *every* reconnect repaint loses scrollback — worth tracking separately.
