#### Issue H1: Session continuation can reuse an incompatible privileged pane
**Severity:** HIGH
**File(s):** `src/tmux_exec.rs:406-426` (reuse arm), `:926`, `:1235-1240`, `:2056-2194` (`spawn_pane`/`build_agent_command`), `:2119-2130` (pane stamps), `src/model.rs:1806-1819` (continuation validation), `src/driver.rs:282-334`, `:295-299`, `src/runtime.rs:2078-2086` (`agent_name_for_node`)
**Description:** Severity rationale: HIGH — fails silently while validation gives active false assurance; a read-only node executes in an unrestricted process and inherits the wrong driver's destructive-command blocklist.

For a `RunAgent` node the effective agent resolves from `runAgentConfig.agent` (`src/tmux_exec.rs:926`, `:1235`; `src/runtime.rs:2078-2086`), but continuation validation compares raw `node.agent` on both sides (`src/model.rs:1807-1808`), so a Codex-effective node passes the "same agents" check against a Claude source pane; `cwd` and `timeout` are shadowed the same way at `:1237-1240`. `PaneGuard::acquire` returns `(pane_id, None, true)` in the reuse arm (`src/tmux_exec.rs:406-426`) and never calls `spawn_pane` — which, with `build_agent_command` (`:2056-2194`), is the only place `access_mode`/`access_profile_override` become argv. Control then goes straight to `wait_for_mode`/`send_text` with no access or agent assertion anywhere. A downstream `read_only` node therefore executes inside the source pane's `Execute`/`Unrestricted` process, and `run_agent_interactive` selects its driver — including the destructive-command blocklist (`:994-1000`) — from the wrong agent.
**Recommended Fix:** Enforce launch-configuration compatibility at the point of pane adoption, using metadata the system already stamps.
- Promote the implicit access ordering in `src/driver.rs:295-299` into an explicit privilege rank on the profile type (`read-only < workspace-write < full-access`).
- In `PaneGuard::acquire`'s reuse arm (`src/tmux_exec.rs:407-411`), call `names::read(&pane_id)` and hard-error — in the existing `resolve_reused_pane` error style — unless the pane's `KEY_AGENT` equals this node's effective agent and its `KEY_ACCESS` rank is no broader than the profile `build_agent_command` would produce for this node's `AgentConfig`.
- Define and implement an explicit policy for panes spawned with a `command` override, which carry no `KEY_ACCESS` (`:2074`, `:2122`); fail closed.
- Fold in the editor-time projection of the same rule: export `agent_name_for_node` (or a `model.rs` twin) and use it on both sides of `src/model.rs:1807-1808`, extending the comparison to effective access profile and `cwd`, so authors see the error before the run starts.
- Add regressions for a `runAgentConfig.agent` override mismatch, for a `read_only` node continuing from a broader-access source, and for a `command`-override pane with no recorded access.

#### Issue M16: `default` access-profile fallback can silently widen `Edit`
**Severity:** MEDIUM
**File(s):** `src/driver.rs:282-324` (`resolve_registry_access_profile`), `:290` (`mapped`), `:291` (override arm), `:295-305` (widening guard), `:307-308` (else arm), `:310-311` (early return), `:314-315` (false comment), `:316-318` (`ReadOnly` fail-closed), `:319-321` (`default` fallback), `:323` (bail); `core/src/agents/mod.rs:28-30` (`AccessProfile`), `:180-186` (`Registry::load` merge), `:342-348` (unknown-name insert); `core/src/agents/builtin.rs:29-45`, `:76-93`, `:117-129`, `:149-156`, `:269`; `Cargo.toml:28` (upstream rev pin); neighbouring tests `src/driver.rs:1819`, `:1830`, `:1841-1887`
**Description:** Severity rationale: LOW — *lowered from MEDIUM*: latent-only. The branch is dead code against every shipped builtin and the operator's own `agents.toml`; reaching it requires a hand-authored registry entry that both omits `workspace-write` and gives `default` broad argv — an author configuring their own escalation, with no third-party channel. ID retained as `M16` for stability.

`resolve_registry_access_profile` resolves a profile name and, when that name is absent from `spec.access_profiles`, substitutes the literal `"default"` at `src/driver.rs:319-321` for every mode except `ReadOnly` (`:316-318`). The comment at `:314-315` asserts that a default "may safely reduce or preserve privileges" — a property the code never checks and *cannot* check, because `AccessProfile` carries only raw argv (`core/src/agents/mod.rs:28-30`) and exposes no privilege metadata. The widening guard at `:295-305` never runs on this path: it lives inside the `access_profile_override` arm (`:291`) and compares the override *name* against the mode, while the `default` fallback is a post-hoc substitution in the `else` arm (`:307-308`) reached only after the early return at `:310`. No test covers `:319-321`.

*Reachability correction to the original write-up:* the branch is **unreachable with the shipped registry**. All four builtins define both `workspace-write` and `full-access` (`builtin.rs:29-45` codex, `:76-93` claude, `:117-129` cursor, `:149-156` agy), as does the operator's `~/.config/tmux-tools/agents.toml`. The only mapped key missing anywhere is agy's `read-only` (asserted at `:269`), which lands on the fail-closed branch at `:316-318`. Custom entries are possible — `Registry::load` merges `~/.config/tmux-tools/agents.toml` (`mod.rs:180-186`) and inserts unknown names as new agents (`:342-348`) — so a user-authored agent declaring only a broad `[x.access.default]` is the sole reaching path.

*Prior history — this reverses a recorded ruling.* `docs/issues/feature-tmux-panes-code-review-20260705-074320.md:514-519` (L7, FIXED) created this asymmetry deliberately and ruled the Edit/Execute side safe: "Read-only is the only mode whose default-fallback can escalate privilege — edit/execute/unrestricted falling to `default` keep or drop privilege (fail-safe)... add a comment explaining it." The comment M16 attacks is the one that ruling mandated. The reversal is correct in principle: the ruling rested on an assumption about `default` that nothing enforces. `...20260716-003531.md:88-92` (M1) later added the `:291-305` override arm and its guard.

*Relationship to H1 — H1 does **not** subsume this.* H1's finalized fix promotes the implicit ordering at `:295-299` into a privilege rank over `read-only < workspace-write < full-access`; `"default"` is not in that lattice and `:319-321` never consults it. H1 supplies the mechanism, not the check. **Sequence M16 after H1.**

*Relationship to M11 — no dependency in either direction.* M11's finalized text sequences itself behind M16 to avoid "inheriting the hole"; verification shows that is unnecessary. Today Spawn's omitted `access` passes `None` into **core's** own fallback (`core/src/agents/mod.rs:222-240`), which is reachable for every builtin, unguarded, and stamps `KEY_ACCESS` regardless — so routing Spawn through `resolve_registry_access_profile` is a strict improvement even with `:319-321` intact. M11 needs nothing from M16, and this fix needs no Spawn-specific addition. *(M11's own sequencing note has been left as written; correcting it was raised but not decided.)*
**Recommended Fix:** Extend H1's privilege rank over the fallback branch so `default` is accepted only when it is provably no broader than the profile it replaces.
- Land **after H1**, and reuse the rank type H1 introduces rather than defining a second ordering.
- Give `AccessProfile` a declared privilege rank and accept the `default` substitution at `:319-321` only when `rank(default) <= rank(mapped)`. A `default` that is unranked or undeclared fails closed via `:323`.
- `AccessProfile` lives in the pinned upstream crate (`Cargo.toml:28`), so this is a coordinated two-repo change: add the rank upstream, then bump the rev. H6 already establishes that upstream edits are in scope for this branch — coordinate the two rev bumps.
- Do **not** implement the rank as a driver-side map keyed on profile *name*: it cannot rank `default` at all, which is the entire question, and collapses into simply deleting the fallback.
- Do **not** infer rank by parsing `default`'s argv for known-broad flags. A denylist over free-form argv is unsound across agents and versions, and the adjudication note explicitly rules it out.
- Delete the false comment at `:314-315` and replace it with text describing the rank check that now exists.
- Add the missing regression: an `Edit` run against a custom agent that declares only a broad `default` must fail closed rather than launch; add a companion positive case where a narrow `default` is accepted.
