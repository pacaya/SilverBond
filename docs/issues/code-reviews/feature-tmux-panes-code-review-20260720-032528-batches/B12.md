#### Issue M15: ~4 full-checkpoint DB writes per second for the whole duration of a human approval wait
**Severity:** MEDIUM
**File(s):** `src/runtime.rs:2795-2798` (ungated persist), `:2789-2790` (`changed`), `:2830`, `:2847-2850`, `:2852`, `:2862-2865` (`wait_changed` gating), `:3518-3535` (`wait_for_approval`), `:3526-3530` (decision arm), `:3531` (250 ms sleep), `:6577-6594` (`persist_checkpoint`), `:6582` (`updated_at` stamp), `:6299`, `:551-589` (checkpoint contents); `src/storage.rs:255-287` (`update_run_checkpoint`), `:284` (`state_json`), `:186-203` (frozen `workflow_json`), `:976-980` (pool), `:991-995` (WAL, `synchronous=NORMAL`, 5 s busy_timeout)
**Description:** Severity rationale: MEDIUM (low end) — pure write churn with no correctness or security impact and no executor blocking; held above LOW because the wait is unbounded by construction, every write is genuinely byte-different so nothing dedups, and this is the known-incomplete remainder of a chartered prior fix.

While a run is parked on a human approval and no agent tasks are in flight, the loop at `src/runtime.rs:2793-2799` spins a 250 ms poll and unconditionally re-serializes and re-writes the full `RuntimeCheckpoint` at `:2797` — `changed` is false at `:2789` while parked, so `:2790` is skipped and `:2797` is the sole write per iteration. That is ~4 writes/s, ~14,400/hour, ~115,000 overnight. The blob is `state_json` (`src/storage.rs:284`), carrying `all_results` (every node's full agent output), `batch_item_results`, `execution_log`, and `output_hashes` (`src/runtime.rs:551-589`) — realistically 50 KB–2 MB on a moderate workflow — and `persist_checkpoint` stamps `updated_at = now_iso()` (`:6582`) before writing, so every blob is byte-different and nothing dedups. Cost is full JSON serialization per tick plus roughly 800 KB/s of WAL traffic on a 200 KB blob, with the periodic auto-checkpoint fsync stealing the pool's writer slot from `append_event`. The wait is unbounded: approval resolves only via the oneshot `wait.receiver`, and there is no timeout arm in `wait_for_approval` or `restore_pending_approval`.

*Corrections to the original write-up:* (1) the cited line range is the **caller** — `wait_for_approval` itself is at `:3518-3535` with its 250 ms arm at `:3531`, and the ungated persist is `:2796-2797`. (2) "the entire checkpoint" is right but the implied cost is inflated: this is **one** `UPDATE runs` writing 10 columns, and `workflow_json` is *not* rewritten (frozen at INSERT, `src/storage.rs:186-203`). (3) "pre-existing; identical on `development`" is misleading — `wait_changed` does not exist on `development` at all, where the *whole* loop persisted unconditionally; this branch fixed two of three sites and `:2795-2797` is the leftover. Mitigating: WAL is on with SQLite's default 1000-page auto-checkpoint (`src/storage.rs:991-995`), so the WAL does not grow unbounded, and writes run on `spawn_blocking` against a pool, so the executor is never blocked.

*Prior history — this is the residual of a chartered prior fix, never a dismissal.* `docs/issues/feature-tmux-panes-code-review-20260620-092605.md:125-130` M9 (FIXED) specified exactly this remedy — "gate the 250ms tick persist with a dirty flag set where the loop does dispatch/apply work" — and the implementation introduced `wait_changed` at `:2830`/`:2852` but missed the `wait_for_approval` early-`continue` path. `docs/issues/feature-tmux-panes-code-review-20260610.md:186` had flagged the same ~4×/s pattern earlier as an efficiency smell. **Downstream dependency worth knowing:** `...20260620-092605.md:183` lowered its M14 to LOW *explicitly because* "M9's dirty-flag persist gate removed the per-250ms re-serialization premise" — an assumption that is false on the approval path until this lands. No overlap with M4, M7, or M8 in this review.
**Recommended Fix:** Make "don't write what didn't change" an invariant of the persistence boundary rather than a rule each caller must remember.
- In `persist_checkpoint` (`src/runtime.rs:6577-6594`), serialize the checkpoint once and hash the resulting JSON **before** stamping `updated_at`, so the stamp cannot defeat the comparison.
- Hold a `last_persisted_hash` on `RuntimeContext`; when the hash is unchanged, skip the DB write entirely and leave `updated_at` un-advanced. Stamp `updated_at` and update the stored hash only on an actual write.
- Audit readers of `updated_at` before landing: it will stop advancing while a run is idle, and any UI or reaper logic that infers staleness or liveness from it must be adjusted to use run status instead.
- This closes the whole class at one choke-point, including `:6299` and any unaudited caller — not just the `wait_for_approval` path.
- Add a regression asserting that N consecutive idle ticks during an approval wait produce exactly one (or zero) `update_run_checkpoint` calls; no test currently covers write frequency, only the correctness round-trips at `src/storage.rs:1373`/`:1410`.
- Complementary trivial follow-up, not part of this fix: returning `bool` from `wait_for_approval` and gating `:2796-2797` on it would make all three loop exits structurally symmetric and finish M9 item (3) as literally chartered. It is redundant once the hash gate lands, but harmless and clarifying.

#### Issue L10: Unbounded hot loop with no sleep in the scheduler
**Severity:** LOW
**File(s):** `src/runtime.rs:2823` (the bare `continue`), `:2793` (`running_tasks.is_empty()`), `:2663` (`is_aborted`), `:2680` (abort break), `:2681` (`process_immediate_cursors`), `:2790` (`changed`-gated persist), `:2794-2798` (M15's arm), `:2801`, `:2805-2821` (`WaitingCollector` arm), `:2941-2946`, `:3441` (`activate_next_approval` early return), `:3413-3414` (`queue_approval`), `:2262-2292` (`rehydrate_checkpoint_for_execution` consistency check), `:2277` (`cancel_requested` retain), `:4599`, `:4605-4607` (`handle_approval_resolution`); `src/storage.rs:186-203`
**Description:** Severity rationale: LOW — real and unbounded (one core pegged, run never terminates), but reachable only from an already-inconsistent checkpoint, with no data loss and a working abort escape hatch.

The bare `continue` at `src/runtime.rs:2823` is taken when `running_tasks` is empty, no approval is active, cursors exist, and not all are `WaitingCollector`. The iteration contains no pending await — `is_aborted` (`:2663`) hits an uncontended mutex fast path, `process_immediate_cursors` (`:2681`) reaches `activate_next_approval`'s early `Ok(false)` at `:3441` and then filters zero runnable cursors (`:2941-2946`) — and `persist_checkpoint` (`:2790`) is gated by `changed`, so the branch performs no emit, no persist, and no sleep. Result: **100% of one core with zero DB writes**, and on a current-thread runtime it would also starve the executor. The run stays Running indefinitely with a frozen `updated_at`. No guard exists: no iteration counter, no elapsed check (`start_instant` at `:2640` is used only for final duration), no watchdog, and `max_total_steps` is enforced in `prepare_cursor_visit`, which never runs here.

*Correction to the original write-up — the cited reachability path is refuted.* The `cancel_requested` retain at `:2277` is immediately followed by the guard at `:2286-2292`, which detects "pending_approval set but no `WaitingApproval` cursor" and routes it to `drop_inconsistent_pending_approval`. If the dropped cursor was the only `WaitingApproval` one, the branch is unreachable; and any surviving `WaitingApproval` cursor was placed there by `queue_approval` (`:3413-3414`), which sets the state and pushes the `queued_approvals` entry in the same synchronous block, so the loop parks in the M15 arm instead. Mid-run `fail_fast_cancel` (`:5961`) always sets `terminal_reason` first, and `restart_from` (`:1467-1486`) replaces `active_cursors` wholesale.

*Actual reachable paths:* (1) `handle_approval_resolution` clears `pending_approval` at `:4599` then returns early at `:4605-4607` if the approval node is absent from the cursor's graph — effectively unreachable while `workflow_json` is frozen at INSERT (`src/storage.rs:186-203`); (2) any externally inconsistent persisted checkpoint — partial write, hand-edited DB, older-version row, or a future cursor-state bug — since `rehydrate_checkpoint_for_execution` validates pending-without-cursor but **never** cursor-without-pending.

*Distinct from M15:* M15's spin is the `active_approval.is_some()` arm at `:2794-2798`, which sleeps 250 ms and writes a full checkpoint per tick. L10's branch writes nothing at all. The fixes are adjacent in the file but functionally independent.

*Escape hatch:* abort works. `is_aborted` is the first statement of every iteration (`:2663`), so the spinning loop observes the flag within microseconds and breaks at `:2680`.

*Governing precedent:* `docs/issues/feature-tmux-panes-code-review-20260620-092605.md:341-342` handled the mirror-image inconsistency by surfacing it loudly (warn + `workflow_warn` event) and **explicitly rejected** reconstructing the approval as riskier than dropping it.
**Recommended Fix:** Close the entry path at the boundary that already owns this repair, and make the loop branch a permanent tripwire rather than the mitigation.
- Extend the consistency check at `src/runtime.rs:2286-2292` with its converse: any cursor in `WaitingApproval` with no matching `pending_approval` and no `queued_approvals` entry is reconciled through the established `drop_inconsistent_pending_approval` convention — `tracing::warn!` plus a `workflow_warn` event naming the cursor and node, then drop the orphan cursor. Follow the `20260620` precedent: surface loudly, drop rather than reconstruct.
- Decide and document the case where the orphan is the run's only cursor: dropping it leaves `active_cursors` empty, which breaks cleanly at `:2801`, so verify that path finalizes with a sensible status rather than a bare Completed.
- Replace the bare `continue` at `:2823` with the internal-error shape already used by the sibling `WaitingCollector` arm at `:2805-2821`: emit `workflow_error` naming the stuck cursor and node, set `status = Failed` and `terminal_reason = "failed"`, clear cursors, and `break`. This makes the loop total — every state either progresses or terminates.
- Do **not** simply add a sleep: that leaves the run hanging forever and merely converts a visible CPU pin into an invisible permanent stall.
- Add two regressions: a rehydrated checkpoint carrying a `WaitingApproval` cursor with empty `pending_approval`/`queued_approvals` is reconciled at load with a warn event; and, bypassing rehydration, the loop branch terminates the run as Failed instead of spinning.

#### Issue L14: `abort_and_wait` awaits `drained_token` with no timeout
**Severity:** LOW
**File(s):** `src/runtime.rs:951-957` (`abort_and_wait`), `:956` (unbounded await), `:952` (guard dropped), `:1071-1073` (`RunRegistry::clear`, sole `drained_token.cancel()`), `:1386`, `:1425`, `:1567` (bare `tokio::spawn` of the run task), `:1405` (`AlreadyActive`), `:1449` (`restart_from` await), `:2878-2896` (error path → `finalize_run`), `:6324-6325` (`cleanup_terminal_active_panes` before `clear`), `:4119-4145` (`apply_join_result`, child tasks only), `:5213` (per-item `catch_unwind`), `:6871-6905` (`PendingInteractionGuard` pattern); `src/api.rs:113-151` (router layers), `:2260` (`restart_run` handler); tests `src/runtime.rs:7665-7687`, `:9516`
**Description:** Severity rationale: MEDIUM — *raised from LOW*: unrecoverable without a server restart (the run id is wedged for resume, restart, and abort alike) and the hung request leaks a task with no server-side timeout; held down only by requiring a top-level panic. ID retained as `L14` for stability.

`abort_and_wait` cancels `abort_token` then awaits `drained_token.cancelled()` with no bound (`src/runtime.rs:956`); that token is cancelled only in `RunRegistry::clear` (`:1071-1073`), whose sole production caller is the tail of `finalize_run` (`:6325`). The run task is spawned as a bare `tokio::spawn` at `:1386`, `:1425`, and `:1567` — the `JoinHandle` is dropped immediately, nothing observes it, no `catch_unwind` wraps it, no `Drop` impl cancels the token, and `Cargo.toml` sets no `panic = "abort"` — so a panic unwinding out of `execute_workflow_to_terminal` never reaches `finalize_run`. `restart_from` awaits this at `:1449` and the axum handler `restart_run` (`src/api.rs:2260`) has no timeout layer (the router at `src/api.rs:113-151` carries only origin middleware), so the request hangs until the client gives up while the stale registry entry makes `resume_run` return `AlreadyActive` forever (`:1405`). No lock is held across the await — the map guard drops in the `let-else` at `:952` — so damage is confined to that run id plus the leaked request task.

*Verification notes:* the error-return path **is** covered (`execute_workflow_to_terminal` → `fail_workflow_after_error` → `finalize_run`, `:2878-2896`), so the finding's "outside `execute_workflow`'s covered path" wording is accurate. The existing unwind machinery is strictly inner: `catch_unwind` at `:5213` wraps a single parallel-batch item and `apply_join_result` (`:4119-4145`) handles `JoinError`/`is_cancelled` for child cursor tasks only — neither covers the top-level run task.

*Second hang path the original write-up missed:* `finalize_run` awaits `cleanup_terminal_active_panes` **before** `registry.clear` (`:6324-6325`), so a wedged tmux stalls the drain signal even when the run task is alive and healthy.

*Prior history:* not a regression, and not a previously accepted risk. `docs/issues/feature-tmux-panes-code-review-20260716-003531.md:275-287` L4 (FIXED) introduced `drained_token`, converting `abort_and_wait` from a `Notify` race to a latched token for lost-wakeup immunity; the unbounded await was accepted as correct *given a cooperative drain*. The panic/`JoinError` path was never considered there or in the `20260620`/`20260705` reviews.
**Recommended Fix:** Make every task-termination mode cancel the drain signal, and bound the await as defense in depth for the non-task stall.
- Replace the three bare `tokio::spawn` calls (`:1386`, `:1425`, `:1567`) with a supervisor that retains the `JoinHandle` and, on `Err(JoinError)`, calls `registry.clear(&run_id)`. `is_panic()` and `is_cancelled()` both land in `Err`, and `clear` is idempotent (`remove` returns `None` on the second call), so the normal path is unaffected.
- Additionally wrap the await at `:956` in `tokio::time::timeout`, force-clearing the registry entry on expiry. This is not redundant with the supervisor: it is the only thing that rescues the `cleanup_terminal_active_panes` stall at `:6324-6325`, where the task is healthy but the signal is blocked.
- Choose the timeout generously relative to `cleanup_terminal_active_panes`' own tmux budget so a legitimately slow drain is never cut short, and `warn!` with `run_id` on expiry so a force-clear is always visible.
- Known remaining gap to note in the change, not solved here: on panic the registry is cleaned but the run's DB checkpoint is still left `Running`. Reconciling persisted status on `JoinError` is a separate concern.
- Add regressions for the panic path specifically: a run task that panics must leave no registry entry and must let a subsequent `resume_run` proceed rather than returning `AlreadyActive`; and `abort_and_wait` must return within its bound when the drain signal never arrives. `abort_and_wait_returns_when_the_run_drains_concurrently` (`:7665-7687`) covers only the cooperative drain and `:9516` only `finalize_run` clearing on persistence error — there is zero panic-path coverage today.
