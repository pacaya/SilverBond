#### Issue L8: `build_log_id` collides at one-second resolution
**Severity:** LOW
**File(s):** `src/runtime.rs:6803-6806` (`build_log_id`), `:6247`, `:6280` (sole call site in `finalize_run`), `:1354`, `:1365` (`run_{Uuid::now_v7()}`, unconstrained concurrency), `:2493`, `:3250` (inline subflow/batch execution); `src/storage.rs:152-153` (`logs.id TEXT PRIMARY KEY`), `:649-690` (`save_execution_log` upsert), `:702` (history ordering); `src/util.rs:41` (`slugify_filename`); `src/api.rs:148-149`, `:2282-2292`, `:2256`; `ui/src/lib/api/client.ts:124-127`; `ui/src/features/history/HistoryPanel.svelte:20`, `:55`, `:201` *(pre-existing)*
**Description:** Severity rationale: LOW — real, unrecoverable loss of a user-visible history entry, but it requires two same-slug top-level runs terminating in the same wall-clock second, and no fan-out path multiplies logs per run.

`build_log_id` is `format!("{}_{}", slugify_filename(workflow_name), Utc::now().format("%Y-%m-%dT%H-%M-%S"))` — a workflow-name slug plus one-second resolution, discarding the already-unique `run_id` available on the checkpoint at the sole call site (`src/runtime.rs:6280`). `save_execution_log` upserts with `ON CONFLICT(id) DO UPDATE SET filename=…, run_id=excluded.run_id, data_json=excluded.data_json` against `logs.id TEXT PRIMARY KEY` (`src/storage.rs:152-153`, `:649-690`), so a colliding run destroys the earlier row outright — `run_id` and full `data_json` included. The loss is user-visible: these rows are exactly what `GET /api/logs` (`src/api.rs:148-149`, `:2282-2292`) feeds to `HistoryPanel.svelte:201`, so a completed run silently disappears from run history. Concurrency is unconstrained — `registry.register` is keyed by the unique `run_id` (`src/runtime.rs:1354`, `:1365`), so `AlreadyActive` can never fire for a second run of the same workflow. `slugify_filename` (`src/util.rs:41`) replaces only non-`[A-Za-z0-9_- ]` characters, so distinct names can collapse to one slug as well (`My Flow!` and `My Flow?` → `My Flow_`).

*Reachability, narrowed:* fan-out does **not** multiply logs. `build_log_id` has exactly one call site, in `finalize_run` (`src/runtime.rs:6247`, `:6280`); subflow and `Call` nodes execute inline via frames (`:3250`, results into `frame.subflow_results` at `:2493`) and `parallel_batch` items likewise — neither spawns a nested run nor calls `finalize_run`. The trigger is therefore two *separate* top-level runs of the same workflow whose terminal moments land in the same second: plausible for short workflows fired concurrently or a fast run plus `restart_run` (`src/api.rs:2256`), not for typical single-run use. Tests do not trip it — the `finalize_run` tests at `src/runtime.rs:9516`, `:10433` each use their own `TempDir` DB. No file is written; `filename` is a cosmetic `"{id}.json"` DB column.

*Sortability is not a constraint:* history is `ORDER BY start_time DESC` (`src/storage.rs:702`), not by id, so an id-format change breaks no reader ordering.

*Prior history:* no prior review covers `build_log_id` or log-id collisions. `docs/issues/feature-tmux-panes-code-review-20260620-092605.md` M19 concerns an unrelated merge-key collision.
**Recommended Fix:** Derive log identity from the run rather than from the clock.
- Change the signature to `build_log_id(workflow_name: &str, run_id: &str)` and emit `format!("{slug}_{}", run_id.trim_start_matches("run_"))`, keeping the slug as a readable prefix. Pass the `run_id` already present at `src/runtime.rs:6280`.
- This eliminates the collision class structurally: `run_id` is a UUIDv7 minted at `src/runtime.rs:1354`, so uniqueness is guaranteed rather than probabilistic, and UUIDv7 keeps the id time-sortable. It also makes the log row joinable to `runs` and to events by inspection.
- Do **not** merely raise timestamp resolution: sub-second formats narrow the window without closing it, and `Utc::now()` is not monotonic, so a backward clock step can re-collide. Do not append a random suffix either — it mints an unrelated value when a unique id is already in hand.
- Confirm the resulting id passes `safe_name` unchanged (UUID hex is alnum plus `-`, already within the allowed charset).
- Leave existing rows in the old format; no migration is needed since nothing parses the id and ordering is by `start_time`.
- Add a regression: two runs of the same workflow finalized within the same second produce two distinct log rows, both retrievable via `GET /api/logs`.

#### Issue L15: `restore_pending_approval` binds a restored approval to the wrong cursor
**Severity:** LOW
**File(s):** `src/runtime.rs:3477-3494` (`restore_pending_approval`), `:3482` (empty-id first matcher), `:3484-3489` (unqualified `.or_else`), `:3505-3507` (emitted prompt), `:3413-3414` (`queue_approval`), `:3444` (`activate_next_approval` `remove(0)`), `:3462-3465`, `:2680`, `:2708`, `:2924` (wholesale clears), `:4605` (resolution reads the cursor's own `node_id`), `:4614-4643` (synthetic user result), `:4707-4712`, `:2303-2325` (`drop_inconsistent_pending_approval`), `:2189`, `:2267` (rehydration-minted cursors), `:2330` (`update_checkpoint_summary`), `:133-134` (`PendingApproval::cursor_id` serde), `:558-559` (`active_cursors` serde); test `src/runtime.rs:9567`
**Description:** Severity rationale: LOW — reachable only via a corrupt or hand-edited checkpoint, with no in-process path producing the required state; retained on the list because the failure mode is a silently bypassed human approval gate with a fabricated user-success result.

`restore_pending_approval` resolves the persisted approval by cursor id, then falls back at `src/runtime.rs:3484-3489` to *any* `WaitingApproval` cursor with no `node_id` check. That cursor already owns its own `queued_approvals` entry (`:3414`), and nothing prunes it — the only removals are `activate_next_approval`'s `remove(0)` (`:3444`) and wholesale `.clear()` on abort/fail (`:2680`, `:2708`, `:2924`), with no `retain` anywhere in `src/`. The cursor is therefore resolved twice: once from the restored oneshot, then again after re-activation (`:3444` → `:3462-3465`), each time stamping an `agent: "user"`, `success: true`, `"[Approved by user]"` result (`:4614-4643`) onto the cursor's *then-current* node, because `handle_approval_resolution` reads the cursor's own `node_id` at `:4605` rather than `pending.node_id`. A human gate is bypassed and a fabricated approval result lands on an unrelated node.

*Reachability correction to the original write-up:* the fallback is **not** the legacy-checkpoint path. The first matcher at `:3482` already accepts any `WaitingApproval` cursor when `pending.cursor_id.is_empty()`, and legacy rows deserialize with an empty id (`#[serde(default, skip_serializing_if = "String::is_empty")]`, `:133-134`; `active_cursors` `#[serde(default)]`, `:558-559`), so they take the first branch. The `.or_else` fires only for a **non-empty but unmatched** id, and `queue_approval` sets `WaitingApproval` and pushes the queued entry in one synchronous block (`:3413-3414`) with no path removing such a cursor while `pending_approval` points at it — so no ordinary run, restart, or resume produces that state. Entry requires a corrupt, hand-edited, or partially-written DB row. This mirrors the same review's L10 reachability correction.

*Pre-existing mismatch inside the fallback:* the emitted `approval_required` carries `pending.node_id`/`prompt` (`:3505-3507`) while resolution applies to the bound cursor's current node (`:4605`) — the user is shown node X and node Y receives the result.

*Prior history:* the fallback is **not** deliberate recovery behavior added by a prior fix — `git log -L3477,3494` traces it to the initial commit `d54da2f`. Qualifying it therefore reverses no prior decision, though it does soften the "surface loudly, drop rather than reconstruct" precedent recorded at `…20260620-092605.md:341` and re-ratified in this review's L10.
**Recommended Fix:** Qualify the fallback so it can only bind a cursor that provably owns the persisted approval, and fall through to the drop path otherwise.
- In the `.or_else` at `src/runtime.rs:3484-3489`, require both that `cursor.node_id == pending.node_id` and that the cursor has no entry of its own in `checkpoint.queued_approvals`. This keeps recovery working for the genuine case — a rehydration-minted cursor (`:2189`, `:2267`) whose `node_id` matches `pending.node_id` via `update_checkpoint_summary` (`:2330`).
- When no cursor satisfies both conditions, fall through to `drop_inconsistent_pending_approval` (`:3492` → `:2303-2325`) so the inconsistency is warned and surfaced rather than guessed at.
- Handle the ambiguous case explicitly: if more than one `WaitingApproval` cursor matches `pending.node_id`, do not pick one — fall through to the drop path and `warn!` with the candidate cursor ids.
- Fix the prompt/resolution mismatch in the same change: the `approval_required` emitted at `:3505-3507` must describe the node the resolution will actually apply to (`:4605`), not `pending.node_id`, so the two can never disagree once the fallback binds.
- Add regressions for the fallback branch, which has none today: a non-empty unmatched `cursor_id` with a node-id-matching idle cursor must bind and resolve exactly once; the same with a node-id mismatch must drop and warn; and a bound cursor must never be resolved a second time via `activate_next_approval`. `resume_warns_when_pending_approval_has_no_waiting_cursor` (`:9567`) exercises only the `:2286-2292` drop and never reaches `:3484`.
