#### Issue M10: `O(call_nodes × subflow_size)` validation blowup blocks a tokio worker
**Severity:** MEDIUM
**File(s):** `src/model.rs:944-960` (`WorkflowV3::graph`), `:1326-1363` (`validate_workflow_input_bounds`), `:1365` (`validate_graph_body`), `:1484` (per-node dispatch), `:2000-2021` (`validate_subflow_catalog`), `:2061`, `:2078-2083`, `:2149-2153`; `src/api.rs:168` (`require_same_origin_mutation`), `:546-548`, `:723-732`; `src/main.rs:21`
**Description:** Severity rationale: MEDIUM — mostly self-inflicted (a legitimate large workflow already hangs the UI for seconds on every validate) plus a local-process DoS; bounded by the loopback bind and the multi-worker runtime, but reachable with no unlock gate.

`validate_graph_body` loops every node and dispatches each `Subflow`/`Call` to `validate_subflow_node_config` (`src/model.rs:1484`), which rebuilds the callee's entire graph via `subflow.graph()` (`:2061`) — three `HashMap`s over all its nodes and edges (`:944-960`) — then scans every callee node for terminals with `outgoing_for` (`:2078-2083`) and rebuilds a `BTreeSet` of its variables (`:2149-2153`). All of this is per call node, giving `Σ(call nodes) × |callee|`; `validate_subflow_catalog` (`:2000-2021`) re-runs `validate_graph_body` for each subflow, so calls nested inside subflows amplify further. Measured on a release build: 200 calls / 500-node subflow (97 KB JSON) = 132 ms; 400/1000 (196 KB) = 874 ms; 800/2000 (398 KB) = **5.09 s**. Both HTTP entry points run it inline on the async task with no `spawn_blocking` (`src/api.rs:548`, `:732` — the latter after a deep `clone()`), `hydrate_saved_subflows` runs *before* `enforce_workflow_input_bounds` (`:546`/`:547` and `:723`/`:731`), and the existing bounds count only subflows and call edges, never nodes (`src/model.rs:1326-1363`). No `DefaultBodyLimit` exists anywhere in `src/`; axum 0.8's `Json` default is 2 MB.

*Worse than the original write-up:* hydration is an **amplifier**. A ~400 KB payload of 4096 trivial call nodes — exactly the `MAX_SUBFLOW_CALL_EDGES` ceiling — pointing at a single **saved** 2000-node subflow pulls that body from disk and extrapolates to roughly **26 s of CPU per request**.

*Reachability, refined:* single-user desktop app bound to `127.0.0.1:3333` (`src/main.rs:21`) with no authentication anywhere; `require_same_origin_mutation` (`src/api.rs:168`) rejects header-less clients, blocking cross-site browser pages and naive `curl`. But that middleware is CSRF protection, not authn — any local process can set `Origin: http://localhost:3333` and pass — and `/api/validate-workflow` carries **no unlock gate**, unlike `create_run` (`:724`). The runtime is `#[tokio::main]` default (num_cpus workers), so a single request degrades rather than kills; a loop of them saturates every worker including the health endpoint.

*Prior history:* direct precedent in the same file. `docs/issues/feature-tmux-panes-code-review-20260705-074320.md:160-169` M10 (FIXED) addressed exponential subflow-cycle detection under the same threat framing, and its fix introduced `MAX_WORKFLOW_SUBFLOWS`/`MAX_SUBFLOW_CALL_EDGES` explicitly as "defense-in-depth … bounds V regardless of algorithm" — sized for that algorithm's V, with a node-count cap never considered. That review also observed the missing `spawn_blocking` and **deliberately declined it**, choosing to fix the algorithm instead. `...20260716-003531.md:307-316` S2 (FIXED) later closed a bounds bypass via nested catalogs. This review's own smells list files the same code as Feature Envy, proposing a `validate_call_against` method on the subflow type.
**Recommended Fix:** Make validation linear by precomputing per-subflow facts once, and bound total input after hydration.
- In `validate_workflow`, build a single `BTreeMap<&str, SubflowFacts>` where `SubflowFacts` holds the subflow's node-id set, terminal-node id list, and variable set.
- Thread that map through `validate_graph_body` and `validate_subflow_node_config` so each call node performs only string comparisons against precomputed sets, never rebuilding a graph. All borrows are immutable from one `&WorkflowV3`, so lifetimes stay trivial; prefer `SubflowFacts` over carrying whole `WorkflowGraph`s.
- Add a total node+edge cap to `validate_workflow_input_bounds` (`src/model.rs:1326-1363`) — suggested 50k nodes / 100k edges, roughly 25× the largest plausible authored workflow — and count it **after** hydration so the saved-subflow amplification path is covered.
- Do **not** wrap `validate_workflow` in `spawn_blocking`: it relocates the CPU burn onto the pool shared with every `src/storage.rs` DB call, so a flood would stall persistence instead of HTTP. The `20260705` review reached the same conclusion.
- This also resolves the Feature Envy smell filed against `validate_subflow_node_config`; consider expressing `SubflowFacts` as a method on the subflow type.
- Add a validation-cost regression (e.g. 800 calls × 2000-node subflow completing well under a fixed budget) and a test asserting the post-hydration cap rejects an over-large hydrated catalog.

#### Issue L4: `retry_count` is unclamped — debug-build panic, and an unbounded retry runaway in the reachable mid-range
**Severity:** LOW
**File(s):** `src/runtime.rs:3696` (the `+ 1`), `:3697-3716` (retry loop), `:2110` (`timeout_for_node`), `:2778`, `:2832`, `:2854` (`JoinSet`), `:3729` (`retry_delay` → `Duration::from_secs`), `:4137-4146` (`apply_join_result`), `:6096`; `src/model.rs:813` (`retry_count`), `:815` (`retry_delay`), `:821` (`loop_max_iterations`), `:1326-1363` (`validate_workflow_input_bounds`); `src/api.rs:547`, `:731` (`enforce_workflow_input_bounds`); `ui/src/features/editor/InspectorPanel.svelte:991-998`
**Description:** Severity rationale: LOW — the claimed release-mode "zero attempts" failure does not exist and the debug panic degrades to a clean `Failed` run; what keeps it on the list is the reachable mid-range runaway (`retryCount: 1000`) through a UI input with no `min`/`max`.

`src/runtime.rs:3696` computes `node.retry_count.unwrap_or(0) + 1` on a `u32` with no clamp, and `validate_workflow_input_bounds` (`src/model.rs:1326-1363`) bounds only `MAX_WORKFLOW_SUBFLOWS` and `MAX_SUBFLOW_CALL_EDGES` — no per-node numeric limits, and `enforce_workflow_input_bounds` at `src/api.rs:547`, `:731` adds none. The practically important consequence is not the overflow but the mid-range: `retryCount: 1000` produces 1000 sequential agent invocations with no cap anywhere, since `timeout_for_node` (`:2110`) is per-attempt and there is no global run timeout. Ingress is the ordinary UI — `InspectorPanel.svelte:991-998` is a bare `type="number"` with no `min`/`max` and no clamp — so a typo or paste reaches the backend directly, not only a hand-edited file.

*Corrections to the original write-up:* the release-mode claim is **wrong**. The loop at `src/runtime.rs:3697-3716` is a do-while — `attempts += 1` precedes the `attempts >= max_attempts` guard — so `max_attempts = 0` executes the node exactly once and reports its real success/failure, behaviorally identical to `max_attempts = 1`. There is no silent skip and no false success. The debug panic is real (overflow checks on; no `[profile]` overrides in `Cargo.toml`) but benign: it occurs inside `run_cursor_task` spawned at `:2778`, is joined at `:2832`/`:2854`, and lands in `apply_join_result`'s `Err` arm (`:4137-4146`), emitting a `workflow_error` event with the panic message and setting `status = Failed` — an attributable failure with no unwind escape or checkpoint corruption.

*Sibling fields sharing this shape, one of them worse:* `retry_delay: Option<u64>` (`src/model.rs:815`) feeds `Duration::from_secs` directly at `src/runtime.rs:3729`, so a large value parks the run indefinitely; `loop_max_iterations` (`src/model.rs:821` → `src/runtime.rs:6096`) and `node.timeout` are likewise unbounded.

*Governing precedent:* `docs/issues/feature-tmux-panes-code-review-20260620-092605.md:63-67` resolved an identical unbounded-`u32` `maxConcurrent` finding with a runtime `clamp(1, MAX)` at the authoritative choke point, a named `MAX_PARALLEL_BATCH_CONCURRENT = 32` constant, **and** a UI clamp — reasoning explicitly that the runtime clamp is the decisive root-cause fix because it holds regardless of input source.
**Recommended Fix:** Apply the settled `maxConcurrent` remedy to `retry_count`: clamp in the runtime, bound at ingress, constrain the UI.
- Add `const MAX_NODE_RETRY_COUNT: u32 = 10;` in `src/model.rs` alongside the existing `MAX_*` constants. Pick the ceiling generously — a hard cap that is too tight will annoy authors who legitimately want ~20 retries.
- At `src/runtime.rs:3696`, use `node.retry_count.unwrap_or(0).min(MAX_NODE_RETRY_COUNT) + 1`. This is the load-bearing half: it holds for imported and legacy workflows that never pass through the API.
- Add a matching per-node check in `validate_workflow_input_bounds`, reusing the existing `ValidationIssue` error style so authors get a real message rather than silent coercion.
- Add `min="0" max="10"` to the retry-count input at `ui/src/features/editor/InspectorPanel.svelte:991-998`.
- Do **not** use `saturating_add(1)` alone: it converts the panic into `max_attempts = u32::MAX`, an unbounded retry loop that is strictly worse than current release behavior.
- Add regressions for a huge `retryCount` (clamped, run completes normally) and for the debug-overflow input specifically.
- Track as follow-up, not part of this fix: a general per-node numeric sweep covering `retry_delay`, `timeout`, and `loop_max_iterations`. `retry_delay`'s indefinite park is the worst of the family. The M-tier finding M10 already opens `validate_workflow_input_bounds` for node/edge caps and is the natural home for it.

#### Issue L12: Subflow cycle detection can collide the root workflow with a subflow of the same name
**Severity:** LOW
**File(s):** `src/model.rs:2205-2216` (`validate_subflow_call_cycles`), `:2240` (warning severity), `:2252-2280` (`collect_subflow_calls`), `:2288` (Tarjan), `:865` (`WorkflowV3.name`), `:886-889` (global subflow-name contract), `:2001` (`validate_subflow_catalog`); `src/api.rs:581` (`hydrate_saved_subflows`), `:736` (error-only filter); tests `src/model.rs:4178`, `:4544`
**Description:** Severity rationale: LOW — warning-only and non-blocking; a spurious banner that mis-labels the root as a subflow, with no masking risk since merging only adds edges.

`validate_subflow_call_cycles` derives the root vertex key from `workflow.name`, falling back to the literal `"__root__"` (`src/model.rs:2206-2211`), then keys every subflow vertex by its catalog name (`:2214-2215`) in the same flat `BTreeMap`; `collect_subflow_calls` appends out-edges via `graph.entry(name).or_default()` (`:2257`, `:2280`), so equal names merge two vertices into one. Nothing forbids a root `name` equal to a catalog key — `WorkflowV3.name` is free-text `Option<String>` (`:865`) and `hydrate_saved_subflows` inserts under storage name into the same namespace (`src/api.rs:581`). The result is a "Subflow call cycle detected among subflows {…}" warning for an acyclic graph, mis-labeling the root as a subflow; the inverse holds too, where a blank root name collides with a catalog entry literally named `__root__`. Impact is bounded: the issue is `severity: "warning"` (`:2240`) and `src/api.rs:736` filters only `error`, so no workflow is rejected, and in the dominant hydration path (root named after a saved catalog entry whose body *is* the root) the merge is semantically correct and the reported recursion real.
**Recommended Fix:** Replace the `String` graph key with a discriminant that separates the two namespaces structurally.
- Introduce `enum Vertex { Root, Subflow(String) }` (or an equivalent `(bool, String)`) as the key type for the call graph in `validate_subflow_call_cycles` (`src/model.rs:2205`), `collect_subflow_calls` (`:2252`), and the Tarjan pass (`:2288`), updating the `BTreeMap`/`BTreeSet` generics accordingly.
- Key the root as `Vertex::Root` regardless of `workflow.name`, and every call edge as `Vertex::Subflow(callee)`. This removes the `"__root__"` sentinel and its inverse collision entirely.
- Add a small formatter rendering `Vertex::Root` as the root's display name (or "root workflow" when `name` is absent) so the warning text at `:2240` stays readable and no longer mis-labels the root as a subflow.
- Confirm real recursion is still caught: a self-referential hydrated body yields `Subflow(X) → Subflow(X)` and must still warn.
- Add regressions for a root whose `name` equals a catalog key over an acyclic graph (must produce no cycle warning) and for a catalog entry literally named `__root__` under a blank root name. `warns_on_subflow_call_cycles` (`:4178`) and `recursion_cycle_warning_includes_depth_bound_in_message` (`:4544`) both use distinct names and cover neither.
