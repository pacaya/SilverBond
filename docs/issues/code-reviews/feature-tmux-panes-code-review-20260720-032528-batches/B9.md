#### Issue M1: Compound extraction silently widens inherited agent access
**Severity:** MEDIUM
**File(s):** `ui/src/lib/stores/workflowStore.svelte.ts:891-911` (`saveSelectionAsCompound`); `ui/src/lib/types/workflow.ts:278`; `ui/src/features/editor/GraphEditor.svelte:232-234` (trigger); `ui/src/features/editor/InspectorPanel.svelte:509`; `src/runtime.rs:2763`, `:2774`, `:4831`; `src/model.rs:~264` (`merge!`); `src/driver.rs:405-412`, `:615-617`, `:840-842`
**Description:** Severity rationale: MEDIUM (top of band) — a pure editor gesture silently revokes a restriction the author explicitly set, with no prompt, diff, or warning; mechanically certain rather than conditional, and it fails toward *wider* access.

The `subflowDoc` object literal at `ui/src/lib/stores/workflowStore.svelte.ts:891-911` copies `cwd: active.cwd` but has no `agentDefaults` key and hardcodes `useOrchestrator: false`; `WorkflowDocument.agentDefaults` is optional (`ui/src/lib/types/workflow.ts:278`), so nothing type-flags the omission. Subflow scope is authoritative at dispatch — `agent_defaults: active_workflow.agent_defaults.clone()` (`src/runtime.rs:2774`, batch twin `:4831`) — so with no subflow defaults and no node override, `merge!(access_mode).unwrap_or_default()` (`src/model.rs:~264`) yields `AccessMode`'s `#[default] Execute` (`src/driver.rs:405-412`), producing skip-permissions for Claude (`src/driver.rs:615-617`) and `--full-auto` for Codex (`:840-842`). The loss is not limited to `accessMode`: `model`, `maxTurns`, `maxBudgetUsd`, `autoApprove`, `systemPrompt`, and `orchestrator` all merge through the same macro, and `useOrchestrator: false` is a second silent semantic change for orchestrator-enabled workflows. The trigger is a bare `prompt()` at `GraphEditor.svelte:234` with no preview or warning, and the store leaves selection on the compound node rather than drilling in, so the user never sees the new scope's config.

*Governing precedent:* `docs/issues/feature-tmux-panes-code-review-20260620-092605.md:92-94` M5 (FIXED) deliberately made the backend source `cwd`/`use_orchestrator`/`agent_defaults` from `workflow_for_cursor` rather than the root, ruling explicitly: "For `cwd`, inherit root when the subflow's `cwd` is empty … **keep strict per-scope values for `agent_defaults` and `use_orchestrator`**." That ruling is why `cwd` is copied here and defaults are not, is re-ratified at `...20260716-003531.md:204`, and is guarded by the passing test `subflow_dispatch_uses_subflow_scoped_cwd_defaults_and_orchestrator` (`src/runtime.rs:10453-10530`). The fix therefore belongs in the UI extraction path, not in the runtime. No prior finding covers compound extraction's failure to populate the new scope; the ~25 existing compound tests (`ui/src/lib/stores/workflowStore.test.ts:259-967`) assert only graph/prompt/variable rewiring.
**Recommended Fix:** Populate the generated subflow with the active workflow's effective configuration at extraction time.
- In the `subflowDoc` literal, add `agentDefaults: structuredClone($state.snapshot(active.agentDefaults))` when present, and set `useOrchestrator: active.useOrchestrator` rather than hardcoding `false`.
- **Do not copy `goal`**, contrary to the original fix text: `goal` is a per-scope prompt-context string (`workflow_goal: active_workflow.goal`, `src/runtime.rs:2763`), not a safety control, and copying the parent's goal into a reusable subgraph is semantically wrong. Leave `goal: ""`.
- Add a store-level regression that extracts a node under `agentDefaults.claude.accessMode = "read_only"` and asserts the generated child retains it; add a companion assertion for `useOrchestrator: true`.
- Accept the snapshot semantics: later parent edits will not propagate to the extracted child. That divergence is the model M5 already established for subflow scope and is not a defect of this fix.

#### Issue M5: A new run can wait for the pane selected in the previous run
**Severity:** MEDIUM
**File(s):** `ui/src/lib/stores/workflowStore.svelte.ts:994-1001` (`beginRunStream`), `:1007-1018` (`resetRun`), `:1035-1044` (`setRunObservability`), `:1061` (`applyRunEvent`); `ui/src/app/AppShell.svelte:147`, `:156`, `:202`, `:211`, `:220`; `ui/src/features/runtime/PaneTerminal.svelte:149`, `:184-194`; `src/api.rs:60`, `:449-451`, `:1251-1265`, `:1281-1295`; `src/runtime.rs:1171-1194`, `:1385`
**Description:** Severity rationale: MEDIUM (lower band) — *lowered*: a dead terminal with a visible workaround, not data loss; the trigger needs a resume/restart or manual pane pick rather than every run, and it self-heals when the same node runs again.

`AppShell.svelte:202` starts every run, resume, and restart via `store.beginRunStream()` (`workflowStore.svelte.ts:994-1001`), which only aborts the SSE controller, bumps `runEpoch`, and installs a new controller — it touches neither `selectedPane` nor `runObservability`. Only `resetRun()` (`:1007-1018`) clears them, and it is called solely from `openWorkflow` (`AppShell.svelte:147`) and `handleCreate` (`:156`). `setRunObservability` (`:1035-1044`) has exactly two branches — `panes?.length === 1` and `panes && panes.length > 1` — with no empty/absent case, and `src/api.rs:449-451` omits the `panes` field entirely when the list is empty while `src/runtime.rs:1385` spawns workflow execution *after* `start_run` returns, so a fresh run's kickoff response never carries panes. A stale exact pane key therefore survives into the new run and reaches `streamPane(activeRunId, pane, …)` at `PaneTerminal.svelte:149`, leaving the terminal blank while the backend holds the request pending.

*Corrections to the original write-up:* the backend **does** re-resolve on every pane-registration notify (`src/api.rs:1281-1295`, `src/runtime.rs:1171-1194`) — but only for the requested key, so the failure needs the new run never to register a pane under that key, and re-running the *same* workflow node typically self-heals. The hold is also not a guaranteed 120 s: `run_still_awaiting_pane` (`src/api.rs:1251-1265`) returns `PaneUnavailable` immediately once the run reaches a terminal status, bounding it at min(run duration, 120 s). Reachability is narrower than "the common case": `selectedPane` can only *become* a stale exact key via a resume/restart kickoff that did return panes (`AppShell.svelte:211` is the only `setRunObservability` call site, and observability is never refreshed mid-run) or via a manual dropdown pick (`PaneTerminal.svelte:188`) — a plain Run→Run sequence never auto-populates it. Finally, the claim that this supersedes a "separately-reported stale-attach-command symptom" is unsupported: no such report exists anywhere in `docs/`.

*Prior history:* this is exactly the hole a prior fix knowingly left. `docs/issues/code-review-20260608_part_4_of_4.md:127` R3-6 (FIXED) added the reset to `resetRun()`/`setWorkflow()`; `docs/issues/feature-tmux-panes-code-review-20260620-092605.md:95` M6 (FIXED) covered the same class but its fix note at `:99-103` **explicitly dropped the "reset at run start/resume" half**, keeping only the membership check. `...20260716-003531.md:212` M9 then introduced `beginRunStream` as cancellation-only by design, and S8 (`:645`) routed all three run entry points through it instead of `resetRun`. The 120 s pending hold is itself a deliberate choice over error-closing (`...20260705-074320.md:90`, M4 FIXED).
**Recommended Fix:** Clear run-scoped selection state where the run lifecycle begins.
- In `beginRunStream` (`ui/src/lib/stores/workflowStore.svelte.ts:994-1001`), set `selectedPane = "active"` and `runObservability = null`, so all three lifecycle entries through `AppShell.svelte:202` start from the sentinel. Have `resetRun` delegate to that shared clearing rather than duplicating it.
- This is effective because `"active"` re-resolves dynamically as panes register (`src/runtime.rs:1180-1184` single-pane, `src/api.rs:2008-2021` candidate fallback), unlike a stale exact key.
- Accept the tradeoff: resuming or restarting the *same* run now discards a deliberate user pane choice. The dropdown at `PaneTerminal.svelte:184-194` remains available to re-select.
- Add the missing cross-run regression: kickoff payload with no `panes`, first registered pane under a different key, asserting the socket opens against `"active"`. `workflowStore.test.ts:974-1024` currently covers only the 1-pane, >1-pane, `resetRun`, and `setWorkflow` paths.
- Worthwhile separate follow-up (not part of this fix): `runObservability` is never refreshed after kickoff, so the pane dropdown and attach command also go stale mid-run. Refreshing it from `applyRunEvent` as panes register would address that independently.
