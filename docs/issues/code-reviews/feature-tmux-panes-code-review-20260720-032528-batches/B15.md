#### Issue L2: `send_socket_error_and_close` is never called
**Severity:** LOW
**File(s):** `src/api.rs:2144-2155` (the dead function), `:2032-2040` (`PaneWsFrame`), `:2111-2126` (`send_error_frame`), `:2128-2142` (`send_frame`), `:1075-1076`, `:1085-1086` (the two abort sites that replaced it), `:914-916`, `:1170-1176`, `:1107`, `:1317-1327`; `ui/src/lib/api/client.ts:458-460`
**Description:** Severity rationale: LOW — compiler-visible dead code with zero runtime or UX impact; the error paths it was written for are all already covered by `send_error_frame`.

`send_socket_error_and_close` builds a `PaneWsFrame { type: "error", seq, error }`, sends it as text, then sends `Message::Close(None)` — and takes the un-split `WebSocket`, which is why the current handler cannot call it. Commit `dac8d59` refactored `pane_stream_socket` to `socket.split()` and deleted both of its call sites, replacing them with `send_error_frame(&mut sender, …)` + `sender.close()` at `src/api.rs:1075-1076` and `:1085-1086`. `cargo check --all-targets` confirms the resulting warning verbatim: `function 'send_socket_error_and_close' is never used --> src/api.rs:2144:10`; there is no `#[allow(dead_code)]` and no test caller.

*Reframing:* the defect is an orphaned duplicate, **not** a missing feature or silently-closing error paths. Every abort path is already structured — auth fails before upgrade (`:914-916`), pane-context failure sends `client_message()` (`:1075`), subscribe failure sends `to_string()` (`:1085`), pane-EOF sends `"pane stream unavailable"` (`:1170-1176`) — and the only silent drops (`:1107`, `:1317-1327`) are client disconnects, which is correct. The frontend already handles the frame shape at `ui/src/lib/api/client.ts:458-460`, but `send_error_frame` is what produces it, so wiring the dead function in would change nothing observable.

*Provenance:* added live in `12ac692` with callers and cited as live in three prior reviews (`docs/issues/code-review-20260608_part_4_of_4.md:56`, `...20260620-092605.md:120`, `...20260705-074320.md:96`). No prior review requested it; it is refactor residue.

*Separate live item, not covered by this fix:* `20260620-092605.md:120` flagged a raw `to_string()` leak, and the successor at `src/api.rs:1085` still passes `&error.to_string()` while `:1075` uses `client_message()`. That inconsistency remains open and should be tracked on its own.
**Recommended Fix:** Delete `src/api.rs:2144-2155` outright. The function is a strictly inferior duplicate of `send_error_frame` (`:2111-2126`) + `send_frame` (`:2128-2142`) — it bypasses the `PANE_STREAM_SEND_TIMEOUT` backpressure guard, never advances `next_seq`, and takes an unsplit socket the handler no longer holds. Removal clears the warning with zero behavior change and keeps `send_error_frame` the single error-frame choke point, matching the existing `send_snapshot` / `send_data_frame` / `send_heartbeat` family. Do not wire it into the abort sites: that would manufacture a caller for a helper the `dac8d59` refactor deliberately superseded, and would either regress backpressure/seq handling or simply duplicate `send_error_frame`.

#### Issue L6: SSE `stream_run` replay/subscribe boundary has no sequence, so events can be both lost and duplicated
**Severity:** LOW
**File(s):** `src/api.rs:873` (`list_events`), `:874` (`subscribe`), `:~898` (`Lagged` arm); `src/runtime.rs:46-51` (`RuntimeEvent`), `:928-937` (`subscribe`), `:~905` (`broadcast::channel(512)`), `:1070` (registry removal), `:6571-6574` (`emit_event`); `src/storage.rs:433-450` (`list_events`); `ui/src/lib/api/client.ts:141-205`, `:170-180`; `ui/src/app/AppShell.svelte:213` *(pre-existing, unchanged from `development`)*
**Description:** Severity rationale: LOW — the loss window is microseconds at run start where only cosmetic events exist and no hang is reachable; it stays on the list because the same boundary already duplicates events today and the naive one-line reorder would make that worse.

`stream_run` snapshots the persisted event journal at `src/api.rs:873` before subscribing to the live broadcast at `:874`, so an event emitted between those two awaits reaches neither path. `RuntimeEvent` carries no id and no sequence (`src/runtime.rs:46-51`), the SSE frames emit no `id:` field, and the client parses only `data:` lines (`ui/src/lib/api/client.ts:170-180`) — no Last-Event-ID, no dedupe, no gap detection, no resync. The window is one mutex acquisition after a completed `spawn_blocking` DB read, and the stream opens exactly once immediately after `createRun`, so only the earliest cosmetic events (`run_start`, first `node_start`) can fall in it; state-bearing events (`approval_required`, `agent_interaction_required` — the only ones the client cannot reconstruct, as `ui/src` has no polling fallback) arrive far later. No terminal hang is reachable: losing `done` does not wedge the loop, since teardown is driven by `RecvError::Closed` when the registry entry is removed (`src/runtime.rs:1070`), and `AppShell.svelte`'s `finally` clears `running`/`approval` regardless.

*Corrections to the original write-up:* the endpoint is **not** legacy — it remains the primary run-event channel (`ui/src/lib/api/client.ts:141-205` → `AppShell.svelte:213` → `store.applyRunEvent`); the WebSocket path added by this branch carries pane bytes only. More importantly, the **converse defect already exists**: because `emit_event` appends before broadcasting (`src/runtime.rs:6571-6574`), an event appended before `list_events` but broadcast after `subscribe` is delivered **twice** today. Duplicates are a property of the current ordering, not a new cost introduced by fixing it.

*Larger sibling in the same function:* `Err(Lagged(_)) => continue` (`src/api.rs:~898`) silently discards an unbounded number of events across a 512-event backlog with no client signal and no resync. The pane WebSocket path handles `Lagged` correctly by forcing a snapshot resync; the SSE path does not.

*Prior history:* `docs/issues/feature-tmux-panes-code-review-20260620-092605.md:359` gave `stream_run` framing an explicit clean bill ("replay + `done` short-circuit + keep-alive correct"), and structurally identical replay/subscribe boundary findings on the pane path were lowered to LOW as cosmetic (`...20260716-003531.md:148-157`). The subscribe ordering itself was never raised.
**Recommended Fix:** Give events a monotonic sequence so the replay/subscribe boundary becomes well-posed, then subscribe → replay → dedupe.
- Attach a per-run monotonic sequence to `RuntimeEvent` (`src/runtime.rs:46-51`) — either by surfacing the persisted `run_events` rowid or by stamping an `AtomicU64` at emit time in `emit_event` (`:6571-6574`).
- Reorder `src/api.rs:873-874` to subscribe **first**, then replay the journal, then drain the already-buffered receiver discarding any event whose seq is ≤ the maximum replayed seq. Reordering alone is not acceptable: with no dedupe key, a duplicated `approval_required` would re-set `store.approval` after the user resolved it.
- Emit the sequence as the SSE `id:` field so the client can detect gaps independently of server-side correctness.
- Use the new sequence to fix the `Lagged` arm at `src/api.rs:~898`: instead of `continue`, signal the client to refetch `/api/runs/{id}/events` — an endpoint that already exists and is currently unused — mirroring the pane path's snapshot-resync discipline.
- Add regressions for an event emitted inside the replay/subscribe window (delivered exactly once) and for a lagged receiver (client receives a resync signal rather than silent loss).
