#### Issue H5: Nested splits lose the outer family's failure policy — a failed branch finalizes the run as Completed
**Severity:** HIGH
**File(s):** `src/runtime.rs:228` (`SplitFamilyState`), `:1927-1935` (`evict_idle_split_families`), `:5412`, `:5421-5431`, `:5428`, `:5525-5534` (`handle_split_node`), `:5941-5943` (`handle_terminal_cursor_status`), `:5957-5962` (sibling cancel), `:6254-6263` (`finalize_run`), `:5696-5705` (collector release); related `:5711`, `:5834-5852` (M9)
**Description:** Severity rationale: HIGH — silent success-on-failure with no backstop anywhere; an orchestration engine reporting a failed run as Completed is the worst defect class in this codebase.

`handle_split_node` removes the parent cursor from `active_cursors` (`src/runtime.rs:5412`) and inserts the new family with `member_cursor_ids: child_cursor_ids` only (`:5421-5431`), while children are pushed carrying `[…inherited, new]` family ids (`:5525-5534`) and are never added to the inherited families' member lists. Outer families thus reference only dead cursor ids, and `evict_idle_split_families` — whose retain predicate is "some `member_cursor_ids` entry is still in `active_cursors`", guarded only by `force_failed` (`:1927-1935`) — drops them while live descendants still hold their ids. On a later descendant failure, `handle_terminal_cursor_status` sets `fail_run = cursor.split_family_ids.is_empty()` → false (`:5941`), then the bare `if let Some(family) = …get_mut(family_id)` at `:5943` finds nothing and silently skips with no `else` and no warn; `finalize_run` (`:6254-6263`) sees no `force_failed` family and returns `RuntimeStatus::Completed`, and sibling cancellation (`:5957-5962`) never fires.

**No backstop exists:** the only run-failure paths for a failed node are `handle_terminal_cursor_status` (call sites `:4256`, `:4507`, `:4741`, `:5085`) and the abort path; collector release always constructs `NodeResult { success: true, … }` (`:5696-5705`) and merely counts failures into `parsed_output.summary`. The run genuinely finalizes Completed.

*Trigger, narrowed:* nested splits are legal — `src/model.rs:1710-1735` only forbids non-success edges out of a split and warns on fan-out < 2. The silent-success outcome requires the **outer** family's policy to be stricter than the inner one (`fail_fast_cancel`/`drain_then_fail` outer over `best_effort_continue` inner); a loop back to the same split produces the same stale ids but is benign, since the regenerated family carries an identical policy. Eviction is not rare — it also runs at the end of `release_collectors_if_ready` (`:5882`), invoked after every collector arrival (`:5646`) and every terminal cursor (`:5973`). Minimal repro: outer split `fail_fast_cancel` → A, B; A → inner split `best_effort_continue` → A1, A2; B → terminal. B's `finish_cursor` evicts the outer family; A1 then fails → Completed.

*Prior history:* this is a **correctness regression created by a prior fix**. `docs/issues/feature-tmux-panes-code-review-20260620-092605.md:181-189` M14 (FIXED) introduced eviction purely as a memory/write-amplification optimization, explicitly characterized as "never a correctness fault", proposing exactly the rule that causes this. Never previously reported or dismissed. **Shares a root cause with M9** — family membership is denormalized onto cursor ids that are destroyed and re-minted at control-flow transitions.
**Recommended Fix:** Make split-family liveness derived from cursors rather than denormalized onto the family, and fix M9 in the same change.
- Rewrite `evict_idle_split_families` (`:1927-1935`) to build the referenced set from `active_cursors.iter().flat_map(|c| &c.split_family_ids)` and retain any family present in it, keeping the existing `force_failed` guard.
- Remove `member_cursor_ids` from `SplitFamilyState` (`:228`) and its population at `:5428`. The eviction predicate at `:1932` is its only reader, so once liveness is derived it is pure duplication — and the two-sided invariant is what allowed the desync.
- Handle checkpoints persisted by the current build: `#[serde(default)]` on the removed field or a checkpoint-version bump, so in-flight runs deserialize.
- Add an `else` branch at `:5943` emitting `tracing::warn!` with the missing `family_id` and `cursor_id`, as a permanent invariant tripwire.
- Fix M9's collector-release fallback (`:5711`, `:5834-5852`) in the same change so it stops emitting a cursor with empty `split_family_ids`, which detaches a live cursor from its policy by the same mechanism.
- Add nested-split regressions: `fail_fast_cancel` outer over `best_effort_continue` inner with an inner-branch failure must finalize Failed and cancel siblings. No existing test covers nested splits — `split_spawns_collects_and_continues` (`:9697`), `split_and_collector_maps_evict_after_completion_without_restart` (`:9772`), `drain_then_fail_waits_for_siblings_before_failing_run` (`:11182`) and `fail_fast_cancel_stops_slow_siblings` (`:11237`) are all single-level.

#### Issue M9: Collector release with no live waiter fabricates a phantom cursor
**Severity:** MEDIUM
**File(s):** `src/runtime.rs:425-432` (`CollectorBarrierState`), `:1907-1919` (`reset_released_collector_barrier`), `:1998-2008` (`collector_barrier_scope`), `:2966`, `:4355-4357` (`complete_subflow_if_at_exit`), `:5632-5634` (sole `waiting_cursor_ids` append), `:5655-5664` (readiness), `:5684-5698` (summary), `:5706-5711`, `:5742-5748`, `:5834-5851` (phantom construction), `:5859`, `:5863-5864` (normal path), `:5910`, `:5911-5939`, `:5941`, `:5963`
**Description:** Severity rationale: MEDIUM (HIGH-leaning) — *raised*: in subflow scope it silently aborts the entire run and discards the subflow's results, and the trigger ("both branches of a 2-way split fail") is an ordinary flaky-agent outcome rather than an exotic authored shape.

`waiting_cursor_ids` is appended in exactly one place — `src/runtime.rs:5632-5634`, inside `handle_collector_entry`'s *live*-arrival path. `handle_terminal_cursor_status` (`:5911-5939`) records the arrival via `insert_collector_arrival`, never touches `waiting_cursor_ids`, and then deletes the cursor at `:5963`. Since barrier readiness at `:5655-5664` checks only `required_inputs ⊆ arrivals`, a barrier whose arrivals all came through the terminal path releases with an empty waiting list: `representative_cursor_id` falls back to `new_cursor_id()` (`:5706-5711`), `representative_state` is `None` (`:5742-5748`), and `:5834-5851` fabricates a `CursorState` with `split_family_ids: Vec::new()`, `call_stack: Vec::new()`, and `var_map: checkpoint.var_map.clone()` — the run-global map rather than the cursor-scoped map the normal path carries at `:5863-5864`. In subflow scope the barrier is keyed to the call frame (`collector_barrier_scope`, `:1998-2008`), so the release targets a subflow-local node id on a cursor with no `call_stack`; resolution runs against the root workflow, misses, and `:2966` emits `Node "…" not found — aborting`, setting `RuntimeStatus::Aborted` for the whole run. `complete_subflow_if_at_exit` returns `false` immediately (`:4355-4357`, cursor absent from `active_cursors`), so the frame is never popped and the parent `call` node receives nothing — regressing the already-fixed R1-6. In root scope the empty `split_family_ids` makes `:5941` compute `fail_run = true` on any later downstream failure, failing the run against a `BestEffortContinue` policy the normal path (`:5859`) would have honoured.

*Reachability, raised:* the minimal repro is the shape of the existing test `best_effort_continue_keeps_run_completable_after_branch_failure` (`:11128`) with `branch-a` also scripted to fail — split → two tasks → collector → after. `DrainThenFail` reaches it as well (`:5946` only sets `force_failed`; the run is not marked failed until `finalize_run`); `FailFastCancel` is largely shielded because `terminal_reason` is set and the main loop breaks. No existing test covers zero surviving branches — `:11128`, `:11182`, and `:11237` all keep one branch alive.

*Semantics, settled:* the collector builds a summary carrying `failed`/`timedOut`/`cancelled` counts and sets `success: true` (`:5684-5698`), and `BestEffortContinue` means continue — so downstream work **must** run even with zero survivors. Suppressing the cursor is therefore not a neutral half-measure.

*Relationship to H5:* **same edit site, distinct defect — partial overlap only.** H5's finalized fix covers the empty `split_family_ids`; it does **not** address the empty `call_stack` (subflow abort and lost frame) or the wrong `var_map`, and the root-scope half is not moot after H5 either. Land both together.

*Prior history:* no prior finding covers `waiting_cursor_ids` or the representative fallback. Adjacent FIXED items: R1-5 (barrier scoping by `frame_id`), R1-6 ("thread the correct node/`NodeResult` into the collector representative-cursor case" — which this bug defeats), H4/M14 (barrier reset and eviction), M19 (merge-key collisions). Nothing here was dismissed or deferred.
**Recommended Fix:** Carry a real cursor snapshot on the barrier and seed the representative from it instead of fabricating one.
- Add `representative_snapshot: Option<CursorState>` to `CollectorBarrierState` (`src/runtime.rs:425-432`), populated in `handle_terminal_cursor_status` from the `cursor` clone already taken at `:5910` before removal, and cleared by `reset_released_collector_barrier` (`:1907-1919`).
- At `:5834-5851`, build the released cursor from that snapshot — restoring `call_stack`, `var_map`, and `split_family_ids` — retaining `new_cursor_id()` only for the cursor id itself.
- Store a single snapshot rather than one per arrival to bound checkpoint growth, and define a deterministic selection rule when branches carry divergent `var_map`s (e.g. first terminal arrival wins); document that a snapshot may be stale if its branch mutated globals after capture.
- Land together with **H5**: both edit `:5834-5851` and share the `#[serde(default)]` / checkpoint-version bump, so M9 rides H5's migration at no extra cost.
- Do **not** simply skip the `active_cursors.push` when the waiting list is empty: that silently drops all post-collector work, contradicting both `BestEffortContinue` and the collector's own `success: true` contract, and leaves the parent `call` stalled.
- Add regressions: a 2-way split under `BestEffortContinue` where **both** branches fail must continue past the collector with the correct downstream node; the same shape inside a subflow must complete the frame and return results to the parent `call` rather than aborting; and a later downstream failure must be judged against the configured policy rather than failing the run.
