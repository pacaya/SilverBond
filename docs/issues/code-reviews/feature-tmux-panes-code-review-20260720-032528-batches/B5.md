#### Issue H6: Pane-stream process setup deadline is not cancellation-safe when descendants inherit pipes
**Severity:** HIGH
**File(s):** upstream `tmux-tools` `core/src/tmux.rs:194`, `:226-229`, `:242-248`; `src/api.rs:61` (`PANE_STREAM_SETUP_TIMEOUT`), `:1391-1409` (guarded prepare), `:1424-1432` (**unguarded** enable), `:1481`, `:1529-1532`; `src/tmux_exec.rs:66-77` (`run_as.command`), `:123-126` (`resolve_tmux_bin_with_timeout`); `Cargo.toml:28` (rev pin)
**Description:** Severity rationale: HIGH — carried by the unguarded enable path, which hangs a pane-stream task indefinitely; every timeout on any path also permanently leaks a blocking-pool thread and an orphan process. The prepare path alone would be MEDIUM.

`command_output_with_timeout` cannot honor its deadline when a descendant inherits stdout/stderr: on deadline it runs `child.kill(); child.wait(); join_reader(stdout); join_reader(stderr)` (`core/src/tmux.rs:226-229`), where `read_pipe` is `read_to_end` (`:242-246`) and `join_reader` is an unbounded `handle.join()` (`:248`). `Child::kill` is `libc::kill(pid, SIGKILL)` against a single pid, so any surviving descendant holding the inherited write end withholds EOF forever. SilverBond hits this on three paths: the traversal probe `ensure_run_as_can_traverse_root` (`src/api.rs:1532`), the `pipe-pane` enable (`:1481` via `:1424-1432`), and `resolve_tmux_bin_with_timeout` (`src/tmux_exec.rs:126`). Reachability is ordinary, not pathological: `run_as.command` is operator-arbitrary (`src/tmux_exec.rs:66-77`), `resolve_tmux_bin` runs `<prefix> zsh -lic …` where an interactive rc that backgrounds anything holds the pipe, and `sudo` forks-and-waits whenever PAM session/timestamp cleanup applies, leaving the exec'd `tmux` alive after the parent is killed.

*Correction to the original write-up — the two consequences differ and must not be conflated:* the **prepare** path *is* wrapped in `tokio::time::timeout_at` (`src/api.rs:1395-1409`, with a comment at `:1391-1394` acknowledging detachment), so the caller returns within 6 s and the cost is a permanently leaked blocking-pool thread plus an orphan process. The **enable** path at `:1424-1432` is `.await`ed with **no** outer timeout — only the budget handed to the broken primitive — so a stuck drain hangs that pane-stream task forever. `PANE_STREAM_SETUP_TIMEOUT` is a real bound for prepare and no bound at all for enable. Mitigating: with `use_pty` (sudo ≥ 1.9.14 default) the command's stdout is a pty rather than the pipe; and `start_pane_stream` is per-websocket-connection (`:1951`), so leakage marches toward the 512-thread blocking pool only across many failures.

*Scoping correction:* `tmux-tools-core` is `git+https://github.com/pacaya/tmux-tools.git?rev=69173d1` (`Cargo.toml:28`) — **the maintainer's own repository**, so the "external dependency, not editable in this repo" precedent recorded at `20260716` H3 / R2-1 no longer binds. Upstream change also has precedent: `20260620` M15/M7 landed the timeout helper itself upstream. Related: `20260716` M18 fixed an earlier uncancellable-setup hang by splitting prep from enable — that split is what left the enable path unguarded.
**Recommended Fix:** Repair the primitive upstream so the deadline holds regardless of process topology, then bump the pin.
- In `command_output_with_timeout`, set `command.process_group(0)` at spawn and, on deadline, `libc::kill(-pgid, SIGKILL)` to kill the entire group rather than the single child. **Trap to avoid:** `std::process::Command` does not create a new process group by default, so issuing a group kill without `process_group(0)` would signal SilverBond itself.
- Additionally, on deadline `drop` the reader handles instead of `join`ing them, so the helper returns by its deadline even if a descendant escaped the group via its own `setsid`. Group-kill alone leaves the unbounded join; non-joining drain alone leaves the orphan process and its thread.
- Bump the `tmux-tools` rev pin in `Cargo.toml:28` to the fixed revision; this is a coordinated two-repo change.
- Add a regression using a run-as wrapper that forks a child inheriting stdout/stderr and delays the tmux command; assert the helper returns within its deadline and that no reader thread remains. Note that nine tmux/socket tests are EPERM-inconclusive under sandbox, so the test must not depend on real socket operations.
- Consider also wrapping the enable path at `src/api.rs:1424-1430` in `tokio::time::timeout_at(setup_deadline, …)` mirroring `:1395`, as defense in depth against any future primitive regression.

#### Issue M12: A stale pane-stream task's teardown disables a freshly established `pipe-pane`
**Severity:** MEDIUM
**File(s):** `src/api.rs:1550-1564` (`stop_pane_stream`, unscoped `pipe-pane`), `:1963` (teardown call), `:1448` (setup-error teardown call), `:1553` (`timeout` over `spawn_blocking`), `:1805-1832` (`subscribe_pane_stream`, `drop(streams)` at `:1832`), `:1834` (`spawn_pane_stream_task`), `:1868-1875` (`sender.closed()` arm), `:1952-1972` (task lifetime), `:1416` (lifecycle marker), `:1704-1716`, `:1756-1758`, `:1886`, `:1162`, `:1169-1173` (`stream_chunks_seen` gate), `:60` (`PANE_STREAM_PENDING_TIMEOUT`); `src/app.rs:223-240` (`unsubscribe`), `:232`, `:251`, `:258-271` (`same_channel` / `remove_terminal_sender`); tests `src/api.rs:3815`, `:4440`
**Description:** Severity rationale: MEDIUM — a visibly dead terminal that self-heals on the next reconnect, with no data loss and no security impact; held below HIGH because trigger 2 is narrow, but the window for trigger 1 is wide until H6 lands.

`stop_pane_stream` runs `tmux::run(&["pipe-pane", "-t", &pane_target])` with no command and no owner check (`src/api.rs:1550-1564`); tmux has one pipe per pane and no way to query its command, so this closes whatever pipe is installed. Nothing serializes setup per `PaneStreamKey` — `subscribe_pane_stream` holds the registry mutex only across the lookup/insert and explicitly `drop(streams)` at `:1832` before spawning the pump at `:1834` — while the registry entry is removed at refcount 0 (`src/app.rs:235-236`) even though the task owning the tmux pipe lives on to `:1963`. A reconnect therefore creates a **second** owner for the same key: task #1's `sender.closed()` arm (`:1868-1875`) fires immediately, and its unconditional teardown at `:1963` (or the setup-error path at `:1448`) disables task #2's pipe. The writer then hits EOF, emits its `.` marker (`:1416`) → `terminated` (`:1704-1716`) → `Ok(0)` (`:1756-1758`) → `Terminal` (`:1886`) → `RecvError::Closed` (`:1162`); the user sees `"pane stream unavailable"` when no bytes had yet flowed, and a silent socket close when they had (the frame at `:1173` is gated on `!stream_chunks_seen` at `:1169`). A second, narrower trigger: `tokio::time::timeout` at `:1553` wraps `spawn_blocking`, and dropping the `JoinHandle` **detaches** rather than cancels, so the closure can still fire its unscoped `pipe-pane` after a reconnect installed a replacement. Teardown is the one place in the codebase that skips the `same_channel` ownership discriminator already used at `src/app.rs:232`, `:251`, `:266`. No test spawns two generations for one key (`:3815` covers a single generation; `:4440` is registry-level only).

*Prior history:* `docs/issues/code-review-20260608_part_3_of_4.md:83-85` filed this exact hazard against the upstream `PaneStream::drop` ("bare `pipe-pane -t <pane>` toggle-off, no owner guard") and fixed it with the broadcast registry + refcount — that removed *concurrent viewers* as a trigger but never made teardown owner-scoped. M12 is the surviving remainder. `...20260716-003531.md:536-546` M18 (FIXED) did **not** create this: its own description at `:540` already records the reconnect-clobber and left it in place.

*Relationship to H6:* **disjoint at line level; sequence H6 first.** H6 targets `:1391-1409`, `:1424-1432` and upstream `core/src/tmux.rs`; M12 targets `:1550-1564`, `:1963`, `:1448`, `:1805-1842`. Neither subsumes the other and there is no hard dependency, but H6's unguarded enable lets task #1 sit in setup indefinitely, which massively widens trigger 1 — and H6's fix caps that window at 6 s and makes trigger 2's late fire far less likely. M12 does nothing for H6's leaked thread and orphan process.
**Recommended Fix:** Make pipe ownership structural by giving the registry a single-owner lifecycle, so teardown can never target another generation's pipe.
- Stop removing the entry at refcount 0. Have `unsubscribe` (`src/app.rs:223-240`) mark the entry `draining` instead, and let only the owning task remove it via `remove_terminal_sender` (`:258-271`).
- On reconnect, a `subscribe_pane_stream` that finds a draining entry **revives** it — cancelling the drain and reusing the live sender and pipe — rather than inserting a second entry. Where revival is not possible, await the owner's exit before inserting.
- Gate revival so a genuinely terminal stream (lifecycle marker observed, `terminated` set at `:1704-1716`) is never resurrected; those must fall through to a fresh setup.
- Give the pump loop an explicit cancel/drain signal rather than relying solely on `sender.closed()` (`:1868-1875`), and add the `draining` state to `PaneStreamEntry`.
- With a single owner per key by construction, `stop_pane_stream` (`:1550-1564`) is only ever reached by the pipe's owner; no generation token and no second key-indexed map are needed.
- Land **after H6**, which edits adjacent lines and shrinks this bug's window.
- Add the missing two-generation regression: disconnect during setup, reconnect, and assert the first task's exit does not issue a `pipe-pane` against the second generation's pane, and that a fast reconnect reuses the existing pipe rather than re-running the 6 s setup. Note that tmux/socket tests are EPERM-inconclusive under sandbox, so prefer the fake-tmux harness.
