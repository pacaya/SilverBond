#### Issue L11: `migrate_output_schema` misclassifies real JSON Schemas as legacy and corrupts them
**Severity:** LOW
**File(s):** `src/model.rs:325-352` (`migrate_output_schema`), `:806-811` (`deserialize_output_schema` serde hook), `:973`, `:981` (`normalize_workflow_value`), `:3852-3946` (legacy-shorthand tests), `:3885-3910`; `src/api.rs:520-522` (save), `:544`, `:721`; `src/storage.rs:333`, `:335-343` (`get_run` CAS write-back), `:851`, `:871`, `:880-886`, `:943`, `:1053` (`backfill_legacy_tmux_sessions` precedent); `src/runtime.rs:3670` (`json_schema = None`), `:4026`; `src/driver.rs:895-925` (`schema_to_prompt_hint`); `docs/workflow-schema.md:392`
**Description:** Severity rationale: LOW — the trigger is narrow and the schema currently feeds nothing but a prompt hint, so there is no execution or validation breakage; it stays on the list because the loss is permanent user data and it must land before or with M14.

Legacy detection is `!obj.is_empty() && !obj.contains_key("type") && obj.values().all(|v| v.is_string())` (`src/model.rs:325-352`), which sniffs format structurally rather than by version. A genuine schema such as `{"$ref":"#/defs/X"}` or `{"$schema":"…","$id":"…"}` satisfies it and is rewritten to `{"type":"object","properties":{"$ref":{"type":"#/defs/X"}},"required":["$ref"]}`. Because the conversion lives in a serde `deserialize_with` on the `output_schema` field (`:806-811`), it fires on **every** deserialization via `normalize_workflow_value` (`:973`, `:981`) — it is not gated on `migrate_workflow_value_to_v4` at all. The corruption is then persisted twice over: `save_workflow` normalizes and writes the migrated document over the user's `.json` (`src/api.rs:520-522` → `src/storage.rs:880-886`), and `get_run` CAS-writes the normalized workflow into `runs.workflow_json` (`src/storage.rs:335-343`). The original schema is destroyed with no backup.

*Corrections to the original write-up:* the trigger is narrower than "any real schema" — only top-level objects whose values are **all** strings qualify, so `$defs`, `properties`, `allOf`, `oneOf`, `enum`, and `items` carry object or array values and are already safe. The reviewer's proposed keyword list is therefore mostly dead weight; the live cases are `$ref`-only and `$schema`/`$id`/`title`/`description`-only schemas.

*Impact ceiling:* native schema passing is dead (`let json_schema = None;`, `src/runtime.rs:3670`) and the repo contains no JSON Schema validator, so nothing errors. The sole reader of `node.output_schema` is `wrap_prompt_for_json` → `schema_to_prompt_hint` (`src/driver.rs:895-925`), which emits a prompt line — a corrupted schema silently produces a nonsense hint such as `- $ref (#/defs/X, required)`. `decide_output_schema` (`src/runtime.rs:4026`) is constructed in memory and never deserialized, so it does not pass through this path; L9/M7 is independent.

*Prior history:* `docs/workflow-schema.md:392` documents the legacy `{"field":"type"}` shorthand and its auto-migration, pinned by tests at `src/model.rs:3852-3946`. No prior review has examined the heuristic.

**Sequencing — must land before or with M14.** M14 removes the `get_run` read-path write-back and moves canonicalization into a `Database::init()` startup pass; its fix text calls for this ordering. While the read-path write-back exists, any `get_run` can persist this corruption; after M14 the exposure narrows to the startup pass and the write path, both of which need L11 correct anyway. Land L11 first or in the same commit — otherwise M14's startup migration would mass-corrupt every stored run in a single pass.
**Recommended Fix:** Stop sniffing on the hot path — gate the migration to genuine imports, and make the predicate sound inside it.
- Move the conversion out of the `deserialize_output_schema` serde hook (`src/model.rs:806-811`) into `migrate_workflow_value_to_v4`, so it runs only when the incoming `version < 4` and never touches a canonical v4 document. This follows the existing one-time-migration precedent at `src/storage.rs:1053`.
- Inside the v3 branch, replace the negative heuristic with a positive test: treat the object as legacy only when **every** value is one of the seven JSON Schema primitive type names (`string`, `number`, `integer`, `boolean`, `object`, `array`, `null`) and every key is a plain identifier. `{"$ref":"#/defs/X"}` fails because `"#/defs/X"` is not a type name. A closed set cannot be broken by new JSON Schema keywords the way a blocklist can.
- Accept the behavior change: v4 documents hand-written with legacy shorthand will no longer migrate. That is the point — canonical v4 is the authored format.
- Retarget the legacy-shorthand tests at `src/model.rs:3885-3910` to a v3 fixture, and add regressions asserting that a v4 document carrying `{"$ref":"…"}` or `{"$schema":"…","$id":"…"}` round-trips through save/load byte-identical.
- Do not attempt a repair pass over already-corrupted rows; the trigger is narrow enough that detection would be less reliable than leaving them.

#### Issue M14: `get_run` is a read that can fail because of a write
**Severity:** MEDIUM
**File(s):** `src/storage.rs:294` (`get_run`), `:328-332` (false comment), `:333` (in-memory normalize), `:335-343` (read-path CAS), `:342` (`?`), `:180-190` (`upsert_run`), `:186` (INSERT), `:189-192` (duplicate false comment), `:985` (`ensure_dir`), `:992-994` (`configure_connection`: WAL, `synchronous=NORMAL`, 5 s `busy_timeout`), `:134`ff (`init`), tests `:1639-1692`, `:1745-1789`; callers `src/runtime.rs:1394-1397`, `:1437-1440`, `:1452-1455`, `src/api.rs:472`, `:1029`, `:1214-1216`, `:1259-1261`; normalization `src/model.rs:973`, `:325-352`
**Description:** Severity rationale: MEDIUM — the filed failure mode alone is LOW (both cited triggers are near-unreachable under WAL + a write-requiring startup), but two comments on a data-integrity path assert a startup upgrade that does not exist, and this write-back is what converts L11 from a transient in-memory bug into permanent on-disk workflow corruption.

`get_run` performs a write on the read path — a genuine CAS at `src/storage.rs:335-343` guarded by `WHERE run_id = ?2 AND workflow_json = ?3` — whose `?` at `:342` propagates through the `with_connection` closure into the returned `anyhow::Result`, so a write-side failure turns a successful read into `Err`. That maps to `RunControlError::Internal` in `resume_run` (`src/runtime.rs:1394-1397`) and `restart_from` (`:1437-1455`), `PaneContextError::Internal` at `src/api.rs:1214-1216` and `:1259-1261`, and a 500 at `src/api.rs:472` and `:1029`. The persistence is pure optimization: the in-memory `workflow` is already normalized at `:333` *before* the UPDATE, so if the write never lands, normalization simply re-runs on each read — nothing reads persisted-canonical-ness.

*Corrections to the original write-up:* both cited triggers are overstated to the point of being unreachable. `configure_connection` sets `journal_mode=WAL` with a 5 s `busy_timeout` (`:992-994`), so under WAL readers never block the writer and only writer-vs-writer contends in what is a single process with a pool — a >5 s busy is effectively impossible. The read-only-DB-file scenario is hypothetical: `Database::init()` unconditionally runs `CREATE TABLE`/migrations (`:134`ff), `with_connection` calls `ensure_dir` (`:985`), and WAL requires writable `-wal`/`-shm`, so a read-only file kills startup long before any `get_run`.

*Two defects the original write-up missed:* (1) the comment is not merely misleading — `:328-332` points to "H3's one-time startup upgrade" as the durable repair, and **no startup upgrade exists anywhere**; `workflow_json` is written only at `:186` (INSERT) and `:340` (this CAS), and the same false claim is duplicated at `:189-192` in `upsert_run`. (2) **This write-back is what makes L11 durable.** `migrate_output_schema` (`src/model.rs:325-352`) runs inside `normalize_workflow_value` (`:973`), i.e. inside this read path at `:333`, so the first `get_run` of a run whose node carries a real JSON Schema rewrites `workflow_json` in the DB with the corrupted form, destroying the original. Without the write-back, L11 is transient and in-memory only.

*Prior history — two prior fixes resolved into contradictory artifacts:* `docs/issues/feature-tmux-panes-code-review-20260705-074320.md:33-42` H3 (FIXED, HIGH) *introduced* this write-back ("`get_run` durably self-heals `workflow_json` via idempotent compare-and-swap so it stops re-migrating on every read"), but its fix text asked for a one-time **startup** upgrade and the implementation delivered on-load-only. `:288-294` L6 (FIXED, LOW) had explicitly *rejected* a read-path write-back, and its entire fix was documentation with "No logic change" — those are the two comments the shipped H3 code now contradicts.
**Recommended Fix:** Make reads pure by moving the upgrade to startup and canonicalizing on write — the design H3 specified and L6 documented.
- Add a migration step in `Database::init()` that scans `runs`, normalizes each `workflow_json`, and CAS-updates rows that differ. Startup is already a write context, so a failure there is honest and loud rather than surfacing as a failed read.
- Have `upsert_run` (`src/storage.rs:180-190`) store the normalized value at `:186`, so new rows are born canonical and nothing non-canonical is ever persisted.
- Remove the write from `get_run` entirely (`:335-343`), keeping the in-memory normalization at `:333` as insurance for rows written by an older binary.
- Rewrite both comment blocks (`:328-332`, `:189-192`) to describe what the code actually does. After this change L6's original invariant is true again, so the text can state it plainly.
- **Sequence L11 before or with this change.** While the read-path write-back exists, every `get_run` risks persisting L11's corruption; once reads are pure, the exposure drops to the startup pass and the write path, both of which L11's fix must be correct for anyway.
- Reconcile with the immutable-snapshot invariant covered by `stores_run_records` before changing `upsert_run`.
- Existing tests `get_run_persists_structurally_migrated_v3_workflow_as_v4` (`:1639-1692`) and `get_run_leaves_canonical_v4_workflow_unchanged` (`:1745-1789`) assert the read-path write-back specifically and must be rewritten to target the startup migration instead. Add a regression that a legacy v3 row is canonical after `init()` with no `get_run` call in between.
