### H2. Session registration lifecycle ignores its own success/failure signals (FINALIZED)
**Severity:** HIGH — an unkilled session plus its agent process leaks permanently and silently, unrecoverable by any later reaper pass; the same path carries `run_as` panes running as another user.
**Files:** `src/tmux_exec.rs:1205-1207` (`kill_tmux_session`), `:1209-1222` (`cleanup_panes`), `:517` (dropped register result); `src/storage.rs:464-473` (`register_tmux_session`), `:479-506` (`remove_tmux_sessions`), `:525` (`list_reapable_tmux_sessions`); `src/runtime.rs:6352-6371`, `:6374-6381`, `:6479`, `:6507-6510`, `:6517-6538`

A kill *rejected* by tmux therefore reports success. The reaper treats that `Ok(true)` as confirmation and calls `remove_tmux_sessions` (`src/runtime.rs:6517-6537`), deleting the only record that makes the session reapable; because the reaper attempts kills only on sessions it just confirmed live (`:6479`, `:6507-6510`), a nonzero exit there is almost certainly a genuine failure, so the delete is wrong in exactly the reachable case. `cleanup_panes` discards every result with `let _ =` while its caller computes `killed_sessions` from the target list *before* the kills run (`:6352-6355`), and `register_tmux_session`'s `false` return (runs row absent) is dropped at both `src/runtime.rs:6374-6381` and `src/tmux_exec.rs:517`. *Correction to the original write-up:* the `Ok(false)` warn arm at `src/runtime.rs:6538` is **not** dead code — `run` still returns `Err` on spawn failure and on the 5 s command timeout. It is unreachable only for tmux-level rejection.
**Fix:** Determine kill success by observing tmux state rather than trusting the kill's own result.
- After issuing the kill, probe `has-session -t <name>`; treat a nonzero exit as "session gone". Ignore the kill command's exit status entirely.
- Delete the DB registration only when the session is confirmed absent. Otherwise retain the registration and `warn!` with `run_id` and `session_name` so a later reaper pass can reconcile it.
- Change `cleanup_panes` to return per-target absent/present verdicts instead of `let _ =`, and compute `killed_sessions` (`src/runtime.rs:6352-6355`) from those verdicts rather than from the target list.

### H5. Nested splits lose the outer family's failure policy — a failed branch finalizes the run as Completed (FINALIZED)
**Severity:** HIGH — silent success-on-failure with no backstop anywhere; an orchestration engine reporting a failed run as Completed is the worst defect class in this codebase.
**Files:** `src/runtime.rs:228` (`SplitFamilyState`), `:1927-1935` (`evict_idle_split_families`), `:5412`, `:5421-5431`, `:5428`, `:5525-5534` (`handle_split_node`), `:5941-5943` (`handle_terminal_cursor_status`), `:5957-5962` (sibling cancel), `:6254-6263` (`finalize_run`), `:5696-5705` (collector release); related `:5711`, `:5834-5852` (M9)
**Description:** `handle_split_node` removes the parent cursor from `active_cursors` (`src/runtime.rs:5412`) and inserts the new family with `member_cursor_ids: child_cursor_ids` only (`:5421-5431`), while children are pushed carrying `[…inherited, new]` family ids (`:5525-5534`) and are never added to the inherited families' member lists. Outer families thus reference only dead cursor ids, and `evict_idle_split_families` — whose retain predicate is "some `member_cursor_ids` entry is still in `active_cursors`", guarded only by `force_failed` (`:1927-1935`) — drops them while live descendants still hold their ids. On a later descendant failure, `handle_terminal_cursor_status` sets `fail_run = cursor.split_family_ids.is_empty()` → false (`:5941`), then the bare `if let Some(family) = …get_mut(family_id)` at `:5943` finds nothing and silently skips with no `else` and no warn; `finalize_run` (`:6254-6263`) sees no `force_failed` family and returns `RuntimeStatus::Completed`, and sibling cancellation (`:5957-5962`) never fires.

**No backstop exists:** the only run-failure paths for a failed node are `handle_terminal_cursor_status` (call sites `:4256`, `:4507`, `:4741`, `:5085`) and the abort path; collector release always constructs `NodeResult { success: true, … }` (`:5696-5705`) and merely counts failures into `parsed_output.summary`. The run genuinely finalizes Completed.

*Trigger, narrowed:* nested splits are legal — `src/model.rs:1710-1735` only forbids non-success edges out of a split and warns on fan-out < 2. The silent-success outcome requires the **outer** family's policy to be stricter than the inner one (`fail_fast_cancel`/`drain_then_fail` outer over `best_effort_continue` inner); a loop back to the same split produces the same stale ids but is benign, since the regenerated family carries an identical policy. Eviction is not rare — it also runs at the end of `release_collectors_if_ready` (`:5882`), invoked after every collector arrival (`:5646`) and every terminal cursor (`:5973`). Minimal repro: outer split `fail_fast_cancel` → A, B; A → inner split `best_effort_continue` → A1, A2; B → terminal. B's `finish_cursor` evicts the outer family; A1 then fails → Completed.

*Prior history:* this is a **correctness regression created by a prior fix**. `docs/issues/feature-tmux-panes-code-review-20260620-092605.md:181-189` M14 (FIXED) introduced eviction purely as a memory/write-amplification optimization, explicitly characterized as "never a correctness fault", proposing exactly the rule that causes this. Never previously reported or dismissed. **Shares a root cause with M9** — family membership is denormalized onto cursor ids that are destroyed and re-minted at control-flow transitions.
**Fix:** Make split-family liveness derived from cursors rather than denormalized onto the family, and fix M9 in the same change.
- Rewrite `evict_idle_split_families` (`:1927-1935`) to build the referenced set from `active_cursors.iter().flat_map(|c| &c.split_family_ids)` and retain any family present in it, keeping the existing `force_failed` guard.
- Remove `member_cursor_ids` from `SplitFamilyState` (`:228`) and its population at `:5428`. The eviction predicate at `:1932` is its only reader, so once liveness is derived it is pure duplication — and the two-sided invariant is what allowed the desync.
- Handle checkpoints persisted by the current build: `#[serde(default)]` on the removed field or a checkpoint-version bump, so in-flight runs deserialize.
- Add an `else` branch at `:5943` emitting `tracing::warn!` with the missing `family_id` and `cursor_id`, as a permanent invariant tripwire.
- Fix M9's collector-release fallback (`:5711`, `:5834-5852`) in the same change so it stops emitting a cursor with empty `split_family_ids`, which detaches a live cursor from its policy by the same mechanism.
- Add nested-split regressions: `fail_fast_cancel` outer over `best_effort_continue` inner with an inner-branch failure must finalize Failed and cancel siblings. No existing test covers nested splits — `split_spawns_collects_and_continues` (`:9697`), `split_and_collector_maps_evict_after_completion_without_restart` (`:9772`), `drain_then_fail_waits_for_siblings_before_failing_run` (`:11182`) and `fail_fast_cancel_stops_slow_siblings` (`:11237`) are all single-level.

### H6. Pane-stream process setup deadline is not cancellation-safe when descendants inherit pipes (FINALIZED)
**Severity:** HIGH — carried by the unguarded enable path, which hangs a pane-stream task indefinitely; every timeout on any path also permanently leaks a blocking-pool thread and an orphan process. The prepare path alone would be MEDIUM.
**Files:** upstream `tmux-tools` `core/src/tmux.rs:194`, `:226-229`, `:242-248`; `src/api.rs:61` (`PANE_STREAM_SETUP_TIMEOUT`), `:1391-1409` (guarded prepare), `:1424-1432` (**unguarded** enable), `:1481`, `:1529-1532`; `src/tmux_exec.rs:66-77` (`run_as.command`), `:123-126` (`resolve_tmux_bin_with_timeout`); `Cargo.toml:28` (rev pin)
**Description:** `command_output_with_timeout` cannot honor its deadline when a descendant inherits stdout/stderr: on deadline it runs `child.kill(); child.wait(); join_reader(stdout); join_reader(stderr)` (`core/src/tmux.rs:226-229`), where `read_pipe` is `read_to_end` (`:242-246`) and `join_reader` is an unbounded `handle.join()` (`:248`). `Child::kill` is `libc::kill(pid, SIGKILL)` against a single pid, so any surviving descendant holding the inherited write end withholds EOF forever. SilverBond hits this on three paths: the traversal probe `ensure_run_as_can_traverse_root` (`src/api.rs:1532`), the `pipe-pane` enable (`:1481` via `:1424-1432`), and `resolve_tmux_bin_with_timeout` (`src/tmux_exec.rs:126`). Reachability is ordinary, not pathological: `run_as.command` is operator-arbitrary (`src/tmux_exec.rs:66-77`), `resolve_tmux_bin` runs `<prefix> zsh -lic …` where an interactive rc that backgrounds anything holds the pipe, and `sudo` forks-and-waits whenever PAM session/timestamp cleanup applies, leaving the exec'd `tmux` alive after the parent is killed.

*Correction to the original write-up — the two consequences differ and must not be conflated:* the **prepare** path *is* wrapped in `tokio::time::timeout_at` (`src/api.rs:1395-1409`, with a comment at `:1391-1394` acknowledging detachment), so the caller returns within 6 s and the cost is a permanently leaked blocking-pool thread plus an orphan process. The **enable** path at `:1424-1432` is `.await`ed with **no** outer timeout — only the budget handed to the broken primitive — so a stuck drain hangs that pane-stream task forever. `PANE_STREAM_SETUP_TIMEOUT` is a real bound for prepare and no bound at all for enable. Mitigating: with `use_pty` (sudo ≥ 1.9.14 default) the command's stdout is a pty rather than the pipe; and `start_pane_stream` is per-websocket-connection (`:1951`), so leakage marches toward the 512-thread blocking pool only across many failures.

*Scoping correction:* `tmux-tools-core` is `git+https://github.com/pacaya/tmux-tools.git?rev=69173d1` (`Cargo.toml:28`) — **the maintainer's own repository**, so the "external dependency, not editable in this repo" precedent recorded at `20260716` H3 / R2-1 no longer binds. Upstream change also has precedent: `20260620` M15/M7 landed the timeout helper itself upstream. Related: `20260716` M18 fixed an earlier uncancellable-setup hang by splitting prep from enable — that split is what left the enable path unguarded.
**Fix:** Repair the primitive upstream so the deadline holds regardless of process topology, then bump the pin.
- In `command_output_with_timeout`, set `command.process_group(0)` at spawn and, on deadline, `libc::kill(-pgid, SIGKILL)` to kill the entire group rather than the single child. **Trap to avoid:** `std::process::Command` does not create a new process group by default, so issuing a group kill without `process_group(0)` would signal SilverBond itself.
- Additionally, on deadline `drop` the reader handles instead of `join`ing them, so the helper returns by its deadline even if a descendant escaped the group via its own `setsid`. Group-kill alone leaves the unbounded join; non-joining drain alone leaves the orphan process and its thread.
- Bump the `tmux-tools` rev pin in `Cargo.toml:28` to the fixed revision; this is a coordinated two-repo change.
- Add a regression using a run-as wrapper that forks a child inheriting stdout/stderr and delays the tmux command; assert the helper returns within its deadline and that no reader thread remains. Note that nine tmux/socket tests are EPERM-inconclusive under sandbox, so the test must not depend on real socket operations.
- Consider also wrapping the enable path at `src/api.rs:1424-1430` in `tokio::time::timeout_at(setup_deadline, …)` mirroring `:1395`, as defense in depth against any future primitive regression.

### M10. `O(call_nodes × subflow_size)` validation blowup blocks a tokio worker (FINALIZED)
**Severity:** MEDIUM — mostly self-inflicted (a legitimate large workflow already hangs the UI for seconds on every validate) plus a local-process DoS; bounded by the loopback bind and the multi-worker runtime, but reachable with no unlock gate.
**Files:** `src/model.rs:944-960` (`WorkflowV3::graph`), `:1326-1363` (`validate_workflow_input_bounds`), `:1365` (`validate_graph_body`), `:1484` (per-node dispatch), `:2000-2021` (`validate_subflow_catalog`), `:2061`, `:2078-2083`, `:2149-2153`; `src/api.rs:168` (`require_same_origin_mutation`), `:546-548`, `:723-732`; `src/main.rs:21`
**Description:** `validate_graph_body` loops every node and dispatches each `Subflow`/`Call` to `validate_subflow_node_config` (`src/model.rs:1484`), which rebuilds the callee's entire graph via `subflow.graph()` (`:2061`) — three `HashMap`s over all its nodes and edges (`:944-960`) — then scans every callee node for terminals with `outgoing_for` (`:2078-2083`) and rebuilds a `BTreeSet` of its variables (`:2149-2153`). All of this is per call node, giving `Σ(call nodes) × |callee|`; `validate_subflow_catalog` (`:2000-2021`) re-runs `validate_graph_body` for each subflow, so calls nested inside subflows amplify further. Measured on a release build: 200 calls / 500-node subflow (97 KB JSON) = 132 ms; 400/1000 (196 KB) = 874 ms; 800/2000 (398 KB) = **5.09 s**. Both HTTP entry points run it inline on the async task with no `spawn_blocking` (`src/api.rs:548`, `:732` — the latter after a deep `clone()`), `hydrate_saved_subflows` runs *before* `enforce_workflow_input_bounds` (`:546`/`:547` and `:723`/`:731`), and the existing bounds count only subflows and call edges, never nodes (`src/model.rs:1326-1363`). No `DefaultBodyLimit` exists anywhere in `src/`; axum 0.8's `Json` default is 2 MB.

*Worse than the original write-up:* hydration is an **amplifier**. A ~400 KB payload of 4096 trivial call nodes — exactly the `MAX_SUBFLOW_CALL_EDGES` ceiling — pointing at a single **saved** 2000-node subflow pulls that body from disk and extrapolates to roughly **26 s of CPU per request**.

*Reachability, refined:* single-user desktop app bound to `127.0.0.1:3333` (`src/main.rs:21`) with no authentication anywhere; `require_same_origin_mutation` (`src/api.rs:168`) rejects header-less clients, blocking cross-site browser pages and naive `curl`. But that middleware is CSRF protection, not authn — any local process can set `Origin: http://localhost:3333` and pass — and `/api/validate-workflow` carries **no unlock gate**, unlike `create_run` (`:724`). The runtime is `#[tokio::main]` default (num_cpus workers), so a single request degrades rather than kills; a loop of them saturates every worker including the health endpoint.

*Prior history:* direct precedent in the same file. `docs/issues/feature-tmux-panes-code-review-20260705-074320.md:160-169` M10 (FIXED) addressed exponential subflow-cycle detection under the same threat framing, and its fix introduced `MAX_WORKFLOW_SUBFLOWS`/`MAX_SUBFLOW_CALL_EDGES` explicitly as "defense-in-depth … bounds V regardless of algorithm" — sized for that algorithm's V, with a node-count cap never considered. That review also observed the missing `spawn_blocking` and **deliberately declined it**, choosing to fix the algorithm instead. `...20260716-003531.md:307-316` S2 (FIXED) later closed a bounds bypass via nested catalogs. This review's own smells list files the same code as Feature Envy, proposing a `validate_call_against` method on the subflow type.
**Fix:** Make validation linear by precomputing per-subflow facts once, and bound total input after hydration.
- In `validate_workflow`, build a single `BTreeMap<&str, SubflowFacts>` where `SubflowFacts` holds the subflow's node-id set, terminal-node id list, and variable set.
- Thread that map through `validate_graph_body` and `validate_subflow_node_config` so each call node performs only string comparisons against precomputed sets, never rebuilding a graph. All borrows are immutable from one `&WorkflowV3`, so lifetimes stay trivial; prefer `SubflowFacts` over carrying whole `WorkflowGraph`s.
- Add a total node+edge cap to `validate_workflow_input_bounds` (`src/model.rs:1326-1363`) — suggested 50k nodes / 100k edges, roughly 25× the largest plausible authored workflow — and count it **after** hydration so the saved-subflow amplification path is covered.
- Do **not** wrap `validate_workflow` in `spawn_blocking`: it relocates the CPU burn onto the pool shared with every `src/storage.rs` DB call, so a flood would stall persistence instead of HTTP. The `20260705` review reached the same conclusion.
- This also resolves the Feature Envy smell filed against `validate_subflow_node_config`; consider expressing `SubflowFacts` as a method on the subflow type.
- Add a validation-cost regression (e.g. 800 calls × 2000-node subflow completing well under a fixed budget) and a test asserting the post-hydration cap rejects an over-large hydrated catalog.

*Verification notes:* the error-return path **is** covered (`execute_workflow_to_terminal` → `fail_workflow_after_error` → `finalize_run`, `:2878-2896`), so the finding's "outside `execute_workflow`'s covered path" wording is accurate. The existing unwind machinery is strictly inner: `catch_unwind` at `:5213` wraps a single parallel-batch item and `apply_join_result` (`:4119-4145`) handles `JoinError`/`is_cancelled` for child cursor tasks only — neither covers the top-level run task.

*Second hang path the original write-up missed:* `finalize_run` awaits `cleanup_terminal_active_panes` **before** `registry.clear` (`:6324-6325`), so a wedged tmux stalls the drain signal even when the run task is alive and healthy.

*Prior history:* not a regression, and not a previously accepted risk. `docs/issues/feature-tmux-panes-code-review-20260716-003531.md:275-287` L4 (FIXED) introduced `drained_token`, converting `abort_and_wait` from a `Notify` race to a latched token for lost-wakeup immunity; the unbounded await was accepted as correct *given a cooperative drain*. The panic/`JoinError` path was never considered there or in the `20260620`/`20260705` reviews.
**Fix:** Make every task-termination mode cancel the drain signal, and bound the await as defense in depth for the non-task stall.
- Replace the three bare `tokio::spawn` calls (`:1386`, `:1425`, `:1567`) with a supervisor that retains the `JoinHandle` and, on `Err(JoinError)`, calls `registry.clear(&run_id)`. `is_panic()` and `is_cancelled()` both land in `Err`, and `clear` is idempotent (`remove` returns `None` on the second call), so the normal path is unaffected.

This is not redundant with the supervisor: it is the only thing that rescues the `cleanup_terminal_active_panes` stall at `:6324-6325`, where the task is healthy but the signal is blocked.
- Choose the timeout generously relative to `cleanup_terminal_active_panes`' own tmux budget so a legitimately slow drain is never cut short, and `warn!` with `run_id` on expiry so a force-clear is always visible.
- Known remaining gap to note in the change, not solved here: on panic the registry is cleaned but the run's DB checkpoint is still left `Running`. Reconciling persisted status on `JoinError` is a separate concern.
- Add regressions for the panic path specifically: a run task that panics must leave no registry entry and must let a subsequent `resume_run` proceed rather than returning `AlreadyActive`; and `abort_and_wait` must return within its bound when the drain signal never arrives. `abort_and_wait_returns_when_the_run_drains_concurrently` (`:7665-7687`) covers only the cooperative drain and `:9516` only `finalize_run` clearing on persistence error — there is zero panic-path coverage today.

### L15. `restore_pending_approval` binds a restored approval to the wrong cursor (FINALIZED)
**Severity:** LOW — reachable only via a corrupt or hand-edited checkpoint, with no in-process path producing the required state; retained on the list because the failure mode is a silently bypassed human approval gate with a fabricated user-success result.
**Files:** `src/runtime.rs:3477-3494` (`restore_pending_approval`), `:3482` (empty-id first matcher), `:3484-3489` (unqualified `.or_else`), `:3505-3507` (emitted prompt), `:3413-3414` (`queue_approval`), `:3444` (`activate_next_approval` `remove(0)`), `:3462-3465`, `:2680`, `:2708`, `:2924` (wholesale clears), `:4605` (resolution reads the cursor's own `node_id`), `:4614-4643` (synthetic user result), `:4707-4712`, `:2303-2325` (`drop_inconsistent_pending_approval`), `:2189`, `:2267` (rehydration-minted cursors), `:2330` (`update_checkpoint_summary`), `:133-134` (`PendingApproval::cursor_id` serde), `:558-559` (`active_cursors` serde); test `src/runtime.rs:9567`
**Description:** `restore_pending_approval` resolves the persisted approval by cursor id, then falls back at `src/runtime.rs:3484-3489` to *any* `WaitingApproval` cursor with no `node_id` check. That cursor already owns its own `queued_approvals` entry (`:3414`), and nothing prunes it — the only removals are `activate_next_approval`'s `remove(0)` (`:3444`) and wholesale `.clear()` on abort/fail (`:2680`, `:2708`, `:2924`), with no `retain` anywhere in `src/`. The cursor is therefore resolved twice: once from the restored oneshot, then again after re-activation (`:3444` → `:3462-3465`), each time stamping an `agent: "user"`, `success: true`, `"[Approved by user]"` result (`:4614-4643`) onto the cursor's *then-current* node, because `handle_approval_resolution` reads the cursor's own `node_id` at `:4605` rather than `pending.node_id`. A human gate is bypassed and a fabricated approval result lands on an unrelated node.

*Reachability correction to the original write-up:* the fallback is **not** the legacy-checkpoint path. The first matcher at `:3482` already accepts any `WaitingApproval` cursor when `pending.cursor_id.is_empty()`, and legacy rows deserialize with an empty id (`#[serde(default, skip_serializing_if = "String::is_empty")]`, `:133-134`; `active_cursors` `#[serde(default)]`, `:558-559`), so they take the first branch. The `.or_else` fires only for a **non-empty but unmatched** id, and `queue_approval` sets `WaitingApproval` and pushes the queued entry in one synchronous block (`:3413-3414`) with no path removing such a cursor while `pending_approval` points at it — so no ordinary run, restart, or resume produces that state. Entry requires a corrupt, hand-edited, or partially-written DB row. This mirrors the same review's L10 reachability correction (`:661`).

*Pre-existing mismatch inside the fallback:* the emitted `approval_required` carries `pending.node_id`/`prompt` (`:3505-3507`) while resolution applies to the bound cursor's current node (`:4605`) — the user is shown node X and node Y receives the result.

*Prior history:* the fallback is **not** deliberate recovery behavior added by a prior fix — `git log -L3477,3494` traces it to the initial commit `d54da2f`. Qualifying it therefore reverses no prior decision, though it does soften the "surface loudly, drop rather than reconstruct" precedent recorded at `…20260620-092605.md:341` and re-ratified at `…20260720-032528.md:669-671`.
**Fix:** Qualify the fallback so it can only bind a cursor that provably owns the persisted approval, and fall through to the drop path otherwise.
- In the `.or_else` at `src/runtime.rs:3484-3489`, require both that `cursor.node_id == pending.node_id` and that the cursor has no entry of its own in `checkpoint.queued_approvals`. This keeps recovery working for the genuine case — a rehydration-minted cursor (`:2189`, `:2267`) whose `node_id` matches `pending.node_id` via `update_checkpoint_summary` (`:2330`).
- When no cursor satisfies both conditions, fall through to `drop_inconsistent_pending_approval` (`:3492` → `:2303-2325`) so the inconsistency is warned and surfaced rather than guessed at.
- Handle the ambiguous case explicitly: if more than one `WaitingApproval` cursor matches `pending.node_id`, do not pick one — fall through to the drop path and `warn!` with the candidate cursor ids.
- Fix the prompt/resolution mismatch in the same change: the `approval_required` emitted at `:3505-3507` must describe the node the resolution will actually apply to (`:4605`), not `pending.node_id`, so the two can never disagree once the fallback binds.
- Add regressions for the fallback branch, which has none today: a non-empty unmatched `cursor_id` with a node-id-matching idle cursor must bind and resolve exactly once; the same with a node-id mismatch must drop and warn; and a bound cursor must never be resolved a second time via `activate_next_approval`. `resume_warns_when_pending_approval_has_no_waiting_cursor` (`:9567`) exercises only the `:2286-2292` drop and never reaches `:3484`.
