### L4. No `concurrency` group: superseded runs are never cancelled (FIXED)

### L5. Cargo cache is write-once — `target/` freezes at the first run (dismissed: mechanism true, harm framing wrong; lock-keyed target cache is the idiom the brief delegates to)

**Severity:** LOW · **File:** `.github/workflows/rust-tests.yml:23-29` · **Source:** Claude (Codex DISAGREE)

Claude (CLAUDE-2, MEDIUM) argued that `actions/cache` only writes on a primary-key miss, so with a key invariant while `Cargo.lock` is unchanged, `target/` is saved once and then frozen while the branch moves on.

The mechanism claim is factually correct. The harm framing is not, and Codex's rebuttal is the stronger reading: the thing keyed on the lockfile is the *dependency* build, which is precisely what stays valid while the lockfile is unchanged. Claude's proposed per-SHA key would force a fresh multi-gigabyte save on every run — `target/` measures 2.3 GB here — against a 10 GB per-repo budget, which is worse than the status quo.

The brief delegates this explicitly: the job caches "in whatever way is idiomatic for the action set in use." The lock-keyed registry-plus-target shape is that idiom.

### L12. Raw `rustc -V` as a cache-key component, and silent degradation on capture failure (dismissed: character concern refuted; degradation is self-limiting)

**Severity:** LOW · **File:** `.github/workflows/rust-tests.yml:37` · **Source:** Claude round-2 (CLAUDE-13, conf 35)

Two parts, both dismissed.
