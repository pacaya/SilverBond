## CRITICAL

### C1. Legacy v2 workflows fail to deserialize — NodeKind config fields lack `#[serde(default)]` (FIXED)
**Severity:** CRITICAL — any persisted v2 decide/batch/subflow/call node saved without a config becomes permanently unloadable via `get_run`/`normalize_workflow_value`; unrecoverable hard failure on real data.
**Files:** `src/model.rs:593-608` (NodeKind variants), `src/model.rs:1008-1060` (migrate_v2_node_to_v3_kind), `src/model.rs:950` (from_value), `src/storage.rs:201` (get_run)
**Description:** The `NodeKind` variants `Decide`, `ParallelBatch`, `Subflow`, `Call` have required config fields with no `#[serde(default)]`. The v2 schema stored these as `Option<..>` with `skip_serializing_if = "Option::is_none"`, so a `None` config wrote no JSON field. `migrate_v2_node_to_v3_kind` carries a config across only when present (model.rs:1031-1039) — only Capture/Kill synthesize an empty-object `{}` fallback (model.rs:1049-1060). The migrated `kind` then omits e.g. `decideConfig`, and `serde_json::from_value` (model.rs:950) fails with `missing field decideConfig`, propagating through `normalize_workflow_value` → `get_run` (storage.rs:201) and `api.rs:333/357/473` so the entire affected workflow/run is un-loadable. Empirically reproduced: `{"type":"decide"}` fails, `{"type":"decide","decideConfig":{}}` succeeds.
**Fix:** Add `#[serde(default)]` to the four variant config fields (`decideConfig`, `parallelBatchConfig`, `subflowConfig`, `callConfig`) on `NodeKind`. The config structs already derive/impl `Default` (DecideConfig L347, BatchConfig L376, SubflowConfig L527), so absent fields deserialize to type defaults; existing `validate_*` paths still reject genuinely-invalid configs downstream. This is a type-level root-cause fix covering all four variants — notably ParallelBatch, which a bare empty-`{}` migration fallback cannot rescue (`BatchConfig` itself can't deserialize from `{}` since `itemsBinding`/`itemVar`/`bodyEntry` lack defaults).

### H1. Pane-stream refcount leak — `send_snapshot(...).await?` bypasses unsubscribe cleanup (FIXED)
**Severity:** HIGH — a failed post-subscribe resync permanently kills a pane for all future viewers in the process (not self-healing); tempered by needing the resync to error AND the leaking receiver to be the channel's last.
**Files:** `src/api.rs:602-603` (subscribe), `:612`/`:644`/`:667` (post-subscribe `send_snapshot?` early-returns), `:707-708` (skipped unsubscribe tail), `:818`/`:825` (pump `NoSubscribers`), `src/app.rs:96-105` (`remove_if_sender`), `:107` (`remove_terminal_sender`), `src/api.rs:1668` (test encoding the buggy behavior)
**Description:** Two independent defects. (1) On any `send_snapshot` failure at api.rs:612/644/667, `pane_stream_socket` returns via `?` and skips the only cleanup tail `drop(pane_receiver); unsubscribe(...)` at :707-708, leaking one refcount on the `PaneStreamEntry` (there is no Drop/scopeguard). (2) When the dropped receiver was the channel's last, the pump exits `NoSubscribers` (:825) and calls `remove_if_sender` (app.rs:96), which keeps the entry because refcount≠0 — leaving a live map entry whose pump task is dead. A later reconnect reuses that stale sender (`subscribe_pane_stream:776-778`) and gets a receiver on a channel nobody pumps, so the pane appears permanently dead to every future viewer until process restart. Resync errors are plausible in normal operation (slow-client backpressure resync at :644, pane closing mid-resync, lag bursts at :667).
**Fix:** Fix both defects. (a) Hold an RAII guard whose `Drop` calls `unsubscribe`, so every exit path — including the three `?` early-returns — decrements the refcount (unsubscribe is async, so drop via a detached task or blocking-lock). (b) Change the `NoSubscribers` branch to use `remove_terminal_sender` semantics (app.rs:107 — evict on sender match ignoring refcount) instead of `remove_if_sender`, so a pump that has exited never leaves a reusable-but-dead entry. Update the test at api.rs:1668 which currently encodes the buggy "keep entry when refcount≠0" behavior as expected, and re-validate the narrow concurrent-subscriber race under the registry lock.

### H2. Session-name collisions — `unique_session_name` keeps only the timestamp half of the UUID (FIXED)
**Severity:** CRITICAL — deterministic (not rare) for any `parallel_batch` started within a ~65s window (the common case); concurrent spawns fail silently at the spawn layer with no retry. `parallel_batch` is a core feature. Only named/reused-pane sessions bypass it.
**Files:** `src/tmux_exec.rs:2237-2244` (`unique_session_name`), `:1887-1906`/`:1888` (`spawn_pane` `new-session`, no `-A`), `src/runtime.rs:3964-3994` (`parallel_batch` JoinSet fan-out)
**Description:** `unique_session_name` builds `silverbond-{base}-{&suffix[..8]}` where `suffix = Uuid::now_v7().simple()`. The first 8 hex chars are the high 32 bits of the 48-bit ms timestamp — zero randomness, empirically constant across a ~65.5s window (the low 16 bits span 2^16 ms). `parallel_batch` fans items out concurrently with the same run-derived `base`, so concurrent spawns build identical `silverbond-run-<8hex>` names. `tmux new-session -d -s <name>` has no `-A`, so the duplicate fails; `run_checked_owned` returns `Err` with no retry, failing every concurrent spawn after the first. Any batch (or two unnamed concurrent `run_agent`/`spawn` nodes) started within ~65s reliably loses all-but-one item.
**Fix:** Format the session name with the full `simple()` UUID suffix (drop the `&suffix[..8]` slice) so the name carries the full 122 bits of entropy and is collision-proof, including same-ms bursts. NOTE: do NOT use `&suffix[..16]` — uuid 1.22 keeps its monotonic counter in the low bytes, so the first 16 hex barely vary and still collide ~998/1000 in same-ms bursts. Do NOT add `-A` to `new-session` — it makes a duplicate name attach to the existing session, silently merging two batch items into one pane (I/O corruption), which is worse than the failure.

### H3. `send_text` sends literal keys without a `--` separator — leading-dash text mis-parsed (FIXED)
**Severity:** HIGH — leading-dash input is common (flag-style answers, markdown bullets `- item`, diff lines `-removed`); each hard-fails or mis-sends a node. Tempered by failing loudly (node error) rather than silent state corruption.
**Files:** `src/tmux_exec.rs:2086` (`send_text` `send-keys` argv), callers at `:544-551` (execute_send), `:1316`/`:1456`/`:1651` (interaction / auto-respond replies)
**Description:** `send_text` (tmux_exec.rs:2085-2091) emits `send-keys -t <pane> -l <text>` with no `--` before `text`. tmux `send-keys` uses getopt parsing that does NOT terminate on `-l` — it keeps consuming option-looking tokens until the first non-option arg, so any `text` whose first char is `-` and matches a send-keys option letter (`-N`/`-R`/`-l`/`-M`/`-H` etc.) is parsed as a flag instead of sent literally. `text` is fully user/agent-controlled (Send node prompts, interaction-escalation and auto-respond replies) with no upstream sanitization. Such input makes `send-keys` error (`run_checked` → `Err` → node fails) or silently send the wrong keystrokes. (No shell-injection — the wrapper passes args via `execve`, not a shell; this is purely tmux's own arg parsing.)
**Fix:** Insert `--` before `text` in the argv: `["send-keys", "-t", pane, "-l", "--", text]`. This call is the shared `send_text` chokepoint, so the single unconditional edit protects every caller (Send nodes, interaction replies, auto-respond). `--` is tmux's documented end-of-options marker with zero behavior change for normal text. The only other send-keys site (line 2088, the literal `"Enter"` keyname) is unaffected.

### H5. `RegistryProfileDriver` has no `interaction_patterns` — registry agents hang on prompts (FIXED)
**Severity:** HIGH — any interactive registry agent run without a skip-permission profile reliably stalls a node to timeout on a benign permission prompt. Tempered by: destructive commands are still caught (inherited blocklist), and many registry profiles skip permissions. Shares its fix with H6.
**Files:** `src/driver.rs:679-730` (RegistryProfileDriver, no override), `:323-325` (empty trait default), `:329-331` (inherited destructive blocklist), `src/tmux_exec.rs:1308-1338`/`:1448-1491` (pattern-gated interaction blocks), `:1510-1515`/`:1541` (idle→TimedOut), `tmux-tools-core agents/mod.rs` (AgentSpec — no pattern field)
**Description:** `RegistryProfileDriver` never overrides `interaction_patterns()`, so it inherits the empty default `vec![]` (driver.rs:323-325); only Claude (468) and Codex (618) supply regexes. ### H7. Pane-stream WebSocket origin allowlist is fail-open when the `Origin` header is absent (FIXED)
**Severity:** MEDIUM — lowered from HIGH: the loopback-only bind (`127.0.0.1:3333`) is a hard boundary (no remote attacker), so exploitation needs a malicious local process or a DNS-rebinding/CSWSH chain. Would rise to HIGH if the bind ever became `0.0.0.0`/configurable or on multi-user hosts.
**Files:** `src/api.rs:546-575` (`pane_stream_ws`), `:552` (origin `if let` with no `else`), `:559` (`ws.on_upgrade`), `:577-582` (`is_allowed_origin`), `:600`/`:633` (snapshot/data frames), `:508` (SSE `stream_run`, no origin check at all), `src/main.rs:21` (loopback bind)
**Description:** `pane_stream_ws` enforces the origin allowlist only inside `if let Some(origin) = headers.get(header::ORIGIN)` with no `else` branch (api.rs:552), so a handshake with no `Origin` header skips the check and falls through to `ws.on_upgrade` (api.rs:559), streaming a tmux pane snapshot plus live data frames (api.rs:600/633) — raw terminal output that can echo secrets. Origin is the sole gate (no token/cookie/CSRF). Non-browser clients (curl/websocat) trivially omit `Origin`. The `127.0.0.1:3333` bind (main.rs:21) bounds exposure to local processes / DNS-rebinding vectors. Separately, the SSE `stream_run` endpoint (api.rs:508) has no origin check at all, so the fail-open surface is wider than this one handler.
**Fix:** Move the origin check into a single axum/tower middleware layer applied to both the pane-stream WS and the SSE `stream_run` endpoint, denying by default any handshake whose `Origin` is absent or not in the loopback/Tauri allowlist. Browsers always send `Origin` on WS/SSE handshakes, so the Svelte/Tauri UI is unaffected. This gives one deny-by-default source of truth across streaming routes so no future endpoint silently fails open. (If the bind is ever exposed beyond loopback, layer on a per-session capability token for real authentication — origin alone is locally spoofable.)

### M1. `streamPane` reconnects forever on a pre-open rejection — never surfaces "Pane unavailable" (FIXED)
**Severity:** MEDIUM — real user-visible perpetual "Reconnecting…" that never resolves to "Unavailable"; triggers are edge cases (server down, pane gone, or H7's origin 403). The loop is genuinely infinite (no total-attempt cap).
**Files:** `ui/src/lib/api/client.ts:321-325` (fast-close gate), `:204-211` (`scheduleReconnect`, no attempt cap), `:230/236` (`openedAt` set in `onopen`), `:260-261` (success reset), `:326-330` (giveup branch), `ui/src/features/runtime/PaneTerminal.svelte:48-51` (Reconnecting vs Unavailable labels)
**Description:** In `streamPane`, the fast-close counter at client.ts:321-325 only increments when `openedAt !== null`, i.e. only for sockets that opened then closed quickly. The UI never reaches the terminal "unavailable" state, leaving a perpetual "Reconnecting…" label (PaneTerminal.svelte:48) instead of "Unavailable" (:50). The pre-open path has zero test coverage (the giveup test always opens first).
**Fix:** Add a separate `consecutiveFailedConnects` counter incremented on any close where `openedAt === null`, with its own limit that drives the same giveup→"unavailable" path; reset it alongside `consecutiveFastCloses` on a successful open / first frame (client.ts:260-261). This cleanly separates "can't even connect" from "connects but unstable," each independently tunable, and guarantees the reconnect loop terminates and surfaces the terminal state. Add a test covering the pre-open close path.

**Files:** `src/api.rs:562` (unconditional WS-upgrade task spawn), `:768-801` (`subscribe_pane_stream` refcount dedup), `:781` (per-pane 256-slot broadcast channel), `:605`/`:707-708` (heartbeat + unsubscribe cleanup), `src/app.rs:83-94` (`PaneStreamRegistry`/unsubscribe), `:160-172`/`src/api.rs:58-91` (router — zero `.layer()` calls)
**Description:** Each pane-stream WS connection spawns a dedicated task (`api.rs:562`) holding one socket FD plus a broadcast `Receiver` for the connection's lifetime, and there is no `ConcurrencyLimitLayer`/semaphore anywhere in the router (`api.rs:58-91`, `app.rs:160-172` have no `.layer()` calls). Per-pane resources (the 256-slot channel + tmux pump at `api.rs:781`) are bounded by pane count and deduped via refcount (`api.rs:768-801`), but per-connection tasks/FDs grow with client count. Normal Close and broken connections self-reap (`unsubscribe` at `api.rs:707-708` + 5s heartbeat at `api.rs:605`), so unbounded growth requires a local client that answers heartbeats while opening many streams — a loopback-only, self-inflicted resource-exhaustion vector, not a crash.
**Fix:** Add a per-pane/per-run subscriber cap using the existing refcount machinery. This targets the root cause (per-connection growth) at the natural choke point that already counts subscribers, without a global layer that could starve other routes or other runs. A sane UI opens only a few panes per run, so the cap is invisible in practice; choose a generous default and consider a complementary global ceiling later if a client opening many distinct runs becomes a concern.

### L1. `Handle::block_on` inside `spawn_blocking` — codify the blocking-thread invariant (FIXED)
**Severity:** LOW — hardening/doc note only; the panic the original finding described is NOT reachable. `Handle::block_on` on a `spawn_blocking` (blocking-pool) thread is safe under every runtime flavor, including current-thread, so there is no live bug — only an undocumented invariant worth protecting against future relocation of the call.

### L2. Persistent-pane registration clears only on the kill path — orphaned pane on crash (FIXED)
**Severity:** LOW — confirmed leak but narrow: only persistent/reused (opt-in `ephemeral_session=false`/`continue_session_from`) panes leak, and only on hard crash (SIGKILL/panic-abort/OOM) before run-end cleanup; the orphan is a named session the user can manually `tmux attach`, and accumulation is bounded by crash-frequency × persistent-session count, not per-run.
**Files:** `src/tmux_exec.rs:980`/`:986-988` (kill-gated clear), `:1202`/`:1208-1210` (mirror), `:361-432` (`ActivePaneRegistration`, no `Drop`), `:1237-1247` (`should_kill_after`), `:2243` (`silverbond-*` name builder), `src/runtime.rs:542`/`:550` (in-memory `ActivePaneTarget` map, never persisted), `:5398` (`cleanup_terminal_active_panes`, graceful-only)
**Description:** `should_kill_after` (`tmux_exec.rs:1237-1247`) returns false for persistent/reused named sessions, so for those both `kill-session` and `active_pane.clear_key()` live only inside the kill branch (`:986-988`, mirrored `:1208-1210`) — intentional cross-run persistence. Graceful run-end (`cleanup_terminal_active_panes`, `runtime.rs:5398`) and abort handle normal exits, but none run on SIGKILL/panic-abort/OOM. In that crash window the in-memory registry (`runtime.rs:550`, never serialized to the DB) dies with the process while the `silverbond-*` tmux session — owned by the detached tmux server, a separate OS process — outlives it as a leaked resource. No startup or shutdown reaper exists anywhere. NOTE: a `Drop` guard does NOT run on SIGKILL or `abort()`, so it would not address the crash case this finding is about.
**Fix:** Persist the pane→run mapping and reap on restart. Serialize each session's `session_name` into the run checkpoint (`PersistedRun`), then on boot enumerate `tmux list-sessions`, match `silverbond-*` sessions against the persisted runs, and `kill-session` any whose run is in a terminal/non-live state. This is the only approach that both survives a hard crash (SIGKILL/abort, where a `Drop` guard never fires) and reliably distinguishes a persistent-awaiting-reattach session from a genuine orphan via persisted run state, reusing the existing checkpoint store. Define "stale" carefully (terminal run state, not merely "no in-memory key") and guard against killing sessions belonging to a concurrently-running second app instance sharing the same tmux server.

### L3. `numOrUndef` accepts `Infinity` (silent field drop) (FIXED)
**Severity:** LOW — silent loss, but requires pathological input: only `Infinity` via scientific-notation overflow (`"1e999"`) is reachable; the `NaN`/`"abc"` path is blocked by `type="number"` browser validation. Affects nine numeric config fields.
**Files:** `ui/src/features/editor/InspectorPanel.svelte:313-315` (`numOrUndef`) + its nine `type="number"` `oninput` call sites (RunAgent/Wait timeout/idleSeconds/readyStableSeconds, BatchConfig maxConcurrent, CaptureConfig lines, SubflowConfig maxDepth), `ui/src/lib/api/client.ts:29` (`JSON.stringify`)
**Description:** `numOrUndef` (`InspectorPanel.svelte:313-315`) is `return v !== "" ? Number(v) : undefined;` with no finite check, feeding nine numeric config `oninput` handlers. Scientific-notation overflow (`"1e999"`) yields `Infinity`, which the `?? 1`/`?? 10` guards do not rescue (`??` only coalesces null/undefined), so `JSON.stringify` (client.ts:29) serializes it to `null` and the field reaches the backend as null — silently dropping the user's value with no UI feedback. The `"abc"` → `NaN` path is unreachable because the inputs are `type="number"`, leaving `Infinity` as the only live trigger.
**Fix:** Add a finite check at the single chokepoint: `function numOrUndef(v: string): number | undefined { const n = Number(v); return (v !== "" && Number.isFinite(n)) ? n : undefined; }`. A non-finite value then becomes `undefined`, so the field is omitted from the serialized JSON (backend sees an absent field, applies its default) rather than sent as `null`. This covers all nine fields at once, preserves the backend contract (number-or-omitted, never null), and is low-risk.

### L4. `collector_id_from_barrier_key` — fragile string-joined barrier key (FIXED)
**Severity:** LOW — near-theoretical: the reviewer's stated trigger (collector_id with `:`) does NOT reproduce (the parse is greedy on the middle and recovers it intact). The genuine variant (scope = raw `call_node_id` with `:`, only when `frame_id` is empty) is doubly-gated and reachable only via hand-crafted import JSON, never through the UI.
**Files:** `src/runtime.rs:1384` (barrier key construct `{scope}:{collector_id}:{epoch}`), `:1393` (`collector_id_from_barrier_key` greedy-middle parse), `:1372` (`collector_barrier_scope`, falls back to raw `call_node_id` when `frame_id` empty), `:554` (sibling `:`-join assumption), `src/model.rs:1111` (`validate_workflow` — no node-id charset check)
**Description:** The barrier key is `{scope}:{collector_id}:{epoch}` (`runtime.rs:1384`) and `collector_id_from_barrier_key` (`:1393`) recovers the collector id as the greedy middle (everything after the first `:` and before the last `:`). The reviewer's claim that a `collector_id` containing `:` mis-parses is REFUTED — the greedy middle recovers it intact, and `epoch` is a `u64`. The actual latent fragility: when a `CallFrame`'s `frame_id` is empty, scope falls back to the raw `call_node_id` (`collector_barrier_scope`, `:1372`); if that id contains `:`, the leading split consumes part of it → wrong reconstruction → `node_map` miss → barrier never fires. Node ids are never charset-validated (`validate_workflow`, `model.rs:1111`, checks only duplicates/refs), so a hand-crafted import could carry a `:`-bearing call-node id — but combined with the empty-`frame_id` gate this is unreachable in normal operation.
**Fix:** Replace the string-joined barrier key with a structural key — make the barrier map key a `(scope, collector_id, epoch)` tuple/struct and read `collector_id` directly from it, deleting `collector_id_from_barrier_key` entirely. This removes the parse step so no delimiter can ever collide with node-id contents, eliminating the whole bug class at the root rather than guarding one delimiter. Account for the checkpoint-persistence path: the barrier map is serialized, so add the serde representation for the new key type and handle migration of any on-disk checkpoints that still carry the old string form.
