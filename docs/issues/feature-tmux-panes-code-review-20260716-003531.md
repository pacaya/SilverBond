### H2. Pane-stream fan-out is keyed only by a tmux-local pane ID, leaking output across runs (FIXED)
> **Fix:** Re-keyed pane broadcasters by invocation prefix, tmux binary, socket, and target; threaded cleanup ownership through the composite key, retaining raw pane IDs and leaving spawn metadata untouched.
**Severity:** HIGH — silent cross-run leak of live terminal content on default configuration, reachable with two concurrent runs and no error surfaced to either operator.
**Files:** `src/app.rs:129` (`PaneStreamRegistry` type), `src/api.rs:1305-1348` (`subscribe_pane_stream`, esp. `:1314,1319-1321,1332-1337`), `src/app.rs:153` (`unsubscribe`), `src/app.rs:176-190` (`remove_terminal_sender`), `src/tmux_exec.rs:83-86,2118` (per-run socket default, raw `#{pane_id}` capture), `src/api.rs:2888-3100` (existing single-run registry tests)
**Description:** `PaneStreamRegistry` is a `HashMap<String, PaneStreamEntry>` keyed only by pane target (`src/app.rs:129`); `subscribe_pane_stream` indexes it with `get_mut(pane_target)` (`src/api.rs:1314`) and `insert(pane_target.to_string(), …)` (`src/api.rs:1332-1337`), ignoring the `run_id` and `invocation` it already receives. Pane IDs are unique only within one tmux server, and `build_tmux_invocation` gives each run its own socket by default (`src/tmux_exec.rs:83-86`, asserted by `build_invocation_defaults_to_run_scoped_socket`), so two concurrent runs both legitimately own `%0` — the target stored at `src/tmux_exec.rs:2118` is the raw `#{pane_id}`, never socket- or session-qualified. Run B's subscribe then finds run A's entry, bumps the refcount, and returns **A's broadcaster** (`src/api.rs:1319-1321`); B's own stream task never spawns. B's snapshot is correct (`send_snapshot` uses B's invocation, `src/api.rs:1010`) but every live frame is A's terminal bytes — a cross-run confidentiality leak plus B never seeing its own pane. The stream-token boundary does not help: each run names its own `%0`, so the ownership check passes for both. Cleanup shares the under-scoped key — `remove_terminal_sender` (`src/app.rs:176-190`) drops the entry when A's task exits, stalling B's still-attached socket.
**Fix:** Key the registry by the full tmux-server identity plus the target, which is the actual namespace a pane id lives in:
- Derive a stable identity from `TmuxInvocation` — add `Hash`/`Eq` or an `fn identity(&self) -> String` covering `prefix`, `tmux_bin`, and `socket` — and key `PaneStreamRegistry` on `(invocation_identity, pane_target)`. A pane id is unique per tmux server, and a server is identified by socket **plus** the owning user/prefix (`sudo -u other` with the same socket name is a different server, since the socket path is per-user).
- Carry that key through subscription, `PaneStreamGuard`, `unsubscribe`, `remove_if_sender`, `remove_terminal_sender`, and `cleanup_pane_stream_task_exit`.
- Do **not** key on `(run_id, pane_target)`: `run_as.socket` is user-configurable, so two runs may deliberately share one tmux server where `%0`/`%1` are genuinely distinct and dedup is correct; a run-scoped key would spawn two independent `stream_pane` readers against the same pane.
- Ensure identity derivation is stable across the persisted-vs-resolved invocation paths (`load_or_resolve_run_tmux_invocation`, `src/runtime.rs:3214-3233`); persisted invocations make this tractable.
- Add a regression test with two invocations that both expose `%0` and assert channel isolation — all seven existing registry tests (`src/api.rs:2888-3100`) are single-target/single-run, so this is a genuine coverage hole.

### H3. Live pane streaming hangs under the documented low-privilege `runAs` setup (FIXED)
> **Fix:** Replaced upstream temp FIFO streaming with timed root-local cross-user FIFOs, explicit chmod, nonblocking reads, lifecycle signalling, weak sender ownership, cleanup, and regression coverage including WebSocket error delivery.
> **Reopened and re-finalized 2026-07-17.** This finding was reopened to re-decide its transport after M5's verification suggested control-mode `%output` IPC could subsume it. **Control mode was evaluated against real tmux and rejected** (see Fix). The reopen was still load-bearing: costing found **two defects in the FIFO fix as originally written** — a `mkfifo` umask flaw that reproduced the hang class, and an `O_RDWR` design that never terminates. Both are corrected below. Severity, Files, and Description are unchanged from the original finalization.
**Severity:** MEDIUM — lowered from HIGH. This is a known, documented upstream tradeoff (`stream.rs:27-31`), not a regression; execution is unaffected and the WebSocket still serves snapshot + manual resync, so the feature is degraded rather than dead. Held above LOW because the containment path is documented and recommended, the UI does consume this socket, and the failure is silent and leaks blocking-pool threads. **ID retained as `H3`** — IDs are stable across sessions and `M3` is already taken.
**Files:** `src/api.rs:1290-1303` (`start_pane_stream`), `src/api.rs:1296,1298,1457` (blocking `spawn_blocking` + `File::open` chain), `src/api.rs:1085` (unreachable error frame), `src/api.rs:717-719` (`SILVERBOND_AGENT_USER` → `RunAsConfig`), `src/tmux_exec.rs:67-75` (`sudo -u <user> -H --` prefix), `tmux.rs:95-113` (thread-local invocation), external `tmux-tools-core` `stream.rs:23-31,36,41,47,90-105`
**Description:** `start_pane_stream` (`src/api.rs:1290-1303`) wraps `stream_pane` in `with_invocation`, but that only installs a **thread-local** consulted by `crate::tmux::run*` (`tmux.rs:95-113`). `make_fifo` (`stream.rs:90-105`) bypasses it entirely — it shells out to `mkfifo(1)` with no mode argument — so the FIFO is created by the **server** user while the `pipe-pane … "cat > <fifo>"` writer runs inside a tmux server started via `sudo -u <user> -H --` (`src/tmux_exec.rs:67-75`). `pipe-pane` returns success immediately (tmux never reports the child's fate), so `stream.rs:36` passes, the `cat` writer dies, and the reader's `File::open` at `stream.rs:41` blocks forever with no timeout, select, or watchdog anywhere in the chain. The WebSocket delivers its snapshot (`src/api.rs:1010`) then heartbeats indefinitely; `pane_receiver.recv()` never fires and never returns `Closed`, so the "pane stream unavailable" frame at `src/api.rs:1085` is unreachable. **Correction to the original report:** the `0644`/EACCES mechanism holds only on Linux. This repo targets macOS, where `std::env::temp_dir()` honors the per-user `TMPDIR` (`/var/folders/…/T/`, `drwx------`); the run-as user fails at directory traversal and never reaches the FIFO, so a chmod-the-FIFO fix would not help. **Aggravator:** each hung attempt leaks two blocking-pool threads (the outer `spawn_blocking` at `src/api.rs:1296` blocked in `block_on`, plus tokio's internal `asyncify` thread blocked in `open()`), never reclaimed, and the registry entry never clears — unbounded across panes and reconnects. A prior fix (M8, 20260620) swallowed the `File::open` context string at `stream.rs:47` into a generic message, further hiding this failure.
**Fix:** Reimplement stream setup inside SilverBond over a cross-user-safe FIFO, guarded by a timeout, with the stream task's lifetime owned by the existing pane lifecycle rather than by FIFO EOF. `tmux-tools-core` is an external, rev-pinned git dependency (`Cargo.toml`, `rev = "69173d1…"`) and is **not editable in this repo**; this also matches the R2-1 precedent (`docs/issues/code-review-20260608_part_3_of_4.md:85`) of staying "entirely within SilverBond (no external-crate change)".
- Stop calling `tmux-tools-core::stream_pane` from `start_pane_stream`; create the FIFO in a SilverBond-owned directory under `SILVERBOND_ROOT/run-states/` (mode `0711` — traversable, not listable) with an unguessable name, rather than in `temp_dir()`. This escapes the per-user `TMPDIR` and fixes macOS and Linux alike.
- **`mkfifo` then explicitly `chmod(0622)`.** ⚠ **Correction — the original spec was defective here:** `mkfifo` mode is masked by umask, measured as `mkfifo(path, 0622)` → **`0620`**, silently stripping the other-write bit that is *exactly* what the run-as writer needs to open the FIFO `O_WRONLY`. Passing the mode to `mkfifo` alone **reproduces the hang class this finding exists to fix**. An explicit `chmod` after creation was verified to yield `622`. Also ensure the run-as user can traverse `SILVERBOND_ROOT`.
- Open the read end `O_RDWR|O_NONBLOCK` so the reader never blocks on a missing writer — verified non-blocking on macOS (fd returned immediately with no writer present). This structurally removes both the hang and the blocking-thread leak.
- **Design explicit teardown — `O_RDWR` has no natural termination.** ⚠ **Correction — second defect in the original spec:** because the reader's own fd holds a write end open, `read()` returns `EAGAIN` forever after the writer closes, never `0`. Verified. Left as written, this trades a blocking-thread leak for a **task leak**, and `pump_pane_stream`'s EOF path stays dead. Tie the stream task's lifetime to the existing pane lifecycle (`PaneStreamGuard`, `remove_terminal_sender`, `cleanup_pane_stream_task_exit`), which already owns stream-task lifetime: on pane death, teardown drops the sender, surfacing `broadcast::Closed` and finally making the "pane stream unavailable" frame at `src/api.rs:1085` reachable — the frame this finding notes is currently unreachable.
- Issue `pipe-pane` through the invocation (`src/` has zero `pipe-pane` occurrences today — this path is new; the writer remains `cat > fifo`), then bound stream setup with `tokio::time::timeout` so a failed writer surfaces a real error frame instead of a silent hang. The timeout alone is insufficient: `spawn_blocking` is not cancellable, so blocked threads still leak unless the FIFO is opened `O_RDWR|O_NONBLOCK` as above.
- Tests: a different-UID integration test (none exists — `tests/http_api.rs:47,582` only construct `PaneStreamRegistry::default()`), a **umask regression test** pinning the FIFO's resulting mode, and a teardown/termination test asserting the `:1085` frame fires on pane death.
- *Deployment caveat:* `SILVERBOND_ROOT` defaults to CWD (`src/app.rs:51-53`). Under `~/Documents`/`~/Desktop` a sudo'd process would be blocked by TCC. Non-default, but document it. No SIP concern.
- **Rejected — control-mode (`tmux -CC`) IPC, evaluated in full during the reopen.** The earlier "future upstream cycle" note framed this as blocked by the rev pin; that was wrong (a `-CC` client would live inside SilverBond). It was rejected on different and stronger grounds: **its multiplexing premise is false at the current cardinality.** Tested against real tmux, a `-CC` client attached to a session sees `%output` for that session's panes and nothing from other sessions — and `spawn_pane` creates **one `new-session` per pane** (`src/tmux_exec.rs:2099-2118`). So "one client per invocation" is unachievable: you get one long-lived `sudo`+`tmux` process pair *per pane* — the same cardinality as the FIFOs, with no multiplexing benefit. The payoff requires restructuring session-per-pane → session-per-run, rewriting `spawn_pane`/`PaneGuard`/`SessionGuard`/`cleanup_panes`/session-ownership — putting the **execution** path (which this finding does not touch) at risk to fix an observability bug. Cost is ~900–1400 LOC of hand-rolled protocol parser, supervisor, and command correlation (no control-mode crate in `Cargo.lock`) versus ~250–350 for the FIFO. Fairer than expected on several risks — `tmux -C` needs no tty so the sudo path fails fast rather than hanging; `%output` octal escaping is lossless and byte-exact for invalid UTF-8; `tokio::process::Child` is cleanly async — and it does supply M5's atomic boundary, but M5 is LOW and cosmetic, so the trade is poor value. Revisit only if session-per-run is undertaken for independent reasons.
