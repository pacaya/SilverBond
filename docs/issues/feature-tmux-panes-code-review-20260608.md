### C1. Decide node mis-routes branches via fuzzy NL prose matching (FINALIZED) (FIXED)
**Severity:** HIGH — wrong-branch routing with no error, but the exact-match fast path handles disciplined single-token replies and prompt echo is already stripped by the sentinel.
**Files:** src/runtime.rs:3022 (`select_decide_outcome`), src/runtime.rs:2811/2853 (`run_decide_node`), src/runtime.rs:2996 (`render_decide_prompt`), src/runtime.rs:5376/5405 (`wrap_prompt_for_json`/`parse_structured_output`), src/model.rs:1755 (outcome validation)
**Description:** `select_decide_outcome` tries an exact-match fast path (runtime.rs:3029), then scans the agent's reply with case-sensitive `\b<label>\b` regexes and picks the **earliest match offset** (runtime.rs:3048-3052); only an exact offset+length tie returns `None`. `render_decide_prompt` (runtime.rs:2996) appends no outcome list and no "emit only the token" instruction, so a reply like *"I would not reject this; approve."* silently routes to `reject` — the wrong branch, with no error and no negation handling. (Note: there is no native driver `json_schema` slot — runtime.rs:2735 is `let json_schema = None`; structured output is done via prompt-injected JSON artifacts.)
**Fix:** Constrain the decide agent to emit a single-value JSON artifact and match it exactly, keeping the NL scan only as a fallback. Concretely: in `render_decide_prompt`, append an instruction to emit `{"outcome":"<one-of-config.outcomes>"}`, reusing the existing `wrap_prompt_for_json` path (runtime.rs:5376); parse the field via `parse_structured_output` (runtime.rs:5405) and validate against `config.outcomes` (validation already exists at model.rs:1755); fall back to the current earliest-offset scan only when the JSON field is absent. Update the raw-string decide tests (e.g. runtime.rs:8856) to cover the new artifact path.

### C2. Crashed/exited agent reported as Completed/Success (FINALIZED) (FIXED)
**Severity:** CRITICAL — silent success-masking propagates a truncated/garbage capture into downstream nodes presented as a valid response; worst class of orchestration bug.
**Files:** src/tmux_exec.rs:1982 (`wrap_keep_open`), src/tmux_exec.rs:1175 (`poll_agent_interactive`), src/tmux_exec.rs:1283/1319-1325 (`is_interactive_completion_reason`), src/tmux_exec.rs:1240-1242 (`SubagentActive` deadline bump), src/tmux_exec.rs:826-836 (caller hard-codes success)
**Description:** `wrap_keep_open` builds `cd {cwd} && {{ {cmd}; }}; exec zsh -li` (tmux_exec.rs:1982) — `;`-separated, so when the agent crashes the shell still execs `zsh -li` and the pane stays alive on a frozen frame. `poll_agent_interactive` has no liveness signal; the frozen screen makes `progress.observe` return `IdleReason::Idle`, and `is_interactive_completion_reason` maps that to success whenever `allow_idle_completion` (tmux_exec.rs:1321), so the caller returns `NodeResult { success: true, exit_code: 0, outcome: Success }` (tmux_exec.rs:826-836). A crashed agent is reported as a successful node.
**Fix:** In `is_interactive_completion_reason` (tmux_exec.rs:1319), drop the `IdleReason::Idle => allow_idle_completion` success path so completion requires an affirmative signal — `ReadyMatched` (the agent's own ready-prompt regex is visible = alive and idle at its prompt) or `UntilMatched` (the `SB_RESPONSE_DONE` sentinel, always folded into `until_regexes` at tmux_exec.rs:1310-1314, was printed). Bare screen-idle no longer completes:
- A task idle-waiting on a silent subagent keeps polling until its deadline, which the existing `SubagentActive → deadline = now + subagent_timeout` handler (tmux_exec.rs:1240-1242) already extends — so complex tasks are not killed prematurely.
- A crashed agent's frozen `zsh -li` prompt matches neither the agent ready regex nor the sentinel, so it falls through to `TimedOut`/failure instead of false success.
- Optional fast-fail enhancement: query `#{pane_dead}` in the poll loop so a real crash fails immediately instead of burning the full deadline.
- Add a regression test: stable screen + no sentinel + no ready-match must not return `Completed`.

### H1. tmux panes/sessions leak on normal run completion (FINALIZED) (FIXED)
**Severity:** HIGH — unbounded, silent leak of orphan tmux sessions/processes on the most common termination path; accumulates across every run.
**Files:** src/runtime.rs:5128 (`finalize_run`), src/runtime.rs:5193-5194 (cleanup + `registry.clear`), src/runtime.rs:5198-5200 (`cleanup_reused_session_panes` empty-set early return), src/runtime.rs:1307-1313 (`build_session_persistence_set`), src/runtime.rs:1831-1834 (`kill_active_run_panes`, Aborted-only gate), src/runtime.rs:703-705 (`registry.clear`), src/runtime.rs:531 (`ActiveRun`, no `Drop`)
**Description:** On `Completed`/`Failed` termination `finalize_run` only calls `cleanup_reused_session_panes` then `registry.clear`. The former kills only `continue_session_from` panes and early-returns when that set is empty (runtime.rs:5200) — empty for any workflow without session reuse — while `registry.clear` (runtime.rs:703-705) just `remove`s the `ActiveRun`, which has no `Drop` (runtime.rs:531), so its `active_panes` map is discarded without touching tmux. Panes registered by Spawn nodes and by `RunAgent` with `kill_after:false` therefore survive in tmux forever; every such run leaks a session and orphans accumulate.
**Fix:** In `finalize_run`, sweep **all** of the run's `active_pane_targets` except those in `build_session_persistence_set`, reusing the existing `cleanup_panes` helper (mirror the abort path's `kill_active_run_panes` at runtime.rs:1831 but subtract the persisted `continue_session_from` keys). Place the sweep so it runs on every non-persisted terminal status, not just Aborted. This single change resolves both Completed and Failed leaks — **H2 is folded into this fix** (same root cause, same teardown path).

### H2. tmux panes leak on failed runs (kill sweep gated on Aborted only) (FINALIZED) (FIXED)
**Severity:** HIGH — same unbounded orphan-pane leak as H1, on the Failed-run path.

### H3. Concurrent pane viewers all dropped on one transient producer read error (FINALIZED) (FIXED)
**Severity:** MEDIUM — mechanism is real but the dramatic trigger is rare: pane death surfaces as `Ok(0)` EOF (correctly closes all viewers), so only a transient non-EOF `Err` on a still-alive pane mis-collapses viewers. Lowered from HIGH; ID kept as H3.
**Files:** src/app.rs:96-105 (`remove_if_sender`, no refcount check), src/app.rs:84-94 (`unsubscribe`, refcount-guarded — the asymmetry), src/api.rs:758-783 (`subscribe_pane_stream` refcount/re-subscribe), src/api.rs:828-835 (EOF `Ok(0)` break), src/api.rs:848-856 (read-`Err` break, no retry), src/api.rs:864-867 (teardown call), src/api.rs:653-668 (receiver `Closed`)
**Description:** One producer task serves all viewers of a `pane_target`; later subscribers bump `refcount` and re-`subscribe()` the shared `broadcast::Sender`. EOF (`Ok(0)`) and any read `Err` take the same `break` path (api.rs:828/848, no retry), and `remove_if_sender` (app.rs:96) drops the registry's last `Sender` regardless of `refcount`, so every other live `Receiver` gets `RecvError::Closed` (api.rs:653-668) and its socket closes. The survivor's later `unsubscribe` hits the `None` branch and no-ops, silently losing the refcount. No restart path exists — recovery needs a fresh client connection. The genuinely buggy case is a transient `Err` on a live pane; on real pane death (EOF) closing all viewers is correct.
**Fix:** Keep a live pane streaming through a transient error instead of collapsing it. In the producer loop: distinguish `Ok(0)` EOF (final — tear down) from a read `Err` (transient — retry with bounded backoff and continue reading rather than `break`); and on any teardown, remove the entry only when `refcount == 0` (fold in the refcount-guard so `remove_if_sender` matches `unsubscribe`'s semantics), letting remaining subscribers keep/restart the producer. Cap the retry/backoff so a genuinely unreadable pane still terminates. Note: Option 1 (refcount-guard alone) was rejected — it stops the silent leak but leaves survivors with an open-but-frozen stream, not solving the liveness problem.

### M4. Lost resync wedges the pane view stale permanently (FINALIZED) (FIXED)
**Severity:** LOW — overstated: the server proactively re-snapshots on its own lag/backpressure (api.rs:650/627), and broadcast lag is the only source of seq gaps, so a true permanent wedge needs a half-open socket where the server snapshot also fails to arrive (a dead socket would error server-side and trigger reconnect). Narrow residual risk. Lowered from MEDIUM; ID kept as M4.
**Files:** ui/src/lib/api/client.ts:252-254 (resync fire on gap), ui/src/lib/api/client.ts:185-189 (`requestResync`, no ack/retry/timeout), ui/src/lib/api/client.ts:257 (`data` early-return while pending), ui/src/lib/api/client.ts:245 & :215 (clear on snapshot / reconnect), ui/src/lib/api/client.ts:223 (`onStatus("open")` never downgrades), src/api.rs:650 & :627 (server proactive snapshot)

(Rejected: a resync-only timeout — symptomatic, covers only the seq-gap path; degraded-status-only — fixes the false "Live" lie but doesn't repaint data without reconnecting.)

### M6. In-flight tmux agent node has no cooperative abort (FINALIZED) (FIXED)
**Severity:** MEDIUM — abort of a node parked mid-interaction stalls the *entire orchestrator loop* for up to the full deadline (300s/600s), not just one node; the mid-poll case is mild (~250ms). Confidence raised to ~90.
**Files:** src/tmux_exec.rs:1175-1300 (`poll_agent_interactive` poll loop, deadline at :1291), src/tmux_exec.rs:1115-1172 (`wait_for_agent_ready_interactive`), src/runtime.rs:533 (`ActiveRun` `abort_flag` AtomicBool), src/runtime.rs:989 (`abort_run` sets flag only), src/runtime.rs:1803-1814 (abort branch: kill panes → `abort_all` → `join_next().await`), src/runtime.rs:1975-1981 (250ms select sleep arm), src/runtime.rs:397 (`InteractionEscalation::request` `block_on`), src/runtime.rs:5502/5504 (parked `receiver.await`), src/runtime.rs:5194 (`registry.clear` drops sender in `finalize_run`)
**Description:** `poll_agent_interactive`/`wait_for_agent_ready_interactive` are plain sync loops inside `spawn_blocking` with zero abort references (grep-confirmed); they exit only on completion regex, wall-clock deadline (:1291), or a capture/send `Err`.
