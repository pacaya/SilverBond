# Model/CLI routing via allow-listed named profiles

Per-execution model and CLI selection goes through named profiles — coherent bundles of `agent` + `model` + `reasoningLevel` + `toolToggles` + related agent config — never through raw model strings in variables. Profiles live in an app-global catalog persisted as an app-level `profiles.json` beside `workflows/` (file-based like the definition store, UI-edited) and in a new workflow-local `profiles` map — deliberately distinct from `agentDefaults`, which stays keyed by agent name and carries no `agent` member (`src/model.rs:255`); resolution precedence is node config → workflow-local `profiles` → app catalog → driver defaults, extending the existing merge chain (`resolve_agent_config`, `src/model.rs:301`). For a node that selects a profile, the profile replaces the `agentDefaults` layer entirely — it bundles the same fields; `agentDefaults` continues to govern only `agent`-selected nodes, preserving brownfield behavior on that path. Nodes select a profile via a node-level `profile` field, mutually exclusive at validation with *every* CLI-determining selector — `agent`, `runAgentConfig.agent`, `spawnConfig.agent`, and `spawnConfig.command` (a raw-command spawn runs no agent at all, so a profile could never take effect on it), since the nested selectors take precedence in `explicit_agent_for_node` (`src/model.rs:57`) and would otherwise shadow the profile's CLI (explicit node-level config fields still override the profile's non-CLI fields; today `agent` is mandatory on task/run_agent nodes, `src/model.rs:1669`). A variable used as a profile selector is allow-listed: it can only name declared profiles. The profile catalog is frozen into the run's immutable snapshot at start (as `workflow_json` freezes today); selectors resolve against the frozen catalog whenever they bind — root selectors at run start, callee selectors at subflow call time — with unknown names a hard error either way, so resume and restart cannot drift when the catalog changes and late-bound subflow inputs stay legal. The resolved profile/model is recorded in the execution log; each profile declares a routing tier (`cheap | standard | high`) as an organizational label — acceptance oracles read resolved model ids, never tier labels. Because resolved configuration proves what was *requested*, not what ran, the `AgentDriver` seam gains exactly one extension: an actual-model capture hook, implemented per driver where the CLI exposes its model (`AgentOutput.model_used` has no producer today — structurally always `None`); harness-port owns the per-driver wiring, and this is the initiative's only driver-seam change. The `decide` node's model path routes through the same profile resolution via the one canonical selector — the node-level `profile` field; `DecideConfig` gains no second selector, and setting `DecideConfig.model` alongside a node `profile` is a validation error — defaulting to `decide`'s current one-shot behavior when no profile is set, with its invocations recorded in the execution log. Nodes linked by `continueSessionFrom` must resolve to the *same effective session configuration* as their source — same profile and identical session-shaping node overrides (model, system prompt, toolToggles, budgets, tool allow/deny lists, extra args, access mode, and effective working directory — full identity across every spawn-time field, not the legacy one-way access inequality) — validated at bind time with a hard error otherwise (static validation cannot see late-bound selectors): a reused pane keeps the session-shaping configuration it was spawned with — config becomes CLI arguments only at spawn (`src/tmux_exec.rs:2257`) — so a differing destination profile could never take effect, and requiring identity keeps the execution record honest; the existing static agent/access/cwd checks (`src/model.rs:2022`) remain as the floor for non-profile continuations. The tmux-tools agents registry remains the machine-level truth of which CLIs are installed; profiles reference registry agents, keeping the dependency direction app-config → installation-state.

## Considered Options

- **Template expansion in raw `agent`/`model` fields** — rejected: stringly, typo-surfaced-at-runtime, and save-time validation loses meaning; per-run selection of coherent bundles is the LiteLLM alias→deployment pattern, the one proven shape in the survey.
- **Branching to differently-configured node subgraphs** — rejected: duplicates entire subgraphs per CLI, the combinatorial rot this initiative exists to remove.
- **Workflow-local profiles only (no app catalog)** — rejected: sharing profile bundles across the user's workflows without copy-paste drift is an explicit requirement; the dangling-reference cost is accepted as a hard run-start error, with export-bundling additive later.

## Consequences

A workflow referencing app-catalog profiles is no longer self-contained; sharing it to another machine can dangle. Accepted for now as a hard run-start error; an export path that inlines referenced app-catalog profiles into the workflow-local `profiles` map is additive later. An ungated override surface is a known CVE class (Flowise), hence allow-list-only selection.

## Evidence

- Routing prior art: Dify declining per-run model selection, LiteLLM alias indirection, Flowise per-node overrides and CVE.
